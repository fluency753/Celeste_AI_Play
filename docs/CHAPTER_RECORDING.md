# 分章录制与菜单冻结

新运行默认 `--recording-mode chapter`：每章一个录像，不录选章过程，包含章节开场、游玩和完整结算；从章节退出时的加载与解锁提示也保留，回到选章地图后结束本片。补收集等需要跨章连续录像时使用 `--recording-mode continuous`。旧运行续跑沿用原来的连续录制，避免中途改变录像组织。

三个菜单冻结开关独立配置，控制台也可设置：

| 参数 | 新运行默认 | 范围 |
| --- | --- | --- |
| `--freeze-chapter-select` | 开 | 选章地图和章节面板 |
| `--freeze-file-select` | 关 | 存档选择 |
| `--freeze-main-menu` | 关 | 主菜单 |

各参数均支持 `--no-…`。只在菜单准备好接收输入时冻结；保存和自动加载照常完成。冻结后仍可显式发送输入，主控不自动代选下一章。菜单冻结与录像过滤独立，连续模式可同时冻结选章。

分章模式由 Bridge 同时过滤视频节拍和独立录音 PCM，章节第一帧开始同步采集；返回地图时截断尚未执行的复合输入，并向 agent 报告剩余计划，不自动重放。下一次显式推进前，主控关闭旧片并准备新片。只经过菜单、未进入章节的空片不发布视频。加载器中的解锁提示仅在本片已有章节上下文时计入，冷启动停在提示上不会凭空开启章节录像。

## 恢复与收尾

`recording/chapters.json` 是整个录像序列的权威清单，每片有独立 ID 和 `chapter-NNN/session.json`；运行内的 `recording_session.json` 是当前片指针。换章前先保存下一片的启动意图，回执丢失后按原 ID 核验并恢复，不能重新创建一片。单片异常恢复仍走原有累计媒体恢复路径。

停止、交还控制和离线收尾会检查整份清单，不能仅凭当前片结束就认为全部完成。旧片的转码离线执行，不占用游戏，也不覆盖当前片指针。准备了但尚未启动的下一片可直接取消；不录制续跑不会另建下一片。修改录像组织须先完整收尾，再使用 `--new-recording` 明确开启新录像。

本功能需要同时更新主控和 Bridge 1.9.0；Runtime 保持 1.0.5，无核心代码变化。已有连续录像可按原方式续录。分章模式要求独立游戏音频 `game_nrt`。

## 验证范围

隔离游戏验证了菜单冻结、选章视频与 PCM 同时排除、序章首帧、章节加载器上下文及复合输入截断。真实 Terra 工具接收验证了“计划 901 帧仅执行 1 帧、剩余 900 帧未执行”的理解，没有自动重放。实际 FFmpeg 验证了两片分别产出完整与纯享视频及各自帧数。

本次原生采集使用私有时钟协议客户端核验 F/N 和 PCM 槽，没有进行真实 OBS 最终像素编码验收或人工听音。进入章节前重建录音混音器清除了正常选章产生的历史音效副本；实时系统尚存活的本次入口尾音仍可能保留。
