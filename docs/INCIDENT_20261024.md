# 故障说明：后台进程随启动它的聊天会话一起退出（2026-10-24）

时间均为北京时间（UTC+8）。

## 概要

2026-10-24 19:06，一次原生 GPT 试玩中，主控、HUD 服务和 HUD 窗口同时退出：智能体的游戏工具与 HUD 心跳失去接收端，试玩中断，没有写出 `summary.json`，录像也没有正常收尾。游戏、OBS 与 Codex 桌面端本身都还在运行。

原因：这几个进程是从一个 AI 编程助手的聊天会话里用"命令执行"工具启动、并保持在后台运行的，它们都是那个聊天的命令会话的子进程。聊天被回退重建时，助手关闭旧的执行环境，并结束它启动的全部进程，主控和 HUD 跟着被结束。

结论：**长时间运行的主控、HUD 等后台进程不能挂在某个聊天或终端的命令会话下面。** 正确做法是用 `orchestrator/background.py` 提供的独立宿主启动它们（`start_gpt.ps1 -Play` 现在默认就这样做）。

## 经过

1. 18:59，在 Codex 聊天里用命令执行工具启动主控与 HUD 服务，并让命令会话保持运行；试玩开始。
2. 19:05:56，桌面端对这个聊天发出中断请求；19:06:06 关闭该聊天的执行环境（Codex 日志里是 `operation="shutdown"`、`Shutting down Codex instance`、`Agent loop exited`）；19:06:07 回退成功并重新加载会话。
3. 智能体事件日志与 `metrics.json` 的最后写入时间都是 19:06:06，此后没有 summary，也没有正常的录制收尾记录。
4. 事后检查：游戏、OBS 和 Codex app-server 仍在运行，主控与 HUD 的 Python 进程都已不存在。19:05:30–19:07:30 的 Windows 应用与系统日志里没有崩溃事件（没有崩溃事件本身不能完全证明没有崩溃）。

## 原因分析

Codex 关闭会话执行环境时（`shutdown_session_runtime`）会调用 `unified_exec_manager.terminate_all_processes()`，结束这个会话用命令执行工具启动的全部进程（见 [openai/codex 的 `codex-rs/core/src/session/handlers.rs`](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/handlers.rs)；核对的是当日 main 分支的实现，不是逐行比对当时所用的 alpha 版本）。主控与 HUD 正是这样启动的，所以随旧执行环境一起被结束。

这个结论来自日志时间线、启动记录与上述实现的对照，属于因果推断：当时没有逐个进程的退出码记录。日志能确认桌面端发出了回退请求，但不能确定当时具体点了哪个控件。

同样的问题适用于任何"在聊天助手或终端里启动、依附于那个会话"的后台进程：会话结束、被回退、被编辑重建，或终端窗口关闭，都可能连带结束它们。

## 恢复

1. HUD 恢复后，原主控仍未运行；桌面聊天页接管了原来的独立会话，但在那里继续对话拿不到原进程提供的动态工具。
2. 第一次续跑因 `already has an active writer`（同一个线程正被桌面端占用）失败。`CodexRunner` 随后补上了只针对这个错误的恢复分支：复制历史另起线程继续运行，并通过了相关测试。
3. 19:10:30 续跑恢复了游戏操作与 HUD 心跳，沿用原来的存档、探索知识范围、规划回放、连续 BGM，以及"完成 1A 后停止"的目标。

## 修复

19:16 完成生命周期修复：

- `orchestrator.background` 通过 Windows WMI 服务（`Win32_Process.Create`）启动独立宿主，主控不再是任何聊天命令或终端的后代进程。不需要管理员权限，不添加定时任务或全局快捷键。
- 宿主持有单实例互斥量，并检查游戏工具端口，避免重复接管游戏桥接。
- 标准输出与错误写入 `local/background/<启动时间>/output.log`；启动 PID、结束时间和退出码写入同目录的 `status.json`。
- `start_gpt.ps1 -Play` 默认使用独立宿主；`-Resume <运行目录>` 续跑。只有显式加 `-Foreground` 才在调用它的终端里运行（调试用）。准备、聊天、HUD 服务与 HUD 窗口也可以由同一种宿主启动。
- 修复后在安全暂停、录制收尾之后，把这次试玩迁移到独立宿主上继续，同一个智能体会话与存档不变，HUD 心跳重新连上，试玩恢复。

验证：`calibration/background_test.py` 实际结束启动命令的进程后，检查独立宿主及其子进程仍在运行，再等它正常退出，确认退出码记录为 0。没有用"编辑正式运行中的聊天"这种破坏性的方式重现中断。

## 教训

- 需要长时间运行的进程（主控、HUD 服务、HUD 窗口、准备与聊天后台）要用独立宿主启动：`python -m orchestrator.background -- <主控参数>`，或直接用默认就这样做的 `start_gpt.ps1 -Play`。
- 在 AI 助手的聊天里用命令工具启动主控（包括 `start_gpt.ps1 -Foreground`），只适合短时间调试：编辑、回退或关闭那个聊天，进程就可能被结束。在你自己打开的终端里前台运行（例如 `start_local.ps1`、`python -m orchestrator.run`）没有这个问题，但关闭那个终端窗口同样会结束主控。
- 后台进程出问题时，先看 `local/background/` 下对应目录的 `status.json`（状态、PID、退出码、错误）与 `output.log`。
