### 2.1 生成 Claude Code 令牌

在自己的电脑上、普通（非管理员）PowerShell 里操作，任意目录都可以：

1. 安装 Claude Code：执行 `irm https://claude.ai/install.ps1 | iex`。安装过程不显示进度，结束后关闭这个窗口。
2. 新开一个 PowerShell，执行 `claude --version`，能打印版本号即安装成功。若提示找不到 `claude`，改用完整路径 `& "$env:USERPROFILE\.local\bin\claude.exe"` 代替下面命令里的 `claude`。
3. 执行 `claude setup-token`。浏览器会打开 Claude 授权页，用 Max 账号登录并点授权；若浏览器没有自动打开，就把终端里显示的链接复制到浏览器。
4. 授权完成后，终端会打印一长串令牌（有效期一年）。用鼠标选中整串令牌并复制，注意换行显示的部分也要选全。
5. 执行 `notepad .env`（在仓库根目录下），把令牌粘贴在 `CLAUDE_CODE_OAUTH_TOKEN=` 后面，不加引号和空格，保存并关闭。
6. 令牌等同于账号凭据：不要发给任何人，也不要提交到仓库。`.env` 已被 `.gitignore` 排除。
7. 核对：带上该令牌执行 `claude auth status`，`authMethod` 应为 `oauth_token`。实测（2026-10-22，Claude Code 2.1.309）：`opus`（claude-opus-5-5）与 `fable`（claude-fable-5-1）均可调用，上下文窗口均为 100 万 token。

### 2.2 Python 虚拟环境

在仓库根目录的 PowerShell 中执行一次：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

之后所有 `python` 命令都可以用 `.\.venv\Scripts\python.exe` 代替，或先执行 `.\.venv\Scripts\Activate.ps1` 激活虚拟环境。依赖见 `requirements.txt`：`mcp`（游戏工具服务）、`pillow`（截图放大、游戏内 HUD 的绘制）、`uvicorn`（本机 HTTP 服务）、`numpy`（规划回放挑选路线）、`pywebview`（网页 HUD 的独立窗口，只在 Windows 上安装）。

### 2.3 安装 Docker Desktop

1. **装 WSL**（管理员权限，需要重启）：右键开始按钮 →"终端（管理员）"，执行 `wsl --install --no-distribution`，完成后重启电脑。Docker 不需要 Ubuntu 等发行版。
2. **检查 WSL 版本**：重启后在普通 PowerShell 执行 `wsl --version`，应为 2.1.5 或更新；否则执行 `wsl --update`。
3. **下载并安装**：从 [Docker 官网](https://docs.docker.com/desktop/setup/install/windows-install/) 下载 `Docker Desktop Installer.exe`，双击安装，配置页勾选 **Use WSL 2 instead of Hyper-V**。
4. **首次启动**：在开始菜单打开 Docker Desktop，接受服务协议（个人使用免费），登录与问卷可以跳过；左下角显示 Engine running 即可。
5. **验证**：新开 PowerShell 执行 `docker version`（Client 与 Server 都有版本号）和 `docker run --rm hello-world`（打印 `Hello from Docker!`）。

装好后已经打开的终端里可能找不到 `docker` 命令，新开一个终端即可；主控也会自动去默认安装位置找。

### 2.4 构建智能体镜像与隔离验收

在仓库根目录执行（Docker Desktop 需在运行）：

```powershell
docker build -t celeste-agent:0.1 agent-container
.\.venv\Scripts\python.exe -m orchestrator.verify --agent opus
```

第一次构建约 1～2 分钟。镜像里有固定版本的 Claude Code（2.1.309）、Python 3 与 numpy、scipy、numba、pillow、networkx、gcc / g++，没有任何游戏文件。

验收脚本会创建（或复用）智能体容器 `celeste-agent-<标签>`（上例是 `celeste-agent-opus`），逐项检查并打印"通过 / 不通过"：

| 类别 | 检查内容 |
| --- | --- |
| 认证 | 容器里的 Claude Code 使用订阅令牌（`oauth_token`），环境里没有 API 密钥 |
| 防火墙 | Claude Code 本身只能连到 Anthropic 官方域名与宿主机上主控的游戏工具端口；任意网站、直连 IP、外部 DNS、宿主机其他端口（包括游戏桥接端口）全部失败 |
| Bash 沙箱 | 让容器里的 Claude Code 用 Bash 工具运行同一套检查：全部失败，包括 Anthropic 与主控端口；命令环境里看不到登录令牌；只能写工作区与 `/tmp` |
| 重算程序沙箱 | 自动重试时主控运行智能体程序用的沙箱（bubblewrap，独立网络命名空间）：同一套检查全部失败；看不到登录令牌；只能写工作区与 `/tmp`，不能写家目录与知识库 |
| 权限 | 智能体用户改不了防火墙、托管配置与 `/etc/hosts`；托管配置拒绝联网工具、禁止退出沙箱 |

实测（2026-10-22）：全部通过。

### 2.5 生成知识库里的参考资料原文

知识库 `kb/` 里的物理常量与机制文件已入库；另外两份社区资料的原文不入库（第三方文本，不在公开仓库里再分发），需要在本机生成一次，生成后随 `kb/` 一起只读挂载进容器的 `/kb/reference/`：

- Celeste Wiki（celeste.ink）的 Tech 总表与全部技巧子页面（转成 Markdown，许可 GPLv3）；
- 草莓酱（Strawberry Jam Collab）训练场 Beginner → Grandmaster 的全部说明文字与机制库全文（英文、简体中文），直接从本机安装的 Mod 压缩包读取。

```powershell
.\.venv\Scripts\python.exe tools\fetch_reference.py
```

游戏目录自动查找（环境变量 `CELESTE_DIR`、部署向导记下的目录、正在运行的 Celeste.exe、各个 Steam 库），找不到时用 `--celeste-dir "<Celeste 安装目录>"` 指定。需要能访问 celeste.ink，并且已经安装草莓酱 Mod（`Mods\StrawberryJam2021.zip`）。只要其中一份时可加 `--skip-wiki` 或 `--skip-sj`。输出在 `kb\reference\`，索引见其中的 `README.md`。实测（2026-10-22）：wiki 17 个页面，草莓酱训练场 230 条、机制库 86 条，共约 310 KB。

另外可以导入你手上的 PDF 资料（同样只放本机），文字版每页标出原文页码，原 PDF 一并复制，智能体需要看插图时可以直接打开：

```powershell
.\.venv\Scripts\python.exe tools\import_reference_pdf.py 资料.pdf --name celeste_mechanics_explained --title "Celeste 机制详解（反向钟）" --note "来源：……"
```

提取文字需要 poppler 的 `pdftotext` 或 `pip install pypdf`。导入的文字版放在 `kb\reference\community\`，准备阶段会要求智能体把它们也读完。本项目实测时导入了两份：反向钟《Celeste 机制详解》（125 页，源码解读与机制详解，文字版约 240 KB）与《岩浆块机制说明》，加上这两份后整份知识库约 34 万 token。只重新生成索引：`tools\fetch_reference.py --index-only`。

## 3. 桥接 Mod：构建、安装与测试

agent 操作触发关卡街机或主菜单 PICO-8 入口时，在切场景及解锁设置等副作用前停止本次输入，返回“这是内置的 PICO-8 小游戏，暂不支持”，提示继续本体关卡。玩家手动游玩不受影响。小游戏尚无截图、冻结及状态适配，不能由 agent 进入。

桥接 Mod（CelesteAIBridge，当前版本 1.9.1）与常驻核心（CelesteAIRuntime，1.0.5）运行在游戏进程内；本机 `127.0.0.1:47774` 的连接（以及 OBS 时钟端口 47776）由常驻核心监听，端口只在核心设置里维护。未接管时游戏照常可玩；测试客户端发送 `activate` 后，游戏在章节内冻结在当前帧（菜单按配置冻结），只有收到 `step` 才逐帧推进。后台完成后的加载器解锁明信片也按剧情呈现冻结，可用 watch／advance 显式处理及原地重载。主控要求桥接 1.4.0 或更新，并核验 `pico8_entry_guard`；默认的录像声音（两条音轨）需要 0.12.7，游戏内 HUD 需要 0.13.0，剧情交给智能体（按输入节点交接）需要 1.0.4，可尝试跳过时提前交接需要 1.0.25，按检查点分段（进入任意检查点）需要 1.0.6。

### 3.1 构建与安装

先关闭游戏。如果 .NET SDK 没有加入 PATH，先执行 `$env:PATH = "<SDK 目录>;$env:PATH"`。然后在仓库根目录的 PowerShell 中执行：

```powershell
.\tools\deploy_bridge.ps1 -CelesteDir "<Celeste 安装目录>"
```

脚本构建并备份安装 `CelesteAIRuntime` 常驻核心与 `CelesteAIBridge` 逻辑两个 Mod。1.3.0 为不兼容的部署结构变化，首次迁移及核心自身更新必须维护重启；1.3.1 要求核心 1.0.2，也必须维护重启安装。启动后日志应分别显示核心与桥接加载成功（核心一行含 `input re-init guard on`）。已安装相同核心的兼容逻辑更新可用 `-HotReload -HudPort 47792` 保持原录像重载，或运行 `tools/reload_bridge.py`；普通 Everest 重载在 Level 中重建房间，在 AreaComplete 中保留原结算场景；自动加载先等待零输入冻结边界，任务 done 不再单独禁止仍持有连接的主控维护；游戏身份由 Bridge／主控核验，核心只持有资源与交接生命周期。桥接1.3.3要求核心1.0.3，本次抽离核心策略也需维护升级。失败保留冻结及 lease 后用 `--retry` 接回，尚未提交的交接可用 `--abort` 撤销；关闭游戏后可用 `-Rollback` 回滚。详见 [桥接重载](BRIDGE_RELOAD.md)，其中列出各版本已完成与待实机重跑的验收。

### 3.2 冒烟测试

1. 确认没有在用主控，启动游戏后执行 `python tools\enter_save.py test --save-slot 10`，只原生继续载入指定存档并保持冻结，不自行退出、选章或跳剧情。若存档没有进行中的章节，会停在地图，需先明确进入测试章节。
2. 在仓库根目录执行 `python tools\bridge_client.py smoke --out-dir smoke`。
3. 通过的标准：冻结 1 秒帧号不变；单帧推进恰好 1 帧；向右走并起跳 51 帧后有轨迹与截图；最后自动交还控制。截图保存在 `smoke\` 里。

### 3.3 测试客户端常用命令

| 命令 | 作用 |
| --- | --- |
| `python tools\bridge_client.py hello` | 查看桥接版本与当前场景 |
| `python tools\bridge_client.py activate` | 保持桥接连接；章节内冻结，菜单按配置冻结 |
| `python tools\bridge_client.py observe --out shot.png` | 读取当前帧的状态、实体、字符地图与截图 |
| `python tools\bridge_client.py step "30,R" "1,R,J" "20,R" --stop death,room --out after.png` | 按帧推进，遇到死亡或换房提前停下 |
| `python tools\bridge_client.py advance --until controllable --max 600` | 空输入推进，直到恢复可操作（过场、重生时用） |
| `python tools\bridge_client.py skip` | 调试用：直接跳过当前剧情，不经过暂停菜单（主控与菜单宏都用暂停菜单跳过，和玩家一样） |
| `python tools\bridge_client.py deactivate` | 交还控制，游戏恢复正常运行 |
| `python tools\enter_save.py <存档名>` | 从标题画面进入该存档的关卡，用暂停菜单跳过开场，停在可操作的第一帧；加 `--chapter 0` 指定章节（0 序章、1 被遗弃之城、2 旧址），加 `--leave-active` 保持接管 |

**预置模拟器的校准（开发用）**：`python calibration\sim_capture.py --chapter 3 --rooms=00-a,01-b --cases 2 --out runs\simcases\3a` 在 test 存档里载入指定房间（`--chapter` 是地图编号：0 序章、1–7 对应第 1–7 章、9 是第 8 章核心、10 是第 9 章告别）、做随机操作，把起止两帧的完整场景与逐帧轨迹存成用例；加 `--targets` 把 Madeline 放到房间里各类实体旁边定点测（同类实体跨章节累计只测 `--per-type` 个，默认 2）；`--speed` 为每个游戏循环推进的帧数（默认 60，即 60 倍速，只跳过中间帧的绘制）；`--assets 文件` 只导出模拟器用的贴图尺寸与精灵动画表。`load_room`、`teleport` 两个桥接命令只在 test 存档上可用，不会动正式存档。

桥接 1.0.13 的测试入口可用 `load_room(chapter=7, mode=2, room="03")` 选择 7C 末房，`mode=0/1/2` 分别为 A/B/C；只传 `chapter` 仍默认 A，不传章节与模式则保留当前地图及面。成功回执表示请求已接受，游戏在下一帧切换场景：先执行不带提前停止条件的中性 `step`，再等待载入完成并核对 `level.chapter/side/room` 与存档槽位，不能立即用旧观测判定进入成功。此能力不改变正式试玩命令行的章节选择。

按键写法：`L R U D` 方向，`J` 跳，`X` 冲刺，`Z` 蹲冲，`G` 抓，`T` 交互，`C` 确认，`B` 返回，`P` 暂停，`N` 日志；`A:角度` 表示左摇杆模拟方向（0 为右，90 为上）。每段以帧数开头，例如 `"6,R,J"` 表示按住右与跳 6 帧。

### 3.4 维护时正常退出游戏

先中断试玩并等待原主控退出、交还桥接连接，再执行（存档槽位须显式指定；有原录像时必须提供原运行目录）：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m orchestrator.maintenance --save-slot 10 --run "runs/<agent>/<time>"
```

维护退出宏要求 Bridge 1.5.1 起；当前发行组合为 Bridge 1.8.1／Runtime 1.0.5，升级核心需要维护重启，1.8.0 还需同步升级主控以获得菜单提示截断。流程只选择暂停菜单的“保存并退出”，不以返回地图替代；然后停止原录制，等 OBS 编码器释放资源，经主菜单的实际按钮和方向关系选择“退出游戏”，确认同一个游戏进程正常结束。加载器正在显示原生解锁提示时，维护宏明确交回，先显式处理提示再重试；受控重载则可在后台完成后直接保留该提示。累计录像合并及纯享版等 Python 后处理在游戏退出后继续，进度与失败原因写入 `local/maintenance-exit-*.json`。没有录制时可省略 `--run`；私有实例用 `--bridge-port` 指定桥接端口。

该入口持有主控互斥锁，不另连在用主控；已知入场／加载、房间转场及屏幕擦除会先有界等待，再继续保存退出。等待共用 600 帧预算和 15 秒墙钟期限（单次 RPC 另受连接超时约束），每次更新都核对存档槽位。加载器只观测，冻结场景只推进单帧中性输入；遇到明信片等剧情输入、未知的不可暂停状态或超时就停下并说明原因，不代按确认或跳过剧情。已经可以打开暂停菜单的剧情仍按正常保存退出处理。

存档不符、未知菜单、录制归属不符或编码器尚未结束时也会停止。不会强制杀进程、关闭 OBS 或自动更新／重启游戏。退出确认后断线不算成功，必须确认原进程以退出码 0 结束；未确认时不自动重发退出按键。原生“保存并退出”本身会增加一次死亡计数，宏保留游戏原有语义。退出成功后再按第 3.1 节部署和启动游戏。

## 4. 运行智能体

下面用命令行说明每一步。不想记参数时，可以用控制台（4.10 节）在图形界面里完成同样的设置、启动与运行中的介入。

### 4.1 让智能体游玩一个章节

1. 启动 Docker Desktop 与游戏，游戏停在标题画面或任意菜单即可（用第 2 节建的、只启用 CelesteAIBridge 的 Mod 配置）。
2. 在仓库根目录执行：

   ```powershell
   .\.venv\Scripts\python.exe -m orchestrator.run --agent opus --save test --model opus --chapter 0 --max-minutes 20
   ```

   录屏默认开启（主控会自己启动 OBS，见 4.4 节）；不录屏时加 `--no-record`。

3. 主控会依次：用菜单宏进入 `test` 存档、跳过开场；接管游戏并核对存档名；在 `127.0.0.1:47780` 启动游戏工具服务；创建或复用智能体容器 `celeste-agent-<标签>`，在容器里启动 Claude Code（无头模式）。智能体先进入**准备阶段**：按顺序把知识库从头到尾读一遍（见下文），整理笔记，然后才开始游玩。智能体结束一轮回复而章节还没通关时，主控发消息让它接着玩；章节完成、时间预算用完或智能体连续 3 轮不调用工具时结束。章节完成时交还游戏控制；没通关就停下时（时间预算用完、出错、Ctrl+C）游戏在章节内冻结在当前帧（菜单按配置冻结），可以续跑（见 4.8 节），不续跑时从控制台“交还游戏控制”（先收尾保留的录像）。
4. 另开一个 PowerShell 查看进度：`.\.venv\Scripts\python.exe tools\run_status.py`（加 `-n 30` 显示更多决策）。

**游玩模式**：速通模式与探索模式二选一（`--mode`），直播模式（`--live`）可以和任一个叠加；主控给智能体的提示词按 模式 × 直播 分版本（`orchestrator/prompting.py`）。

| 模式 | 内容 |
| --- | --- |
| 速通模式 `--mode speedrun`（Claude 执行器默认） | 以最短的游戏内章节计时通关。完整知识库 `kb/`；`--sim`（默认）/ `--no-sim` 决定是否开放预置模拟器，把速通模式分成两个版本（4.5 节）。游戏工具：`observe`、`act`、`narrate`、`set_effort`、`stop_run` |
| 探索模式 `--mode explore`（原生 GPT 执行器默认） | 新手探索、学习并完成指定章节，不以速通为目标。只读 `kb/explore`（基本操作与工具说明），不开放模拟器文件；`--sim-assist`（默认开）提供有额度的短路线预测。另有 `cutscene`，开了限额预测时有 `simulate`。详见 [LIVE_ADAPTATION.md](LIVE_ADAPTATION.md) |
| 直播模式 `--live`（叠加，默认关） | 观众实时观看：解说计时 10 秒（不开直播时半分钟）、用户可以要求退出关卡（另有 `exit_level`、`cutscene`），HUD 默认用网页形式。速通 + 直播不改变速通目标 |

容器里的智能体：

- **工具**：Bash、Read、Write、Edit、Glob、Grep 与游戏工具（见下文"游戏工具"）。WebSearch、WebFetch 在托管配置里被拒绝；Claude Code 以受限模式启动，不读取任何用户、项目或本地设置文件，文件工具只能访问 `/workspace` 与 `/kb`。
- **网络**：容器出站只放行所用模型平台的域名（默认 Anthropic 官方域名；`--provider deepseek` 时只放行 api.deepseek.com，不放行 Anthropic）与宿主机上的游戏工具端口；Bash 命令（智能体自写的程序）在零网络的沙箱里运行，连模型平台也连不上。验收方法见 2.4 节。
- **没有后台任务**：容器里的 Claude Code 以 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 启动，Bash 命令只在前台运行，默认最多 5 分钟（可以用 timeout 参数加到 10 分钟），超时就结束、不会转入后台。
- **工作区** `/workspace`：对应宿主机的 `workspaces\<标签>\`，跨房间、跨章节、跨运行保留。每次观测与动作后，主控把完整观测（`game/latest_obs.json`）、上一次动作的全精度逐帧轨迹（`game/last_act.json`）与每个房间的首次观测（`game/rooms/`）写进来，供智能体的程序读取。
- **知识库** `/kb`：只读挂载仓库的 `kb/`，记录物理常量、状态机、实体规则、全部技巧与机制库、工作区数据格式，以及 `reference/` 里的社区资料原文（见 2.5 节）。技巧与机制的专有名词一律用英文（wallbounce、cornerboost、coyote time、liftboost 等），不用中文译名；基本动作（冲刺、跳、抓墙、体力）与实体名照常用中文。系统提示词也这样写，并要求智能体的思考语句同样只把这类专有名词写成英文。维护知识库时可以用 `python tools\english_terms.py kb\*.md orchestrator\prompts\*.md`（加 `--check` 只检查）按其中的对照表统一替换；不要用它处理 `kb\reference\` 的原文。
- **计划文件**：智能体可以把程序算出的按键序列写成 JSON 文件，调用 `act` 时传 `plan_file`，不必把按键抄进参数。
- 主控在每轮开始时核对智能体拿到的工具列表，出现上面以外的工具会立即停止。

`--runtime host` 时（早期的过渡方式）：Claude Code 直接在本机运行，以 `--tools ""` 关闭全部内置工具，只能调用游戏工具；使用独立配置目录 `agent-home/<标签>/`，并关闭 CLAUDE.md 与自动记忆。

准备阶段（读知识库）：

- 第一条消息按顺序列出要读的文件：`kb/` 下的全部文件（开模拟器时加上 `/sim/README.md`），加上 `reference/` 里导入的社区资料文字版、wiki 页面与草莓酱英文原文（中文版是同一内容的翻译，不要求读）。文件数取决于本机生成了哪些参考资料：实测（2026-10-22，尚未导入 PDF 资料）共 27 个文件。
- 主控从 Claude Code 输出流里 Read 工具的结构化结果（起始行、行数、总行数）逐行核对读过哪些行，不依赖模型自己汇报。长文件被 Read 按长度截断时，截断之后的行不算读过。
- 读完之前，`observe` 与 `act` 不执行，只返回"还有哪些文件的哪几行没读"；智能体一轮结束时还没读完，主控就把这份清单发给它。
- 准备阶段不计入现实用时；第一次成功执行游戏工具时开始计现实用时。超过 `--study-minutes` 时自动开始计时并开放游戏工具。`metrics.json` 的 `study_s`（HUD 的"知识库读取"）只记读知识库的用时（开局到读完）；之后的准备（写笔记、写程序、在模拟器里规划第一个房间）照常计入思考与工具时间，HUD 状态栏也照常显示思考中、运行工具。早先整个准备阶段都记在"知识库读取"里，智能体在准备阶段就规划第一个房间时，HUD 看不出它在做什么。
- 结束后 `summary.json` 的 `kb_study` 记录每个文件读了多少行。
- Opus 5.5 与 Fable 5.1 在 Claude Code 里的上下文窗口都是 100 万 token（在容器里用 `/context` 实测）。实测（2026-10-22）：27 个文件约 24 万 token，读完后还有约 72 万 token 才会触发自动压缩；导入 2.5 节的两份 PDF 资料后，整份知识库约 34 万 token。

实测（2026-10-22，Haiku 5.5，准备阶段）：27 个文件全部读完，用时 35 秒（并行读取），上下文约 24.4 万 token；读完后智能体写好 `notes.md` 再调用 `observe`，主控在这时开始计时，时间预算按预期生效。

规划（默认不限制）：

- 默认不限制思考与模拟器调用：想多久、调用多少次模拟器、每次推演多少条都由智能体决定，计划文件的自动重试照常生效。观测里不显示现实用时与时间预算（`--max-minutes` 只是主控的安全上限）。开模拟器版本的提示词（`orchestrator/prompts/system_sim_zh.md` 的"做法"与"建议的工作方式"、`free_zh.md`）要求整个房间在模拟器里推演到出口、优化完再一次执行，没推演到出口的路线不执行（只有超过单次 `act` 600 帧的上限才分几次执行），需要分段搜索时用模拟器的检查点（4.5 节）；每个房间尽量一次通过：推演出能通关的路线之后以它为基准继续优化，哪怕是帧级的优化也加分（换起跳点、冲刺方向与时机，压缩每段帧数，试别的走法与技巧）；评价指标只有章节计时；搜索要以用时评分，只看"能不能到"的搜索往往给出能过但很慢的路线。
- 为什么默认不限制：早先按房间限制规划轮次（见下文）。实测（2026-10-23，DeepSeek V4.1 Flash，每屏 3 轮）：好几轮花在程序出错和搜索失败上，轮次用完只能执行手里能过但很慢的路线（例如整段普通爬墙）。
- 为什么不显示预算、要求"推演到出口再执行"：不限制轮次之后，实测（2026-10-24，DeepSeek V4.1 Flash，test 存档，30 分钟短测）它仍然"推一点走一点"、路线乱也照走。读它的思维链，原因有四：它一直看观测头部的"现实用时 / 预算"（"Time check… Let me move faster now"、"partial progress is better than none"），在序章第一个房间找到 266 帧的路线、自己列出可改进的地方后，因为赶时间直接执行；提示词前部"一段动作一次执行""用 land 停下检查""再规划下一段"是为没有模拟器的玩法写的，与"每个房间尽量一次通过"矛盾；它在 1A 临时写的搜索是从固定动作片段里随机拼接、按"走多远"打分、不做局部优化，到不了出口就先执行走得最远的那条，再从新位置重抽；模拟器不能存中间状态，在游戏里走一段成了它拿新起点的办法。于是观测去掉了预算，开模拟器版本的提示词改成现在的写法，模拟器加上了检查点。

规划轮次（`--limit-planning` 打开）：

- 游戏只在 `act` 执行时推进，`act` 返回之后游戏冻结、章节计时停住，想多久由智能体决定。限制的是"规划轮次"，按房间大小给：本章每进入一个没来过的房间，按 ceil(3 × (宽/320) × (高/180)) 存入轮次、至少 3 轮——一屏大小（1A 第一个房间）3 轮，长、高每加倍轮次翻倍，比一屏小的房间也给 3 轮（`--rounds-per-room`、`--room-scale`）。序章的四个房间（448×180、464×200、320×180、992×180）依次是 5、5、3、10 轮，1A 的房间多数 3 轮、高一些的 4～5 轮，两倍长两倍高的房间 12 轮（早先的基数是一屏 5 轮，序章四个房间 7、9、5、16 轮）。在游戏里死亡一次补 1 轮（`RunConfig.death_bonus`），没用完的留给后面的房间，换章节清零。任何时候（任何位置、任何一帧停下时）都可以调用模拟器，只要还有剩余轮次。剩余轮数写在每次观测的头部（HUD 不显示）。
- 只有调用模拟器才占轮次（`--sim` 时）：一条消息的工具全部返回后，这期间 `/sim` 写出了推演记录（或命令里直接调用了 `celeste-sim`），这条消息就扣一轮，同一条消息里并行的几次调用算一轮。Read、Write、Edit、Glob、Grep、`observe` 和不调用模拟器的 Bash（看数据、改程序、分析地图）都不占轮次。模拟器只能通过 Bash 调用，所以轮次用完后 Bash 被拒绝，其他工具照常可用。没有 `--sim` 时退回旧规则：`act`、`set_effort` 以外的工具每条消息占一轮，用完全部拒绝。
- 提示词（`pause_zh.md`）要求智能体每个房间只过一次：用这几轮在模拟器里探索、比较、选出最快的路线，然后一次执行通过；简单的房间省着用，把轮次留给难的房间。建议直接用预置模拟器（只有它的推演会画进规划回放）；搜索算法由智能体自己决定，提示词鼓励它针对具体房间的结构设计剪枝条件与引导条件。提示词强调章节计时是唯一的评价指标、用时越短评分越高；不写"避免死亡"一类的话。思考语句只写对房间或这一轮的分析与判断，不写具体数值与算法名。
- 为什么按房间给轮次：每次暂停只给一轮工具时，智能体只敢走一小段保险的慢路线；完全不限制时，它在一次暂停里反复搜索，观众看不到试错过程。按房间给轮次，智能体有余地在模拟器里找快路线，探索过程再用"规划回放"画进游戏给观众看。实测（2026-10-23，Fable 5.1 的正式运行，当时不限轮次）：各房间用的轮次中位数是 4，最难的房间 14～25 轮。
- 剩余轮次怎么告诉智能体：每次观测的头部有一行；每次调用模拟器的那条 Bash 结束时，`/sim/sim.py` 在标准错误末尾提示一行"（系统）这条消息调用了模拟器，占一轮规划轮次；本章剩余 N 轮"；工作区的 `game/rounds.json` 由主控实时更新（`left` 剩余、`used` 已用等），智能体随时可读，读文件不占轮次。
- 实现：容器的托管配置登记了 PreToolUse 钩子（`agent-container/celeste-gate.py`），Claude Code 调用任何工具之前都先问主控的 `/gate`（`orchestrator/pausegate.py`）；扣轮次由 `orchestrator/playback.py` 在一条消息的工具全部返回时根据推演记录做。拒绝次数记在 `metrics.json` 的 `pause_denials`，用掉的轮次记在 `plan_rounds_used`，主控输出里有 `[gate] 用掉一轮模拟器规划 …` 与 `[gate] 拒绝 …`。
- 准备阶段（游戏工具第一次真正执行之前：读知识库、写程序、自测）不受限制；第一次执行游戏工具时开始记账。续跑（`--resume`）没有准备阶段。
- 计划文件的自动重试同时关闭（`retry` 被忽略，结果里会说明），因为它会在不消耗轮次的情况下自动跑多次重算。
- 注意：只数模拟器调用，智能体用自己写的模拟器搜索就不占轮次。提示词要求搜索用 `/sim`（回放也只画 `/sim` 的推演），目前没有别的强制手段。
- 更早的做法是"每次暂停只允许一轮工具"。实测（2026-10-23，Haiku 5.5，test 存档序章）：房间 1 起跳太早掉进坑里、会塌的木桥上又掉下去三次，最后通关（章节计时 1:05.365，19 次决策，死亡 4 次）；DeepSeek 每次只敢走一小段。按房间给轮次之后，试错改在模拟器里进行，由规划回放展示。

规划回放（默认开启；`--no-playback` 关闭）：

- 智能体每规划完一轮（这条消息的工具全部返回），主控就把这一轮在预置模拟器里推演过的路线画进游戏画面，给观众看试错的过程；智能体同时在想下一轮，下一轮先结束时排队依次放，录像里一轮接一轮。回放时游戏完全不推进，不计章节计时，也不占轮次；录像里照常录下，`frames.csv` 里这些帧的章节计时记为 -1，`recording.json` 的 `replay_frames` 是回放帧数。
- 数据从哪来：工作区存在 `game/simlog/` 时，`/sim/sim.py` 的 `Sim`、`SimPool` 把每一次推演记成一条二进制记录（每帧位置、结果、按键哈希等，格式见 `orchestrator/playback.py`）。一轮结束后主控把记录文件移出工作区（运行目录的 `playback/pending/`），回放线程只把表头读进内存，挑好要画的路线，画完删掉。准备阶段（第一次执行游戏工具之前）的推演同样回放：智能体常在准备阶段就开始规划第一个房间，不画的话序章第一个房间看不到绘制过程。只用自己写的模拟器做搜索时没有记录，提示词因此要求智能体用 `/sim` 搜索，并把每轮运行搜索的 Bash 的 `description` 写成一句给观众看的中文（只写分析与判断，不写数值和算法名），回放时显示在 HUD 上。
- 画几条：每 100 条推演画一条（`RunConfig.playback_ratio`），每轮至少 40 条（`playback_min_tracks`；推演更少时全画），不设上限。挑法：金色的一条（这一轮往前走的出口里最快的，快慢比的是推演终点的帧号——从检查点出发的推演帧数少，不能只比帧数；离起点不到 40 像素的出口多半是掉头回上一个房间，不算；这一轮没有往前走的出口就没有金色路线）；各个出口位置最快的一条；死亡按地点归并、离目标近的优先，最多占三分之一；剩下的名额按路线形状做最远点采样，挑和已选的最不像的。按推演先后出场，看起来像搜索一步步往前推进。
- 怎么画：基础节奏是 3 倍速（`playback_speed`），每条路线每帧一个点（画之前合并误差不到 0.3 像素的共线点）。一轮里的路线在 0.8 秒内（`playback_stagger_s`）按推演先后陆续从 Madeline 身上长出来，延伸中普通路线为较亮的绿色，最佳路线为亮薄荷色；一条线走到头的那一帧定下结果：死亡的从死亡点往起点一路变成淡红（终点画一个叉），这一轮最快的一条从终点往起点一路变成实心金色，变色以 8 倍速传导（`playback_recolor`）；其余的保持绿色。普通路线宽 1.5 像素、基础不透明度 65%，最佳路线宽 2 像素并加深色描边；线多时普通路线整体调淡。只画线和前端标记，不画角色。桥接 1.0.12 起按实际绘制条数动态调节：12 条以内保留完整普通路线，更多路线时旧亮色线段逐步加快褪色，亮度减半时间从约 0.3 秒缩短至最低约 0.03 秒；普通线和标记同时调淡，最佳路线保留完整高亮。轮末默认 8 帧转灰，密集时缩至最低 1 帧；历史线每轮保留比例从 0.2 随密度进一步降低，过淡后清理。缓存层和直接绘制回退采用同一衰减规则。
- 每轮回放最长 1.5 秒（`playback_round_s`，以 1A 第一间这样一屏 320×180 的房间为准，房间面积是它的几倍就乘几倍）；按上面的节奏会超过时，这一轮整体按比例加速（倍速、出场间隔、变色、停留与淡出一起缩短），在上限内画完。每轮回放的概况（推演条数、画了哪些线、渲染用时）记在运行目录的 `playback/playbacks.jsonl`；HUD 在回放时状态显示"规划回放"，下面写第几轮、推演了多少条路线。
- 执行之前：智能体调用 `act` 时，主控先等排队的轮次放完（最后一轮变色传导完成），镜头平滑回到 Madeline（本来就在那里时直接开始），然后真实执行，画面上的线全部清掉。
- 镜头：线条延伸时镜头跟着伸得最远的绿线（此刻所有路线里前端离起点最远的那一点）平滑移动（受房间边界限制）；金色路线走到头、开始往回变金时，镜头跟着变色的那一点往回移，回到起点后停住；这一轮没有金色路线时，所有线画完后镜头沿伸得最远的那条线以同样的速度往回移到起点；两轮之间停在回放镜头上；渲染时临时换上回放镜头、渲染完原样换回，渲染期间随机数也换成单独的发生器，游戏状态一点不变。智能体 `observe` 截图的那一帧不换镜头、不画线，它看到的是游戏本来的画面。
- 刚进章节时圆圈转场还没放完：回放帧先把转场放完，黑屏消失之后才开始画线（进关卡的转场只影响能不能暂停，没有别的作用）。
- 声音：回放帧里实时播放的音乐照常、音效暂停，录像里的音乐和之后真实执行时连在一起；游戏冻结、也没有回放时声音整体暂停（`--continuous-music` 时音乐继续）。录像的声音默认由桥接按帧单独混出（独立游戏音频 `game_nrt`，见 4.4 节）：完整版音轨 `audio.wav` 在每个回放帧里正好混出 1/60 秒音乐（音效暂停），纯享版音轨 `audio_play.wav` 只随真实游玩帧推进，两个版本的音乐都是连贯的（桥接 0.12.7 起）。
- 回放帧跟不上 60 帧时（**只适用于 `obs_mix` 录音**；`game_nrt` 的声音按帧生成、与墙钟无关，插件不补帧——补帧只能重复同一块声音，回放的长度就是画出的帧数）：录制插件只给录下的帧配 1/60 秒的声音，回放时音乐又一直在放，所以画一帧超过 1/60 秒时，漏掉的节拍的音乐会被跳过，录像里听起来像加速。实测（2026-10-23，DeepSeek V4.1 Flash 正式运行的头两轮）：每轮两三千条线、再叠上前一轮的灰线，一帧 20～28 毫秒，漏掉 16%～41% 的节拍。`obs_mix` 下插件把回放时漏掉的节拍用下一帧补上（重复帧，`frames.csv` 里章节计时记 -2，`recording.json` 的 `replay_filled` 是补帧数），声音一段不丢、音乐保持原速；画面在慢的地方会略显卡顿。游玩帧不补，成片里的游玩帧数仍然等于游戏推进的帧数。
- 画得快：桥接 0.11.1 起把不再变化的线画进三张房间大小的缓存层（世界坐标的渲染目标）：前几轮的淡灰线、本轮其他与出口路线走过的每一段（一段只画一次）、死亡路线变完红后的整条，以及开始转灰时整轮的淡灰线（转灰期间两层交叉淡化，放完直接合进历史层）。每帧只重画还在延伸的那一小段、还没变完色的死亡路线和金色路线；每段线的方向与长度预先算好。房间超过 4096 像素时退回逐条重画。每轮回放的回复里带渲染用时（`render_avg_ms`、`render_max_ms`，记在 `playback/playbacks.jsonl`），平均超过 14 毫秒时主控输出里提示"渲染偏慢"。实测（2026-10-23，离线压测，test 存档序章，回放比例临时调成 5:1，三轮各 2400、3000、3200 条线，叠着前几轮的灰线）：整帧渲染平均 1.07～1.52 毫秒、最慢 15～22 毫秒；930 个回放帧补了 3 帧（开始转灰时画整轮灰线、或收到下一轮几兆字节的数据那一帧）；按"相邻两帧声音接缝处的跳变"统计，回放帧接缝的跳变比例从改前正式运行的 14%（121/863）降到 1%（8/863），与游玩帧相当；回放前后状态不变、两轮之间观测截图与回放前逐字节相同、执行与推演逐帧一致。
- 关模拟器的版本：主控同样建好 `game/simlog/`，并在每次运行开始时把展示接口 `game/show.py` 写进工作区（源文件 `orchestrator/workspace_files/show.py`，只用标准库）。智能体不管用什么办法（自己写的模拟器、手算、别的程序）算出 Madeline 的逐帧轨迹，都可以调用 `show.trajectory(points, result)` 交给系统：`points` 是每帧推进之后的位置，`result` 是 `exit`、`death` 或 `open`。记录格式与 `/sim` 相同，主控按同样的规则一轮一轮画进游戏，画法、颜色、镜头都一样，不加标注，也不区分准不准（智能体的模拟器不准时照它给的轨迹画）；只用于展示，不影响成绩，算不算由智能体决定。提示词里写明："不管用什么方法，如果需要计算 Madeline 逐帧轨迹，就在算出后输出到这个接口，系统会画给观众看，只用于展示，不影响成绩。计算与否由你自主决定。"轨迹的起点帧不写时取游戏当前停下的那一帧（`game/latest_obs.json`），金色路线按终点帧号比较，与开模拟器时相同。实测（2026-10-24，离线，用假工作区写入几百条轨迹）：回放模块读出的条数、结局与起止点与写入的一致。
- 实测（2026-10-23，离线，不用模型：真模拟器几轮进化搜索 → 回放线程逐轮画进游戏 → OBS 锁步录制）：回放前后帧号、位置、镜头完全不变；两轮之间 `observe` 的截图与回放前逐字节相同；之后按最终按键执行，每帧位置与模拟器推演一模一样；录像 1093 帧中回放 880 帧，无缺帧。
- 实测（2026-10-23，DeepSeek V4.1 Flash，test 存档序章，`--no-study --sim --record`，预算 20 分钟，当时按房间限制轮次）：通关，章节计时 0:52.360，死亡 2 次，决策 11 次；模拟器调用 14 次（每次一轮）、推演约 10.7 万条，每次调用模拟器后都在输出末尾看到剩余轮次；录像 7778 帧（129.6 秒），其中规划回放 4291 帧，无缺帧，回放时音乐不断。

非可控段由主控处理，节奏与原版游戏一致：

- 房间转场、死亡动画与重生：按原速播放（转场约 39 帧，死亡到重生约 103 帧）。
- 能跳过的剧情（默认 `--cutscene-mode auto`）：像玩家一样按暂停键，停留约 0.3 秒后在菜单里下移到"跳过剧情"，再停留约 0.17 秒后确认；序章开场同样在它的暂停菜单里选"跳过"。录像里会出现暂停菜单与跳过时的转场。
- 不能跳过的剧情：按原速播放，对话框等待翻页时按确认键。
- `--cutscene-mode agent` 时剧情交给智能体：可尝试跳过时先交回，它用 `cutscene` 的 skip 尝试跳过或 watch 继续观看到真实输入节点，再推进对话或明确选择分支。
- 智能体只能按游玩按键（方向、跳、冲刺、抓、交互），暂停、确认、返回等菜单键只由主控使用。

分层执行（M4）：

- **计划文件**：除了按键段数组，还可以写成对象 `{"inputs", "expect", "tolerance", "stop_on", "retry"}`，格式见 `kb/game_data.md` §3。
- **预期轨迹与偏离停止**：`expect` 是智能体的模拟器预测的逐帧位置（可附状态名）。桥接每帧推进后立即对照，x 或 y 偏差超过 `tolerance` 像素（或状态不符）就在这一帧停下，停止原因 `deviate`，返回第几帧、预期与实际。
- **自动重试**（默认生效；`--limit-planning` 时 `retry` 被忽略）：`retry` 声明一个重算命令。遇到死亡（先推进到重生）、偏离预期、或按键用完仍在本房间时，主控在容器的零网络沙箱里运行它；它读 `game/retry.json` 与最新观测、从当前状态重算并改写同一个计划文件，主控接着执行，最多 5 次（可调参数 `retry_max`），期间不唤醒智能体。命令出错、超时（最长 60 秒，可调参数 `retry_timeout_max_s`）、没改动计划或新计划不合法时停止，把经过与错误输出返回给智能体。重算用时计入工具时间，次数记在 `metrics.json` 的 `retries`。

### 4.2 HUD：右上角信息卡片

HUD 显示智能体名称与状态、当前房间、本局的关卡内游戏时长（主计时）、推理强度、思考与工具总时间、对话上下文、压缩次数、知识库读取用时、死亡次数、模拟器调用次数、推演的路线条数、当前房间推演出的最速出房用时、正在调用的工具，以及智能体最近的思考语句。现实用时不显示（时间预算照常生效）。规划回放时状态显示"规划回放"，下方写第几轮、推演了多少条路线。

HUD 有两种形式，用 `--hud-mod` / `--no-hud-mod` 选择：

| 形式 | 默认 | 显示在哪 | 特点 |
| --- | --- | --- | --- |
| 游戏内 HUD（MOD 形式） | 不开直播时 | 桥接 Mod 画在游戏画面右上角，录像里随游戏画面一起录下 | 旧版卡片版式（见下表）加思考语句历史；主计时在关卡里按当帧游戏时间走，逐帧准确；智能体的观测截图里没有它 |
| 网页 HUD | 直播模式，或 `--no-hud-mod` | 屏幕上的独立窗口，以及 OBS 浏览器源 | 可交互：卡片之外还有会话、试玩与目标等控制（只在窗口里显示，OBS 里隐藏）；思考一栏是可滚动的公开解说历史 |

两种形式读同一份数据：主控实时写的 `metrics.json`，以及公开解说历史（`public_events.jsonl`）与每次决策的思考语句（`decisions.jsonl`）。

- **服务**：主控运行时会在进程内启动 HUD 服务：`http://127.0.0.1:47790/hud`（`--hud-port` 改端口，`--no-hud` 关闭）。也可以单独启动：`.\.venv\Scripts\python.exe -m overlay.server`。它总是显示最近一次运行（`runs\latest.txt`），换一局不用刷新页面；`--run <运行目录>` 可以固定显示某一局。
- **游戏内 HUD**：主控里的 `overlay/modhud.py` 每 0.1 秒看一次 `metrics.json` 与公开解说历史，内容变了就用 Pillow（Noto Sans SC 可变字体，没有时用微软雅黑；数字用 Bahnschrift；全部粗体）画一张卡片图，经共享内存 `Local\CelesteAIHud-47774` 交给桥接，桥接（`ModHud.cs`）每帧画完游戏后把它贴在游戏显示区右上角。版式是旧版网页 HUD 的（名字与状态、章节与房间、大号主计时、推理强度、统计两列、调用工具），思考语句一栏保留最近几条历史（每条一个气泡，标着本机时间与"解说 / 尝试"，最新一条在最下面高亮，放不下时最早的从上边渐隐裁掉），规划回放时下面一行写第几轮、推演了多少条。主计时不在图里：主控给出本局已核实的关卡内时长，桥接在关卡里随当帧的章节计时逐帧走、用主控给的数字字形拼出来，录像里逐帧准确。卡片全透明：不画底色、边框与投影（`configs\hud.json` 的 `mod_card` 不透明度为 0；调成不透明时照旧画卡片），所有文字与计时数字加深色描边（`mod_stroke`），小字一律用最粗的字重；统计值按栏名上色（思考金、工具紫、上下文青、压缩青绿、知识库读取蓝、死亡红、推演各项绿，颜色是 `stat_*` 几项），状态文字与圆点同色，思考语句每条左边一条色条（最新一条为金色）。开了 `--formal-thought`（仅正式思考）时思考语句一栏只显示当前这一句正式思考，字号更大。卡片在游戏显示区右侧，上边在显示区高度的 10% 处（`configs\hud.json` 的 `mod_top`；设为 null 时贴着上边），内容变多时往下长；思考语句每条有一个 85% 透明的深色气泡（`mod_bubble`）。卡片宽度按游戏显示区宽度的 18.2%（1080p 下 350 像素）画，显示区变大时主控按新尺寸重画。HUD 画在后备缓冲上，智能体的观测截图（游戏自己的画面缓冲）里没有它。锁步录制时游戏停住的节拍本来不重画，HUD 有新内容时隔 0.1 秒以上重画一次，这些重画没有时钟令牌，不进录像。开着时不打开网页 HUD 的窗口，OBS 浏览器源里的网页 HUD 也隐藏（录像里只有游戏画面里的一份）。主控退出 5 秒后 HUD 消失。需要桥接 0.13.0；桥接太旧时主控提示并改用网页 HUD。
- **网页 HUD 的窗口**：主控运行时自动打开（游戏内 HUD 开着或 `--no-hud-window` 时不打开；已经开着就沿用），结束时关闭；也可以单独打开：`.\.venv\Scripts\python.exe -m overlay.window`（需要 `pip install -r requirements.txt` 装上 pywebview，使用系统自带的 WebView2）。窗口无边框、背景透明，可以拖动、缩放，位置与大小会记住；最小化或关闭都隐藏到托盘（双击托盘图标恢复，托盘菜单"退出 HUD"彻底退出），可以切换是否置顶。它是独立窗口，不跟随游戏窗口移动。这个窗口不会进录像（录像里的网页 HUD 来自 OBS 浏览器源）。
- **OBS**：`tools\obs_setup.py` 建的场景里已经有 HUD 浏览器源（见 4.4 节），默认用网址 `http://127.0.0.1:47790/hud?surface=obs` 打开（`surface=obs` 时隐藏控制区）。OBS 33 的本地文件源不能跨源访问本机服务，所以默认不用本地文件方式；`obs_setup.py launch`（主控启动 OBS 时也一样）会先确认 HUD 服务在运行，没有就启动一个。默认大小 420×760、位置 (1480, 40)（1080p，见 `configs\recording.json` 的 `hud`），你在 OBS 里调整过的位置与大小会保留。游戏内 HUD 开着时，这个页面在 OBS 里自动隐藏。自己加时：添加"浏览器"来源，URL 填上面的网址（OBS 打开页面时 HUD 服务要已在运行），页面背景透明，不用额外设置。
- **实时性**：执行中桥接每 6 帧（0.1 秒）推送一次章节计时、冲刺次数与房间。网页 HUD 每 0.1 秒取一次数据，在关卡里执行时两次之间按实时外推（菜单里不外推），所以主计时逐帧走动、左侧色条随冲刺状态变色；游戏内 HUD 的主计时由桥接在关卡里按当帧的游戏时间走。思考期间思考时间持续走动。新的思考语句一出现就替换：主控在每段动作推进之前先把新语句写出、等 0.4 秒（`RunConfig.thought_lead_s`，游戏冻结着，录像里不占时间）让 HUD 换好，所以录像里新语句与这段动作的第一帧同时出现。早先的做法是每 3 秒检查一次，常常动作做完、进了下一个房间才换上。
- **思考与工具状态**（所有模式都有）：提示词里的 HUD 一节（速通模式 `orchestrator/prompts/hud_zh.md`，探索模式写在 `explore_zh.md` 里）要求智能体思考期间想法每有进展就调用 `narrate` 写一句给观众看的话（不攒到 `act` 时才写），运行耗时较长的程序时在程序里定期调用工作区 `game/show.py` 的 `status("……")` 报告进度。`narrate` 写下的语句立即替换 HUD 的思考；`status()` 把进度原子地写进 `game/hud_status.json`（同一个程序每 0.2 秒最多写一次），主控每 0.2 秒检查一次这个文件（`orchestrator/live.py`），有工具在运行时显示在"调用工具"一行的工具名后面（"Bash — 第 3 轮，已试 2 万条"），这次工具调用全部返回后清掉。规划回放期间思考语句的位置照常显示最新的思考，"第几轮、推演了多少条路线"在状态下面的一行。
- **解说计时**：主控按 HUD 同一口径累计"思考状态"的时间（工具运行与游戏推进不算），自上次 `narrate` 起每满半分钟（直播模式 10 秒，`RunConfig.live_remind_s`）记一次该提醒，在智能体下一次调用任何工具（Bash、Read、`act` 等）时，由容器里的 PreToolUse 钩子（`agent-container/celeste-gate.py`，经主控的 `/gate`）把一句提醒作为 `additionalContext` 放到那次工具结果旁边；调用 `narrate` 就从头计时。模型一段连续的思考（中间不调用工具）没有插入点，提醒只能等到它下一次调用工具时送到；硬打断会丢掉这段思考，所以不这么做。主控输出里有 `[live] 提醒更新 HUD 思考`，`metrics.json` 的 `narrates`、`narrate_reminders` 记录调用与提醒次数。改了钩子要重新构建镜像。
- **按一局统计**（开不开计划外地图都一样）：思考、工具、死亡、决策、模拟器调用等从这一局开始时起算，换图、换章、进出计划外地图、重新进入计划章节、换到计划的下一截都不清零（知识库读取、上下文与压缩次数本来就不清零）。中断后续跑（`--resume`）接着同一局，基准与关卡内时长存在 `metrics.json` 的 `chapter_base` 与 `game_clock`；续跑追加新计划（`--resume <已完成的运行> --chapters N` 或 `--segments`）开始新的一局，从 0 重新算。主计时是本局在关卡里真正执行的帧数（60 帧一秒）：计划与计划外地图都算，关卡里的剧情、冻结、死亡动画与暂停菜单也算；主地图、选章、选档等菜单、加载与结算画面以及规划回放不算。帧数按每次推进的结果核实（有逐帧轨迹时按 Madeline 在关卡里的帧加死亡动画的帧算，少数没有 Madeline 的关卡剧情帧可能不计），游戏重启后接着累计；执行中按进度推送估算显示。分段成绩（`splits`）与总计时（`total_time_ticks`）仍按游戏内章节计时，口径不变。
- **配置**：配色、名称与参数在 `configs\hud.json`；本机想改的项写进 `configs\local.hud.json`（不入库），会覆盖同名项。

游戏内 HUD 的版式（网页 HUD 的卡片大体相同，差别见表中说明）：

| 区域 | 内容 |
| --- | --- |
| 页眉 | 智能体名称（按 `configs\hud.json` 的 `names` 映射，如 Opus 5.5、DeepSeek V4.1 Flash）、状态（等待、读知识库、思考中、运行工具、执行中、自动推进、自动重试、规划回放、压缩上下文、等待额度重置、网络中断等待恢复、已完成）、章节与房间（如 1A 6c） |
| 主计时 | 本局在关卡里执行的游戏时长，精确到毫秒（毫秒位小一号）；换图、换章不清零，菜单、结算画面与规划回放不算（见上面“按一局统计”） |
| 推理强度 | 主计时右侧：五格刻度与英文档位名（low、medium、high、xhigh、max；`configs\hud.json` 里加 `effort_names` 可改）；xhigh 与 max 用琥珀色；智能体申请了切换、还没生效时后面跟一个"→ 目标档位" |
| 统计 | 两列九项：思考、上下文（达到自动压缩阈值的 90% 变橙）、工具、压缩次数、知识库读取（开局到知识库读完的用时，读完就不再走；跳过准备阶段即 `--no-study` 时显示"—"）、死亡（"N 次"）、模拟器调用（调用了模拟器的消息数，"N 次"）、推演路径（当前这次模拟器调用推演的路线条数，"N 条"，上万时以"万"为单位，这一轮回放画完清零；网页 HUD 这一项是"累计推演"）、推演最速（当前房间里推演出的最快出房用时，从进入房间的那一帧算到推演的终点帧，所以从检查点或房间中途出发的推演也按整个房间的用时比较；只算往前走的出口，换房间清零）；探索模式开了限额预测时另有"推演额度"（余额 / 上限）；探索模式关掉限额预测时，模拟器调用、推演路径、推演最速与推演额度都不显示。最后一行占满整行的"调用工具"（放不下时折行，最多三行）：智能体正在调用的工具与说明（Bash 用它写的 description，Read、Write、Edit 用文件路径，Glob、Grep 用模式，游戏工具只写 act、observe 或 set_effort；同一条消息里并行的几个调用写成"Bash ×2"），没有在调用工具时显示"—"。一轮里有工具在运行时（输出流里出现 tool_use、还没收到结果）算工具时间，包括容器里的 Bash、Read、Write 等和游戏工具；没有工具在运行时算思考时间（模型推理、输出、压缩上下文）；游戏真正推进的时间两边都不算，单独记为游戏推进时间 |
| 思考 | 最近几条思考语句（`narrate` 与每次 `act` 的 `thought`），一条一个气泡，最新一条在最下面高亮；网页 HUD 是可滚动的公开解说历史 |
| 左侧色条 | Madeline 的发色：一次冲刺绯红、冲刺用尽冰蓝、两次冲刺粉色 |

M5 验收（2026-10-23，桥接 0.7.0，当时的网页 HUD）：`python calibration\m5_hud_demo.py` 不调用模型，按"思考 3 秒 → 执行"的节奏驱动游戏三轮，全部通过。执行中每轮收到 8～11 次进度推送，章节计时随之前进；连拍置顶窗口：思考时主计时静止、思考时间走动，执行时主计时逐帧前进，向上冲刺时色条变成冰蓝、落地恢复绯红，思考语句按 3 秒间隔淡入。窗口启动前后前台窗口不变（不抢焦点）。

### 4.3 重放一次运行（不调用模型）

按某次运行记录下的决策逐条重放，用来复现问题或检查主控、桥接的改动是否影响游戏结果：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.replay runs\<标签>\<时间戳> --save test --chapter 0
```

每条决策会打印停止原因与实际帧数，并与原记录比对（"一致"或"不同"）。重放的日志写在 `runs\replay\<时间戳>\`。实测（2026-10-22）：重放 Opus 5.5 的一次序章记录，21 次决策逐帧一致，两段剧情都通过暂停菜单跳过。

### 4.4 录制：OBS 只录游玩帧

新运行默认 `--recording-mode chapter`，每章一个视频：不录选章，保留章节开场、游玩和完整结算。补收集等跨章连续录制可设 `--recording-mode continuous`；旧运行续跑沿用连续方式。菜单冻结、分章清单和恢复说明见 [分章录制](CHAPTER_RECORDING.md)。

录制时 OBS 的每个视频帧都向游戏要一帧：游戏推进一帧、画到屏幕上，OBS 采下这一帧；智能体思考、游戏停住时 OBS 一帧也不写。成片的帧数等于游玩帧数（加上规划回放帧，见 4.1 节），声音也只取这些帧对应的那 1/60 秒，思考时间在成片里完全不存在。HUD 随游戏画面（游戏内 HUD）或作为场景里的浏览器源（网页 HUD）一起录进去。

**一次性准备**

1. 安装 OBS（28 或更新，实测 32.2.2；Steam 版即可）与 ffmpeg（`winget install Gyan.FFmpeg`）。
2. 构建并安装锁步插件（先关闭 OBS；不需要 Visual Studio，脚本会用 pip 装 zig 交叉编译）：

   ```powershell
   .\.venv\Scripts\python.exe tools\build_obs_plugin.py
   ```

   OBS 目录自动查找（`configs\local.recording.json` 的 `obs_dir`、Program Files、各个 Steam 库），找不到时用 `--obs-dir "<OBS 安装目录>"` 指定。OBS 更新后要重新构建，并重跑下面的校准测试。
3. 本机设置写进 `configs\local.recording.json`（不入库，只写要改的键；默认值见 `configs\recording.json`）：

   ```json
   {
     "obs_dir": "<OBS 安装目录，反斜杠写两个>",
     "ffmpeg": "C:\\Users\\<你>\\AppData\\Local\\Microsoft\\WinGet\\Links\\ffmpeg.exe",
     "video_args": "-c:v h264_nvenc -preset p5 -tune hq -rc constqp -qp 16 -g 120",
     "audio_offset_ms": 130
   }
   ```

   `video_args` 是 ffmpeg 的视频编码参数：有 NVIDIA 显卡用上面的 NVENC，否则保留默认的 libx264。`audio_source` 是录像声音的来源：默认 `game_nrt`（独立游戏音频：桥接另开 FMOD 系统按帧混出声音，不经过声卡与 OBS 混音），`obs_mix` 是旧路线（OBS 的应用音频捕获，按段校准延迟）。`audio_offset_ms` 只用于 `obs_mix`：某段量不到声音延迟时作为后备（见下），`--continuous-music` 时作为固定偏移。

**每次录制**

```powershell
# 启动游戏（桥接 0.12.7 以上；游戏内 HUD 需要 0.13.0）后直接运行主控：录屏默认开启
.\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --model opus
# 不录屏
.\.venv\Scripts\python.exe -m orchestrator.run --agent dev-opus --save test --model opus --no-record
```

- **录屏开关**：`--record`（默认）时主控在开局前检查 OBS：没在运行就调用 `tools\obs_setup.py` 的启动流程（自动建好专用的配置文件与场景集合 CelesteAI、记下你原来选中的配置、确认 HUD 服务在运行、最小化到托盘、等锁步插件连上桥接），最终收尾时（成片与纯享版写好之后）关掉 OBS；中断且保留接管时不收尾、不关闭 OBS。正常关闭时（最小化到托盘的 OBS 有时不响应正常关闭，30 秒内没退出就强制结束；`obs_setup.py stop --force` 同样），并把 OBS 下次打开时选中的配置还原成你原来的；OBS 已经开着时直接用（要是 CelesteAI 配置），结束时不关。`--no-record` 时不启动、不调用 OBS。手动管理 OBS 的命令照旧可用：`tools\obs_setup.py launch` / `stop` / `status` / `restore`。改了网页 HUD 后，先关掉开着的 OBS，让主控下次重新启动它（OBS 的浏览器源不会自动刷新）。
- `obs_setup.py` 不动你自己的配置文件与场景：CelesteAI 配置文件是 1920×1080、60 fps、NV12、48 kHz；场景里只有游戏采集、应用音频捕获（只录 Celeste.exe）与 HUD 浏览器源，没有桌面音频和麦克风。场景集合已存在时保留你在 OBS 里的调整，只把 HUD 浏览器源的网址与打开方式同步成 `configs\recording.json` 里的值（旧版本建的整画布 HUD 源会迁移成默认的大小与位置；OBS 运行时不改，`stop` 之后再 `launch` 即可）；`setup --reset` 重建（原来的先备份）。`status` 查看插件是否加载、是否连上桥接；`restore` 在手动关闭 OBS 之后还原原来选中的配置。
- **开局也录进去**：主控先把游戏退回选档页（这一步不录、快速完成），从选档页开始录制，再按正常速度选存档、进地图、选章节、进关卡、用暂停菜单跳过开场剧情，所以录像从选档页开始。HUD 在这段时间显示智能体名称、推理强度与"等待"，计时都是 0。`--resume` 有保留录制时直接接续，菜单宏进入过程按正常速度录入同一份录像；原编码器已退出时按[录制恢复](RECORDING_RECOVERY.md)接到原录制会话，同样不另开录像。`--resume` 加 `--chapters`（或 `--segments`）追加章节、且上一章的录像已经正常收尾（`finished`）时另起新录像：停在目标关卡里则接管后开始，否则从选档页开始，上一章的录像目录与成片保持不变。从未录制过的运行续跑时同样新开录像。`--skip-enter` 时接管后开始录制。
- 正常结束或点击停止时收尾录像，再交还游戏控制；中断且保留接管时保留 OBS 编码器与独立音频，续跑继续写同一份录像，不重置帧号。编码器已退出时，普通续跑会核验旧文件并恢复到同一录制会话，新增片段在收尾时合并回原目录（追加章节且上一章录像已正常收尾时例外，见上一条）；其余情况只有明确 `--new-recording` 才另开录像，失败重试及边界见 [录制恢复](RECORDING_RECOVERY.md)。中断摘要中的 `recording.state` 为 `retained`；具体冻结规则见 4.8 节。
- **录像中途失败时恢复同一录制会话**：录制中每次推进游戏前，主控顺带查一次录像状态：OBS 插件报失败、桥接的独立录像音频出错或锁步停止时，先收尾这次采集，再按[录制恢复](RECORDING_RECOVERY.md)把新采集写进同一录制会话（收尾时合并回原 `recording\`），控制台对话栏记一条系统消息。出错那次推进里、出错之后的画面录不上，也不会补造；之后不再推进录不上的帧。OBS 断开或已重启时不发停止、不等收尾，立即暂停试玩（游戏保持冻结，这次按键不执行）并提示：OBS 重新连上且原采集仍在时可以直接继续，否则中断主控后正常 `--resume`，以原会话恢复。恢复也失败时同样暂停，按提示处理后重试；只在确定放弃原录像时才加 `--new-recording`。桥接 1.0.28 起，独立音频里单个音效的句柄失效（`ERR_INVALID_HANDLE`）只丢掉这个音效的镜像、照常录下去（桥接日志写明是哪个调用、哪个音效，`audio_diagnostics` 的 `dropped` / `drops` 计数），不再让整段录像失败（10-27 的 5A 曾因一次这样的错误丢了约 12 秒游玩）。
- 游戏窗口不能最小化：最小化后游戏的画面缓冲缩成 8×8 像素，录像里游戏区域是一块深色方块。主控在开始录制前、以及录制中每次推进游戏前检查，发现最小化就把窗口还原（不激活，不抢你当前窗口的焦点）并在输出里提示。窗口被别的窗口挡住不影响录制。
- 录制期间动作块按 60 fps 实时播放（节奏由 OBS 决定），`--play-speed` 不起作用。
- **直播**：`--keep-obs-open` 让主控结束时保留它启动的 OBS（直播继续用），锁步录像照常收尾；手动关闭 OBS 后可以用 `obs_setup.py restore` 还原原来的配置选择。`--continuous-music`（或 `configs\local.recording.json` 里写 `"continuous_music": true`）时游戏冻结期间 BGM 照常实时播放、只暂停音效，适合直播；`--freeze-music` 时音乐也一起暂停。
- 其他参数：`--ffmpeg`、`--record-video-args`、`--audio-offset-ms` 临时覆盖配置；`--record-marker` 在画面左下角画帧号条码（只用于校准）。

**产出**（`runs\<标签>\<时间戳>\recording\`）

| 文件 | 内容 |
| --- | --- |
| gameplay.mp4 | 成片完整版：画面 + 声音（AAC 256 kbps），含规划回放 |
| gameplay_pure.mp4 | 成片纯享版：只有真实游玩的帧（去掉规划回放），录制结束时由主控生成 |
| video.mkv、audio.wav | 只有画面、只有声音（32 位浮点，每帧 800 个样本；`game_nrt` 时是完整版音轨，回放帧里音乐继续、音效暂停） |
| audio_play.wav | 纯享版音轨（只有 `game_nrt` 录音才有）：只随真实游玩帧推进，每个游玩帧 800 个样本，纯享版直接用它 |
| frames.csv | 每个成片帧对应的游戏帧号、章节计时与 OBS 时间戳 |
| segments.csv | 连续推进的各段，以及每段开头量到的声音延迟（`obs_mix`） |
| recording.json | 结果摘要：帧数、缺帧与重复检查、声音对齐情况 |

**纯享版**：录制结束时主控从完整版里去掉规划回放的帧（`frames.csv` 里章节计时为 -1、-2 的行），生成 `gameplay_pure.mp4`：画面按行号（即 `video.mkv` 的帧序号）挑帧、按录制时的编码参数重新编码；声音：有纯享版音轨 `audio_play.wav`（`game_nrt` 录音，桥接 0.12.7 起）时直接用它，它只随真实游玩帧推进，音乐是连贯的；没有时（`obs_mix` 录音、旧录像）按同样的行号从 `audio.wav` 裁剪（每帧 800 个样本），两段游玩之间去掉了回放，音乐不再连续，接缝处淡出、淡入各 5 毫秒去掉爆音（`recording.json` 的 `pure.audio` 记着用的是哪一种）。没有规划回放时复用完整版 MP4（硬链接或复制）；旧 MKV 则无损转封装为 MP4。结果写进 `recording.json` 的 `pure`；失败不影响完整版。已有的录像可以补生成：`python tools\make_pure.py runs\<标签>\<时间戳>\recording`（编码参数默认用那次录制的）。实测（2026-10-24，DeepSeek V4.1 Flash 短测的录像，20919 帧，其中回放 13979 帧）：纯享版 6940 帧（115.7 秒，31 段），NVENC 编码 36 秒生成；截帧检查画面里没有回放的线。

**`obs_mix` 录音的声音对齐**（下面三段只适用于 `audio_source: "obs_mix"`；默认的 `game_nrt` 不经过 OBS 混音，每推进一帧正好混出 800 个样本，没有延迟与接缝的问题）：

- **声音怎么对齐**：OBS 采到的声音比画面晚 110～170 毫秒，而且录制中途 OBS 增加音频缓冲时会突然变化约 70 毫秒，不能用一个固定值。桥接在游戏停住时暂停全部声音（录制时在停住后的第二个空闲节拍暂停、推进前恢复；不录制时停住 60 毫秒后暂停），所以每段动作开头的声音都从完全静音恢复；插件在每段开头找这条边（对齐到这一段第一帧的开头），量出当时的延迟（取最近 5 次的中位数）用于这一段。
- **暂停与继续之间的接缝**：桥接 0.11.3 之前停住 60 毫秒后才暂停声音，这段时间放出的音乐不进录像，每段开头还多一帧静音，接缝处音乐会跳一下（实测：2026-10-23 正式运行的录像里能听出来）。现在暂停在上一帧的 1/60 秒结束后生效、恢复在下一段第一帧生效，音乐内容是接上的；插件在相隔一个节拍以上的两帧之间，前一帧结尾淡出 2 毫秒、后一帧开头淡入 2 毫秒，去掉爆音；每段量到的延迟与最近 5 次的中位数相差不超过 20 毫秒时直接用这一段自己的值，恢复的那一刻正好落在第一帧开头。桥接 0.11.4 起停住后的第二个空闲节拍才暂停：0.11.3 在第一个节拍暂停，暂停正好卡在上一帧的末尾，FMOD 按混音块生效的抖动常把上一帧最后 3～19 毫秒截成静音（实测：2026-10-24 DeepSeek 短测约四分之一的接缝），听起来是细小的断口；现在上一帧的音乐总能完整放出，代价是接缝处音乐向前跳约一帧长度（约 17 毫秒，有淡出淡入，听不出来）。`calibration/m6_recording_test.py` 会检查每段动作最后一帧末尾的静音（应在 3 毫秒以内）。
- **音频块边界的断口（电流声）**：早先的插件在约一半的段里每 1024 个样本留下一个值为 0 的样本（OBS 音频块的边界，取样时向上取整与四舍五入不一致），连续游玩时听起来是持续的电流声，与接缝无关。现在块与块首尾衔接、偶尔漏掉的单个样本用相邻样本补上；更新插件要重新编译安装（先 `python tools\obs_setup.py stop`，再 `python tools\build_obs_plugin.py`）。M6 测试会检查 WAV 里有没有这种断口。

两条录音路线共用 `orchestrator/audio_validation.py` 的断点检测：`obs_mix` 的 M6 校准会调用它，`game_nrt` 的输出也可用同一离线工具检查。默认仅将"左右声道同时精确为零，且同一声道前后信号均高于 1e-6"标为疑似单采样断点，避免把静音中的浮点残留误报。1e-6 是线性振幅（满幅为 1，约 -120 dBFS），与声音恢复校准的 2e-3 阈值分开；较安静的信号可显式降低阈值。结果用于定位候选断点，不等于完整音质鉴定，也不会改写录音。

```powershell
.\.venv\Scripts\python.exe tools\check_recording_audio.py runs\<标签>\<时间戳>\recording\audio.wav
```

离线工具发现疑似断点返回退出码 1，未发现返回 0；文件格式或参数错误返回 2。使用 `--silence-threshold` 调整离线检查阈值，M6 校准的对应参数为 `--dropout-threshold`。检查按块读取，适用于较长录像。`calibration/audio_mixer` 的独立混音器自检可用第二个位置参数导出 float32 立体声 WAV，再交给同一工具检查，整个过程不连接真实游戏或 OBS。

桥接 1.0.8 补齐独立音轨的实例参数、音量、音调、暂停、空间位置与总线/VCA 修改，`release()` 后仍接收控制；原声实例整体清理时回收对应循环，短音效继续播放自己的录制尾音。`recording.json` 的 `audio_diagnostics` 保存各轨创建、释放、峰值和残留数量，以及最老事件的名称、状态、暂停、音调、帧龄与原声句柄状态，桥接日志也保留收尾快照。已录好的旧音轨不能凭此补回漏失的声音。

1.0.9 另回收启动时接入、在录制前已经 release 的一次性音效：等副本尾音结束且原声句柄无效后再释放，`retired_stopped` 记录此类回收。源事件仍有效的可重用音乐／快照不会因此被移除。

桥接 1.0.10 修正冻结中重新启动独立录音的暂停继承：子总线不再把父总线的暂停记成自身暂停；显式暂停指令在录音停止期间仍被保留。无需修改 OBS 音轨或系统音频设备。

### 4.5 预置模拟器（速通模式默认开启；`--no-sim` 关闭）

预置模拟器是由完整游戏代码逐帧推演的《蔚蓝》模拟器：从游戏某一帧的完整场景出发，给出任意按键之后每一帧 Madeline 与房间里实体的结果，与真实游戏逐帧一致（序章与第 1–9 章 A 面的校准用例全部通过）。它含有游戏代码，**只在开发者本机构建，不在仓库里**；发布目录是 `sim\dist\`（`celeste-sim` 单文件程序、资源表、说明 `README.md` 与 Python 接口 `sim.py`）。新电脑上没有模拟器时，把整个文件夹从构建它的电脑复制过来，或用 `--no-sim` 运行关模拟器的版本。

- 开关与两个版本：只用于速通模式，容器方式下默认开启（`--no-sim` 关闭；本机运行方式没有模拟器）。开关把速通模式分成两个版本，目标都是以最短的章节计时通关，提示词各一套：
  - **开模拟器**（`orchestrator/prompts/system_sim_zh.md`、`container_sim_zh.md`、`sim_zh.md`、`free_zh.md`、`retry_zh.md`、`playback_zh.md`）：智能体可以随意调用模拟器寻找并优化路线；提示词写明做法（整个房间推演到出口、按帧数优化完再一次执行）、建议的工作方式、物理参数简表、自动重试与规划回放。
  - **关模拟器**（`system_nosim_zh.md`、`container_nosim_zh.md`）：不挂 `/sim`，提示词删掉所有教它怎么玩的部分（做法、建议的工作方式、物理参数简表、写模拟器与搜索的建议、规划与优化的要求、自动重试的用法建议），只写目标、规则（不得调用或破解模拟器，不读、不反编译游戏程序，断网）、游戏工具与观测的格式、工作区里有什么，其余由智能体自由发挥。它算出的逐帧轨迹可以用 `show.trajectory()` 交给系统画出来（只用于展示，见 4.1 节"规划回放"）。准备阶段仍要求读完知识库（知识库本身两个版本相同）。
  - 两套共用 `interface_zh.md`（推理强度、坐标与画面、act 的输入格式、系统自动处理的部分），也都加上 HUD 一节 `hud_zh.md`。`--limit-planning` 只用于开模拟器的版本。
  - 探索模式不开放模拟器文件；`--sim-assist` 的限额短路线预测由主控在后台调用模拟器，智能体只能通过 `simulate` 工具花模拟体力使用。
- 开模拟器时，主控会把 `sim\dist` 只读挂到容器的 `/sim`，开局要求智能体把 `/sim/README.md` 和知识库一起读完；之后游戏每次停下（每次 `act`、`observe` 之后，自动重试之前），主控都会把当前帧的完整场景写到工作区的 `game/sim_state.json`，作为模拟器的起始状态。
- 智能体用 `/sim/sim.py`（`Sim`、`SimPool`）或 `/sim/celeste-sim` 命令行推演候选按键，把选中的按键与预测的逐帧位置写成计划文件交给 `act`；自动重试的重算程序也能调用它。
- **检查点**：任何一次推演的任何一帧都可以存成检查点（`r.save(路径, 第几帧)`），之后 `Sim(检查点)`、`SimPool(检查点)`、`sim.load`、`celeste-sim --state` 都从那一帧接着推演，存哪条路线、存到第几帧由智能体决定；检查点上还能再存检查点。检查点文件嵌着它所依据的快照、从快照出发的完整按键与每帧 expect，读入时从快照把按键重放一遍（几百帧只多几毫秒）；`r.full_inputs()`、`r.full_expect()` 拼出从快照算起的完整路线，`r.write_plan(路径)` 直接写成计划文件，并核对快照就是游戏当前停下的这一帧（否则不能从当前帧执行）。这样分段搜索、拼接都在模拟器里做，不必为了拿新起点先在游戏里走一段。实现在本机的 `sim\engine\Sim\SimStart.cs`（读入快照或检查点）与 `sim\package\sim.py`。实测（2026-10-24，容器里）：校准用例里随机 155 个（加序章 172 个）各在随机一帧存检查点再接着推演、再在后半段随机一帧存第二层检查点，与整段推演逐帧完全相同；`SimPool`、命令行、`info` 都能读检查点；同一个起点重复推演结果相同。
- **结果可复现**：每次读入都把随机数种子设成快照的帧号，同一个起点、同一串按键的结果总是一样（检查点重放与当初那次推演逐位相同）。游戏里由随机数决定的序章木桥（木板开始掉落前晃动 0.1～0.5 秒或 0.1～0.3 秒）一律取下限，即木板最早掉的最坏情况：模拟器里能过的路线，在游戏里不管随机数如何都能过。早先随机取，实测（2026-10-24 短测）出现过模拟器里能过、游戏里死了一次的情况；最坏情况下随机试 6000 组跑跳，236 组能到桥尾触发小鸟的剧情，桥仍然过得去。
- 剧情：碰到剧情触发器、心与磁带，或走到会按位置自动开始剧情的 NPC 附近（序章的老奶奶、序章结尾的鸟、2A 的镜子，以及第 3–6 章的 Oshiro、Theo、老奶奶、Badeline 等）时，模拟器在游戏开始剧情的那一帧以 `cutscene` 停下，`detail` 是事件名或 `npc:类型名`。NPC 的判定（本机 `sim\engine\Sim\SimNpcCutscene.cs`）照反编译源码，只保留与 Madeline 位置、状态有关的条件。早先模拟器把这些 NPC 当装饰：实测（2026-10-23，DeepSeek V4.1 Flash 正式运行）序章老奶奶的对话没有预料到、序章结尾的剧情被报成"死亡"。核对：新旧模拟器跑起始快照里有这些 NPC 的 203 个校准用例，通过数相同；只有两个序章桥尾用例由"中途对不上"变成"在剧情开始处停下"（旧版在那两处与游戏差在剧情开始后的慢动作上）；把 Madeline 挪到桥尾起跳，在剧情条件成立的那一帧停下；按正式运行序章房间 2 的按键推演，老奶奶的剧情在第 67 帧开始（游戏里第 68 帧失去控制）。
- 自检（不调用模型）：游戏在 test 存档的关卡里时运行 `python tools\sim_check.py`，主控推进几段随机按键，每段之前让容器里的模拟器先预测，再与游戏实际逐帧对照，应全部"逐帧一致"（实测 2026-10-23：6 段全部一致；容器里 Claude Code 的 Bash 沙箱也能直接运行 `/sim/celeste-sim`）。
- 速度：模拟器不按游戏的实时节奏走，每一帧固定按 1/60 秒的游戏时间推演，算完马上算下一帧，能多快就多快。实测（2026-10-23，容器里，序章第 3 个房间）：单个进程连续推演约 7.4 万帧/秒（约为实时的 1200 倍）；每组按键都要重新读入起始状态，随机生成 200 组、每组约 180 帧时约 3.3 万帧/秒、每秒 190 组；`SimPool` 开 4 个进程约 12.7 万帧/秒、每秒 720 组。Docker 不限制容器的 CPU（实测机器上容器能用 24 个核）；`SimPool()` 默认开 4 个进程，可以用 `workers` 参数开更多（22 个进程实测约 20 万帧/秒、每秒约 1560 组，每组约 130 帧）。
- 开关会改变容器的挂载，切换时主控会自动重建容器（工作区与会话记录保留）。

### 4.6 依次通关多章（`--chapters`）

`--chapters 0,1,2` 表示依次通关序章、1A、2A：一章通关（章节计时在这一帧停止）后，主控记下分段成绩，自动走完结算画面（序章没有结算画面，直接回地图）、回到地图（第一次通关时等解锁下一章的动画）、选下一章、按掉第一次进入章节时的明信片、用暂停菜单跳过开场剧情，停在新章节可操作的第一帧，智能体在同一个会话里接着玩。换章途中按正常速度推进，录像不快进。HUD 换章不清零：主计时与思考、工具、死亡等统计都按这一局累计（见 4.2 节“按一局统计”）；`summary.json` 里有每章的分段成绩（`splits`）与总计时（`total_time_ticks`）。`--scope campaign` 则从 `--chapter` 起按官方章节顺序一直玩下去。

自检（不调用模型，只用 test 存档，不碰正式存档）：

```powershell
# 可选：先关掉游戏，把 test 存档重置成某个正式存档的初始进度（这里是 opus5.5；只读它的存档文件；test 存档先备份到 runs\test_save_backups\<时间戳>\）
.\.venv\Scripts\python.exe calibration\reset_test_save.py --saves-dir "<Celeste 安装目录>\Saves" --like opus5.5
# 启动游戏后（停在任意画面）：进入 test 存档的序章，在每章把 Madeline 放到终点前走进去，确认主控自动进入下一章
.\.venv\Scripts\python.exe calibration\chain_check.py
```

实测（2026-10-23，test 存档重置成 opus5.5 的初始进度：1A 没通关过、2A 尚未解锁，与正式挑战开跑时相同）：通过。序章的结尾剧情用暂停菜单跳过，17 秒后停在 1A 第一个房间；1A 通关后经过结算画面与地图，22 秒后停在 2A 第一个房间；分段成绩两条。菜单宏也能从别的存档的关卡里退回选档页再选目标存档。要把 test 存档还原成重置前的样子：关掉游戏后运行 `reset_test_save.py --saves-dir ... --restore runs\test_save_backups\<时间戳>`。

### 4.6.1 按检查点分段（`--segments`）

每个官方章节（A 面）按检查点分成几段：段 k 从检查点 k（0 是章节开头）到下一个检查点，最后一段到通关。例如 1A 有两个检查点（十字路口、峡谷），分成"开头 → 十字路口""十字路口 → 峡谷""峡谷 → 通关"三段；第九章再见有八个检查点，分成九段。各章的检查点见 `configs/checkpoints.json`。`--segments` 选要玩的段，逗号分隔，每项写 `章节`（整章）、`章节.段` 或 `章节.起-止`（含两端）：

```powershell
# 1A 的后两段，然后整个 2A
.\.venv\Scripts\python.exe -m orchestrator.run --agent dev-opus --save test --mode explore --segments 1.1-2,2
```

- 选中的段按官方顺序玩。同一章里相邻的段连成一截，连续游玩，中间不打断。
- 一截在进入它终点检查点所在的房间时完成（桥接在那一帧停下），最后一段在通关时完成。完成时记一条分段成绩（`splits` 里有 `from`、`to`：起止检查点，`to` 为 `null` 表示到通关）。
- 两截之间由主控换过去：上一截在章节结尾结束时照常走完结算画面、回到地图；下一截从章节开头开始时走菜单进入，从检查点开始时直接进入那个检查点，与在选章面板里选它相同，**没到过的检查点也能进**（桥接的 `enter_checkpoint`，需要 1.0.6）。从检查点进入时新的章节计时从 0 开始，评价指标是各截计时之和。
- 最后一截在检查点结束时，主控用暂停菜单返回地图再结束运行，不让游戏在关卡里无人看管地继续运行。
- 提示词里写明每一截的起止检查点和终点房间；换到下一截时主控告诉智能体到了哪里、这一截到哪里为止。
- 检查点表来自 `configs/checkpoints.json`（从游戏里导出：`python tools\dump_checkpoints.py`，需要游戏开着、桥接 1.0.6）；没有这个文件时主控向游戏里的桥接要。
- 控制台：在"存档与章节"页选好章节后，下面列出各章的段，取消不想玩的段即可；运行中在"当前运行"的"要通关的范围"里改之后要玩的段（见 4.10）。
- 续跑：计划写在 `run_state.json` 的 `plan_pieces`（已完成的截 + 当前这一截 + 之后的截），续跑按已完成的截数接着走；在两截之间中断时（`piece_pending`），续跑先进入下一截的起点。

自检（不调用模型，只用 test 存档，不碰正式存档；游戏开着、没有主控在运行）：

```powershell
.\.venv\Scripts\python.exe tools\dump_checkpoints.py          # 导出检查点表（configs\checkpoints.json）
.\.venv\Scripts\python.exe calibration\segment_check.py       # 进入检查点、一截完成、换到下一截、最后一截返回地图
```

### 4.7 正式挑战

流程已全部由主控串联，并在 test 存档上彩排通过（见 4.6 节）。本项目的正式挑战是：Opus 5.5 与 Fable 5.1 各用自己的新存档（`opus5.5`、`fable5.1`）从序章开始，依次通关序章、1A、2A，分开时段各跑一次。你可以换成自己的存档名、标签与章节。

1. **开跑前**
   - 在 Claude Code 里用 `/usage` 看一下余量。额度用完时主控会让游戏冻结、等额度重置后接着玩（不计时，见 4.8 节），所以余量不足不会毁掉成绩，只会拉长现实时间；Fable 占每周额度更多。注意运行期间同一账号的其他会话也会被用完的额度挡住。
   - 启动 Docker Desktop；建议重启一次游戏（用只启用 CelesteAIBridge 的 Mod 配置），停在标题画面即可。游戏停在别的存档或章节里也可以，菜单宏会先退回选档页。
   - 确认本机有预置模拟器 `sim\dist\celeste-sim`（见 4.5 节）；没有时加 `--no-sim`。
2. OBS 不用手动启动：录屏默认开启，主控会自己启动 OBS、结束时关掉（见 4.4 节）。
3. **启动主控**（以 Opus 5.5 为例）：

   ```powershell
   .\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --model opus --chapters 0,1,2 --max-minutes 600
   ```

   Fable 5.1 把前三个参数换成 `--agent fable5.1 --save fable5.1 --model fable`，其余相同。`--max-minutes` 是现实用时上限（不含准备阶段与等待额度的时间），按需要放宽。
4. 主控依次：用菜单宏进入存档的序章并跳过开场剧情；核对存档名；把存档的全部文件备份到本次运行目录的 `save_backup\`；开始录制；创建智能体容器 `celeste-agent-<标签>` 并启动 Claude Code。智能体先读完知识库与 `/sim/README.md`（准备阶段，不计时，上限 60 分钟），第一次执行游戏工具时开始计现实用时。
5. 成绩以游戏内章节计时为主：序章、1A、2A 的章节计时之和（`summary.json` 的 `splits` 与 `total_time_ticks`；HUD 主计时是关卡内游戏时长，另含暂停菜单、片尾等章节计时不走的帧）。剧情能跳过的一律通过暂停菜单跳过；推理强度默认 high，智能体可以用 `set_effort` 自己调整。
6. 一章通关后主控自动进入下一章；2A 通关后结束：停止录制、交还游戏控制，产出写入 `runs\<标签>\<时间戳>\`。中途出意外时见 4.8 节续跑。

智能体标签决定工作区：新标签的工作区是空的。想让智能体带着准备好的程序开跑，就先用同一个标签在 test 存档上跑一次准备（工作区跨存档、跨运行保留）。本项目的正式挑战给两个模型各用一个新的标签（`opus5.5`、`fable5.1`），两者从同样的空工作区起步。

### 4.8 额度等待与中断续跑

**额度等待**：Claude Code 输出流里的限额事件报告 Max 套餐 5 小时与 7 天窗口的已用比例与重置时刻。默认一直用到额度真正用完：Claude Code 报告限额拒绝（rejected 限额事件，或"usage limit reached"一类的错误提示）时，主控结束 Claude Code 进程；设了 `--max-usage` 时，任一窗口的已用比例到这个值就提前这样做。之后游戏在章节内冻结在当前帧（菜单按配置冻结）（章节计时不走），现实用时与准备阶段的计时都暂停，HUD 显示"等待额度重置"；到重置时刻再等 2 分钟，用 `claude --resume` 接着同一个会话（上下文保留），第一条消息告诉智能体暂停过、先 `observe`。被结束时正在执行的 `act` 会照常执行完，结果写进工作区。重置还要等超过 `--quota-wait-max-hours`（默认 24）小时、或不知道何时重置时就停止本次运行（之后可以续跑）；只看到错误提示、没有重置时刻时，按最近一次限额事件里用量最高的窗口的重置时刻等待，至少 5 分钟。`metrics.json` 的 `waited_s`、`quota_waits` 记录等待。

**网络等待**（Claude Code 执行器，含第三方提供方）：模型连不上（没有 HTTP 响应，例如断网、DNS 失败、超时；或 5xx、529 过载）时 Claude Code 先按退避自己重试。连接类错误重试到第 4 次（`net_retry_attempts`），或它放弃重试、这一轮以 `API Error: Connection error` 一类错误结束时，主控认定断网：结束 Claude Code 进程，游戏在章节内保持冻结，现实用时与思考僵直**从第一次连不上起**停表（之前已记成思考的那几秒退回），HUD 显示"网络中断，等待恢复"，控制台对话栏记一条系统消息。之后约每 15 秒从智能体所在的位置探测一次模型接口（容器运行时在容器里以 agent 用户探测，与 Claude Code 走同一条出站路径；探测不了时退回本机；收到任何 HTTP 响应都算连得上），连续两次连得上、且至少等了一段时间（第一次 30 秒，连续断网时逐次加倍，最多 10 分钟，避免接口过载时反复重启）后，用 `claude --resume` 接着同一个会话，第一条消息说明暂停了多久、游戏一直冻结、不计入思考僵直，请先 `observe`；聊天 / 整理会话里则请它接着处理用户刚才的消息。认证失败（401/403）与额度限制（429）不算断网，照旧按原来的规则处理。等待期间控制台的停止、中断照常有效；连续连不上超过 `--net-wait-max-hours`（默认 24）小时就停止本次运行（之后可以续跑）；`--no-net-wait` 关掉这一功能。`metrics.json` 的 `net_wait_s`、`net_waits` 记录等待。Codex 执行器暂未接入。

**中断续跑**：Claude 执行器的运行没通关就停下（时间预算用完、主控报错、Ctrl+C）时不交还游戏控制，游戏冻结在原处——游戏在暂停菜单里章节计时也照样会走，所以不能靠暂停菜单。原生 GPT 在控制台显式选择“中断（保持冻结，可续跑）”时也保留接管；两种执行器在用户设置的自动停止条件（包括时长目标）触发后都正常收尾录像、但保留接管与冻结（见 4.10 节“两种结束方式”）；其他退出方式照常交还控制。用同样的 `--agent`、`--save` 加 `--resume <运行目录>` 续跑：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --resume runs\opus5.5\<时间戳>
```

- 模型、提供方、章节、`--sim`、时间预算沿用原运行，推理强度沿用中断时生效的那个（这些都可以显式改，例如加大 `--max-minutes`）；游玩模式不能改；直播、录屏、规划回放、HUD 形式与剧情处理方式不写就沿用。续跑不跑准备阶段。
- 统计接着累计：现实用时、分段成绩、死亡、决策数；Claude Code 接着原来的会话。游戏停在要续跑的章节里时直接接着玩；中断发生在两章或两截之间（结算画面或地图上）、游戏重启过、还没载入存档或停在别的存档的菜单里时，主控像新开一局那样用菜单宏进入（开了录屏时这段也从选档页开始录进录像）。游戏停在别的存档或别的章节的关卡里时拒绝续跑，先退出那个关卡。
- 运行按目标停下（例如"1A 通关后结束"）后，还没玩的章节也可以用 `--resume` 接着玩：时间上限按累计的现实用时算，通常要加大 `--max-minutes`。
- 原会话无法恢复时加 `--fresh-session` 开一个新会话，智能体从工作区的笔记与程序接着玩。
- 想在续跑时给智能体留一段话（例如章节之间的变化说明、要求先读新增的资料），写进一个文本文件，加 `--note-file 文件`。留言也会作为你发的一条消息显示在控制台的对话栏里（标着"局间留言"），方便回看发了什么。
- 有文件工具时，稳定操作说明放在工作区的分节版本指南中；启动只给当前任务、配置和索引路径。同会话未变的节不重读，变化节按索引哈希补读，压缩或遗忘时按需查阅。新会话首次接手仍须自行阅读。Codex 续跑通过系统指令更新配置；Claude 为覆盖旧压缩快照，规则与该会话上次送达的版本不同时才在首条另附短配置及指南版本（无文件工具的 host Claude 内联完整规则），断网、额度等待后重接同一会话且规则未变时不重复。智能体改动已发布的指南文件时，主控把原版本目录移到 `game/instructions/.stale-*` 后重新发布，不会因此拒绝启动。
- 原计划已经全部通关、还想用同一个会话接着玩下一章时，续跑加 `--chapters`（或 `--segments`）追加，例如 `--resume <运行目录> --chapters 3`：设置与统计接着原运行，新的一章从开头玩；HUD 开始新的一局，各项统计与主计时从 0 起算。原计划还没完成时不能另加，续跑沿用原计划。
- 新版主控中断后保留录像，续跑继续写入首次运行目录的 `recording\`，后续运行的 `recording_session.json` 指向同一份录制会话。原编码参数与声音设置保持不变；最终停止或“交还游戏控制”时生成完整版与纯享版。只在游戏冻结在关卡里时保留：停下时游戏在地图或菜单上（照常运行），这一段录像照常收尾，续跑另起一段，免得中断期间的菜单画面被一直录进去。保留期间尽量不要关闭 OBS 或游戏；编码器或独立音频丢失时，普通续跑核验原文件后把新内容接到同一录制会话，不覆盖原文件（见[录制恢复](RECORDING_RECOVERY.md)）。确定放弃原录像时才加 `--new-recording`（控制台里点“另起录像续跑”）另起一段：OBS 还开着同一目录就先收尾它，已经停了就把原会话标成放弃（已写下的文件原样保留）。已正常收尾的录像：普通续跑恢复到同一会话；加 `--chapters` / `--segments` 追加章节时另起新录像，上一章的录像不动。被标成放弃的录像不能再恢复，续跑须加 `--new-recording`（或 `--no-record`）。`--no-record` 只用于原录像已经结束（`finished`、`failed` 或放弃）的运行；原录像还在录或尚未收尾时请不加 `--no-record` 正常续跑。
- 不打算续跑时：在控制台点击“交还游戏控制”，收尾录像并恢复游戏（采集一停就交还游戏，视频后处理在后台接着做）。原录像收不了尾（OBS 关了或崩溃）时也照样交还，并把原录像标成放弃。游戏本身关掉或崩溃后无法续跑（章节进度只在游戏内存里）。

实测（2026-10-23，Haiku 5.5，`dev-haiku` 标签，test 存档 2A）：把上限设成 0.5、等待时长限制成 15 秒，连续 16 次"到上限 → 结束进程 → 等待 → 用 `--resume` 接回"都接回了同一个会话，上下文逐次累加，等待时间不计入现实用时；随后用 `--resume` 续跑这次运行，会话、上下文与决策数都接上了，智能体接着之前的思路继续游玩。

### 4.9 其他平台的模型（`--provider`）

除了 Max 订阅里的 Claude 模型，也可以让其他平台的模型进同一个沙箱游玩：容器里运行的还是同一个 Claude Code，只是通过平台兼容 Anthropic 的接口调用它们的模型；工具、提示词、知识库、沙箱、规划轮次与回放、HUD 与录制全部相同。提供方列在 `configs\providers.json`，目前有 `deepseek`（已实测）；GPT 使用原生 `--engine codex` 执行器。

**API 密钥只放在本机**，不入库、不出现在命令行与日志里：

1. 把密钥存成本机的一个文本文件（只有密钥一行），放在仓库目录之外，例如用户目录下的 `secrets\deepseek.key`。
2. 新建 `configs\local.providers.json`（`configs\local*` 不入库），写上文件位置：

   ```json
   { "deepseek": { "key_file": "C:\\Users\\<你>\\secrets\\deepseek.key" } }
   ```

   也可以不建这个文件，改设环境变量 `DEEPSEEK_API_KEY`。部署向导的 platform 步骤会帮你写好。
3. 主控读出密钥，经 `docker exec -e 变量名` 把它作为 `ANTHROPIC_AUTH_TOKEN` 交给容器里的 Claude Code（值从主控进程的环境传入，不写进命令行）。智能体自写的程序在零网络的 Bash 沙箱里运行，并且看不到密钥：主控以 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` 启动容器里的 Claude Code，它启动的子进程里清掉 `ANTHROPIC_AUTH_TOKEN` 等凭据变量。实测（2026-10-23）：不设这一项时 Bash 里能读到密钥（长度 35），设了之后读不到；沙箱也连不上 api.deepseek.com。

**运行**（DeepSeek V4.1 Flash；存档先在游戏里建好，或加 `--create-save` 让主控新建）：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent deepseek-flash --save <存档名> --provider deepseek --model deepseek-flash --chapters 0,1,2 --max-minutes 600
```

- 模型名：`deepseek-flash`（DeepSeek 官方接口里这个名字目前指向 V4.1 Flash 1017）、`deepseek-v4-pro`。主控在模型名后加 `[1m]`，让 Claude Code 按 100 万 token 的上下文压缩（压缩窗口 786432 token），Claude Code 的各个模型槽位与子智能体都指向这个模型，与 DeepSeek 文档里的 Claude Code 配置一致。HUD 显示的名字在 `configs\hud.json` 的 `names` 里。
- 网络：容器的防火墙只放行 `api.deepseek.com` 与游戏工具端口，**不放行 Anthropic**；Max 订阅令牌不会传给第三方。换提供方会改变容器的防火墙设置，主控会自动重建容器（工作区与会话保留）。建议每个模型用自己的 `--agent` 标签。
- 截图照常附上（DeepSeek 接口支持图片）；`set_effort` 照常可用，强度作为请求参数发给平台，效果以实测为准。
- 额度：Max 额度等待只针对订阅。第三方按用量计费，余额不足或接口出错时 Claude Code 报错、主控停止本次运行，游戏冻结在原处，处理好之后用 `--resume` 续跑（续跑沿用原来的提供方）。
- 认证失败（密钥错了、过期）时 Claude Code 会按退避重试 10 次、拖约 3 分钟，主控在第二次 401 时就停下并提示检查密钥。
- 实测（2026-10-23，假密钥，`--provider deepseek --model deepseek-flash --sim`，test 存档）：容器重建后只连得上 api.deepseek.com（Anthropic 与其他网站的域名都解析不到）；Claude Code 拿到全部游戏工具、连上游戏工具服务，请求到达 DeepSeek 并返回 401（"api key ****0000 is invalid"），主控 4 秒内停下；启动命令里没有密钥。
- 实测（2026-10-23，真密钥，test 存档序章，`--sim --record`，标签 `dev-deepseek`，当时是"每次暂停一轮工具"的规则）：`/models` 列出 `deepseek-flash` 与 `deepseek-v4-pro`；准备阶段读完知识库 45 秒、连同写工具共 4 分钟；游玩 10 分钟，9 次决策、没有死亡，停在第 2 个房间。它每次暂停用一次 Bash 跑自己写的束搜索，第二次调用被拒绝后直接执行；思考语句里 bunnyhop、jumpthru、climb 等用英文。扫描本机的运行记录与工作区，没有任何文件含有密钥。
- 加别的平台：在 `configs\providers.json`（或本机的 `configs\local.providers.json`）里照 `deepseek` 加一项（接口地址 `base_url`、防火墙放行的 `allowed_domains`、要放行的宿主机端口 `allowed_host_ports`、开跑前检查的地址 `gateway_check`、密钥的 `key_env` / `key_file`、模型名后缀 `model_suffix`、传给 Claude Code 的 `env`），平台需要提供兼容 Anthropic Messages 的接口；部署向导的 platform 步骤选"其他平台"会帮你写好。

**GPT**：使用原生 `--engine codex`，不再内置经 Claude Code 转换 OpenAI 协议的预设。准备、存档选择与 HUD 会话流程见 [LIVE_ADAPTATION.md](LIVE_ADAPTATION.md)。第三方 Anthropic 兼容接口仍可按上一段配置。

### 4.10 控制台：在图形界面里设置、启动与介入运行

控制台是一个独立窗口，主控的全部参数都能在里面设置：选模式与开关、选模型与推理强度、选存档与章节、调整可调参数与知识库的阅读权限，预览与修改提示词，然后开始运行；运行中看状态、暂停或继续、改推理强度、给沙箱里的智能体发消息；结束后续跑或交还游戏控制。HUD 只负责显示，控制台负责操作。

**打开**（仓库根目录）：

- 双击 `CelesteAIConsole.exe`。它是一个很小的启动器，用 `.venv` 里的 Python 打开控制台，不弹出命令行窗口；控制台已经开着时只把窗口提到前面。还没有 `.venv` 时，它会提示先运行一键部署。
- 或者用命令行：

  ```powershell
  .\.venv\Scripts\python.exe -m overlay.console              # 独立窗口（pywebview，使用系统自带的 WebView2）
  .\.venv\Scripts\python.exe -m overlay.console --browser    # 用默认浏览器打开 http://127.0.0.1:47790/console
  ```

控制台的数据来自 HUD 服务（端口 47790；控制台页面与接口只接受本机访问）。没有 HUD 服务在运行时，控制台把它作为独立后台进程启动；关掉控制台窗口不影响正在进行的运行，窗口开着时每 5 秒检查一次服务，断了就重新启动。端口上是没有控制台的旧版 HUD 服务时，控制台会提示，加 `--restart-service` 让它结束旧服务、启动新版（有主控在运行时不会这样做）。

**五个页面**：

| 页面 | 内容 |
| --- | --- |
| 运行 | 左栏"新运行"：执行器与提供方、模型、推理强度（档位由所选模型决定）、智能体标签（决定 `runs/<标签>/` 与工作区）、现实时间上限；游玩模式（速通 / 探索）与直播；开关（预置模拟器或限额短路线预测、思考僵直、仅正式思考、节省上下文、规划回放、OBS 录屏、游戏内 HUD、先读知识库、开始时先暂停、剧情交给智能体）；探索模式另有"规划程序"一栏（单次时长与两次 act 之间的次数，见 4.11）；存档、章节与知识库的摘要；"更多设置"里是其余命令行参数（时间与额度、规划轮次、录像与声音、HUD、调试与端口）；"可调参数"见 4.11。最下面实时显示等价的命令行，设置有问题时显示原因。中栏"当前运行"与运行记录，右栏"对话" |
| 存档与章节 | 地图（目前只有蔚蓝官方章节，以后会加入 MOD 地图）；游戏位置（填《蔚蓝》的安装目录，控制台会记住，空着时自动查找）；存档（已有存档按槽位区分，或新建）；章节（一条往上爬的路线，点选要依次通关的章节，下面有"序章 → 2A""只玩一章""全部章节"等快捷选择）；选中的章节有检查点时，下面按检查点列出各段，取消不想玩的段就只玩剩下的（4.6.1） |
| 知识库 | 按游玩模式列出智能体能读到的文件（速通模式是整个 `kb/`，含本机的 `kb/reference/`；探索模式只有 `kb/explore/`），标出准备阶段要求读完的"必读"文件；勾选决定阅读权限（4.12）；点文件名在右边查看、编辑（Markdown 可以预览），保存后下一次运行生效 |
| 提示词 | 按运行页的当前设置生成智能体会收到的提示词全文（页面上也可以直接切换速通 / 探索，与运行页同步），左边列出它由哪些文件拼成（按长度画成一条色带），右边逐段显示，每段标出来源文件；最后是准备阶段的第一条消息。每段都可以点"编辑"改对应的文件，见 4.13 |
| 关于 | 当前版本（控制台与桥接 Mod 的版本、提交号与日期）、当前环境（系统、Python、游戏目录、Everest、桥接、预置模拟器、知识库参考资料、Docker、OBS 与锁步插件、Codex CLI）、项目地址、作者、待办（`TODO.md`）与更新记录（`CHANGELOG.md`） |

顶栏三盏灯：游戏（桥接版本、正常运行 / 主控接管中 / 冻结中、当前章节与房间）、OBS（没在运行 / 运行中 / 锁步录制中）、主控（空闲 / 运行中与智能体标签）。游戏被接管、停在当前帧而没有主控在运行时，顶部出现提示，可以续跑最近一次运行，或交还游戏控制让游戏恢复正常。

**当前运行**：智能体名字与状态、章节与房间、章节计时、死亡、决策、推理强度、思考与工具时间、上下文、正在调用的工具；暂停 / 继续、推理强度（自动或固定某一档）、剧情处理、Fast（原生 GPT）；停止并保存录像、中断（保持冻结，可续跑）；目标与停止条件；要通关的范围（运行中按段改之后要玩的段：已完成的段标绿、正在玩的标金，之前的段不能选；和当前这一段紧接着的段连续玩，不紧接着的由主控直接送过去；都不选 = 当前这一段完成后结束。主控会告诉智能体，并把新计划写进 `run_state.json`，续跑照新计划走。旧版主控只能按整章改）。运行记录列出最近 40 次运行；最近一次停下时保持冻结、而且游戏此刻仍冻结着的运行可以直接续跑。

**推演设置**：已开启有限模拟辅助的新版主控，可在 HUD 实时修改当前额度、费用、预测长度、恢复规则等。修改等当前工具完成后生效，录像持续录制；未提交的编辑不会被状态刷新覆盖。余额留空表示保留，调整初始额度不重置账本，降低容量会截断余额。后台确认后显示结果，并向智能体排队通知新规则；续跑沿用本次参数。旧主控须先更新才支持，此能力不修改当前玩法或停止目标。

**两种结束方式**：

- **停止并保存录像**：结束这次运行、保存录像、交还游戏控制（游戏恢复正常运行）。
- **中断（保持冻结，可续跑）**：结束主控运行，保留游戏接管与录制会话：章节内冻结在当前帧、章节计时不走，菜单按冻结配置处理，之后可以在运行记录里点"续跑"接着玩并接续同一份录像。Claude Code 和原生 GPT 均支持；正在执行的动作会先走完。原生 GPT 的普通停止、自然通关、出错或全局时间预算结束仍交还控制；用户设置的自动停止条件（包括时长目标）触发后保留接管与冻结，但正常停止录像并生成成片，不留下活编码器。放弃续跑时点击“交还游戏控制”；显式中断保留的录像须先收尾再释放游戏。

**给智能体发消息**：Claude Code 执行器会先停下当前这一轮（正在执行的动作照常走完），再把你的消息作为下一轮交给它；原生 GPT 会把消息插入当前这一轮。暂停时智能体只回复，不操作游戏。

**注意**：

- 同一时间只能有一次运行。控制台检测到有主控在运行（包括从命令行启动的）时，"开始运行"不可用，知识库与提示词也不能保存修改。
- 桥接只接受一个连接，新连接会顶掉主控的连接。所以控制台平时不连桥接：游戏状态来自桥接（0.13.1 起）每 0.25 秒写进共享内存的状态字段；只有确认没有主控在运行时，"交还游戏控制"才会连一次桥接。
- 控制台启动的主控在后台运行，输出在 `local/background/<时间>/output.log`；没能完成运行就退出（没有写出运行总结）时，控制台会显示最后几行输出。
- 控制台记住的设置（游戏位置、各模式的知识库阅读权限）在 `configs/local.console.json`，改过的提示词在 `local/prompts/`（都是本机文件，不入库）。
- 只在命令行有的是 `--prepared`（用原生 GPT 预先准备好的会话开局，见 [LIVE_ADAPTATION.md](LIVE_ADAPTATION.md)）、`--fresh-session`（续跑时开新会话）与 `--note-file`（续跑时附用户留言）。

### 4.11 可调参数（`--tune`）

主控里原本写死的一些数值可以按运行调整：命令行写 `--tune 名称=值`（可以写多个），控制台在"新运行"的"可调参数"一栏（探索模式的两项在"探索：规划程序"一栏）。默认值就是一直以来的数值，不改时行为与提示词都与之前完全相同；改了之后，提示词与工具说明里提到的数字跟着变（例如"一次最多 600 帧""默认最多 5 分钟""单次规划程序最多 15 秒"）。续跑沿用原运行改过的参数，续跑时再写 `--tune` 可以覆盖。

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent dev-opus --save test --chapter 0 --tune playback_speed=4 --tune playback_round_s=2.5
.\.venv\Scripts\python.exe -m orchestrator.run --engine codex --agent dev-gpt --save test --chapter 1 --mode explore --tune explore_program_s=20 --tune explore_program_runs=3
```

| 分组 | 名称 | 含义 | 默认 | 范围 |
| --- | --- | --- | --- | --- |
| 执行与解说 | `max_frames_per_act` | 速通模式单次 act 最多推进的帧数（提示词与 act 的说明里的上限跟着变；探索模式用下面的 `explore_act_frames`） | 600 帧 | 60～3600 |
| 执行与解说 | `min_frames_per_act` | 单次 act 最少推进的帧数，两种模式都用（超过本模式的上限时按上限算）。只在角色可以操作时检查，不足时退回；死亡、换房等截断条件照样提前停下 | 40 帧 | 1～600 |

### 4.12 知识库的阅读权限（`--kb-deny`）

默认智能体能读到这个模式的整个知识库。控制台的"知识库"页里取消勾选的文件（或命令行 `--kb-deny 文件,文件`，写知识库内的相对路径），不会挂进容器，准备阶段也不要求阅读：这时主控把允许的文件同步到 `local/kb_views/<工作区标签>/`，挂进容器 `/kb` 的是这个副本（容器会按需重建，工作区与会话保留）。全部可读时直接挂知识库本身，与之前相同。续跑沿用原运行的设置。

提示词里提到的个别文件（例如探索模式的 `/kb/tools.md`、速通模式的 `/kb/techniques.md`）被取消后，智能体会读不到，请按需要决定。

**追加本机资料（`--kb-extra 目录`）**：某个系列赛要在默认知识库之外多给智能体一些资料（例如探索模式某一章起加入的技巧、机制节选）时，把这些文件放进本机的一个目录（建议 `local/kb_extra/<系列>/`，`local/` 不入库），开跑时加 `--kb-extra local/kb_extra/<系列>`。主控把默认知识库与这个目录合并同步到 `local/kb_views/<工作区标签>/` 挂进容器：目录里的新文件加进去（新开一局时准备阶段也要求读），与默认知识库同名的文件（例如 `README.md`）覆盖默认版本，`--kb-deny` 对追加的文件同样生效；默认知识库本身不改，别的运行不受影响。续跑沿用原运行的目录（目录里的文件改了，下次开跑或续跑时同步），传 `--kb-extra ""` 取消。第一次加上或取消时 `/kb` 的挂载方式会变，容器要重建：旧容器 `/tmp` 里的东西（智能体常把程序放在 `/tmp/claude-<uid>`）会先打包到 `local/container_tmp/`，新容器建好后原样放回，核对无误再删掉打包；放回失败时运行不开始，打包保留，报错里写了手动放回的命令。

### 4.13 提示词：预览与修改

提示词由 `orchestrator/prompts/` 里的几个文件按本次的设置拼成：速通模式按开 / 关模拟器选系统提示词，中间插入工具接口说明，再加运行环境（容器或本机）、自由度、自动重试、规划回放、HUD 与直播等说明；探索模式是 `explore_zh.md`，直播时加 `explore_live_zh.md`。主控还会按设置自动加几句（本次的章节、剧情模式、限额预测的规则；原生 GPT 另加工具名的对应表）。控制台的"提示词"页按运行页当前的设置显示这一版的全文，每一段标出来源；运行页的设置一改，这里跟着变。

点某一段的"编辑"就能修改它所在的文件：

- **保存到本机，不改仓库**：保存的内容放在 `local/prompts/<文件名>`（不入库），主控读提示词时优先用它；仓库里的文件不变，更新仓库也不会冲突。改回与仓库相同的内容，或点"恢复仓库版本"，就删掉本机修改。
- **占位符**：`{interface}`（在这里插入工具接口说明）、`{act_max_frames}`、`{bash_max}` 等在运行时换成本次的值（可调参数见 4.11），编辑页下面列出这个文件里有哪些。保存时删掉了占位符会提示，那个位置就不会再填入对应的内容。
- **生效时间**：下一次运行（包括续跑）开局时读取；有主控在运行时不能保存。同一个文件被几个版本共用（例如 `interface_zh.md` 在速通模式开 / 关模拟器时都用），改了以后这几个版本都变。
- **记录**：用了本机修改的运行，开局时在输出里列出改过的文件，`run_state.json` 的 `prompt_overrides` 记下文件名与内容的指纹，`system_prompt.md` 是这次实际发给智能体的全文。

提示词全文也能复制出来（"复制全文"），方便对比或分享。Claude Code 执行器的提示词接在 Claude Code 自带的系统提示词之后；原生 GPT 的提示词作为 Codex 的开发者指令。

## 6. 主控更新与检查

普通状态检查只读取 HUD、运行记录与 Bridge 共享内存，不连接桥接、不创建录制，脚本不额外扫描进程或历史运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/restart_controller.py check
```

修改主控 Python 后，在 HUD 暂停并等动作结束，再执行：

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/restart_controller.py restart
```

脚本经原主控中断入口，以同一会话、存档、端口和原录制续跑，新主控保持暂停。关卡要求已冻结，接回后帧号不变；已暂停的选章地图（Overworld）允许背景正常运行，关闭本段编码器后恢复追加，核验已录总帧数保留。地图中断不生成累计成片或纯享版，留到最终正常停止时处理。录制锁步或音频断开、其他未冻结场景仍拒绝。此命令不部署 Bridge／Runtime，不自动恢复试玩。

默认 HUD 端口为 47792，可用 `--hud-port` 指定，`--json` 输出简短结构化结果。旧主控尚未记录宿主及桥接端口时，首次需显式提供 `--host <local/background/宿主目录>` 和 `--bridge-port <端口>`；新主控会自动登记这些信息。`check` 只读报告原录制的实际状态（含非 recording、缺失或无法读取），不因此报错；`restart` 仍只接受 recording 状态。命令行直接启动的主控（`python -m orchestrator.run`）也持有同一主控互斥锁，维护与重启工具据此识别；它没有后台宿主，`restart` 会明确拒绝，请在 HUD 中断后手动 `--resume <原运行目录> --start-paused`。

交接记录在 `local/controller-restart.json`。默认等待 90 秒，`--timeout` 可设为 1–300 秒；超时或启动回执丢失后用 `restart --retry` 观察并接续同一次交接，不重复中断或另开宿主。若新宿主明确退出，脚本记录失败终态，报告宿主日志与标准 `--resume <原运行目录> --start-paused` 恢复路径；修复并人工续跑后，可以再次正常更新。明确的交接拒绝（中断被拒、其他宿主接管、录制身份或游戏帧号改变）也结束本次事务，须按报错检查现状；不会自动停止新宿主或回滚游戏。`--retry` 不替代修复失败的进程，也不自动恢复模型操作。Windows 明确未创建宿主进程（WMI 返回失败）时，`--retry` 换用新的宿主目录重新启动；启动结果未知时，只有宿主目录超过 60 秒仍无状态文件、且主控互斥锁空闲，才确认没有宿主并重新启动，不会出现两个主控。交接已被其他运行取代（例如人工续跑）且它启动的宿主未在运行时，新的 `restart` 将旧记录标为失败后正常预检。

## 7. 常见问题

| 现象 | 处理 |
| --- | --- |
| `deploy_bridge.ps1` 提示文件被占用 | 游戏还在运行，关闭后重试 |
| 平时自己玩时少了很多 Mod | 运行时用的是只启用 CelesteAIBridge 的 Mod 配置；在 Mod 管理器里切回自己的配置即可 |
| 测试客户端连不上 | 确认游戏已启动且 `log.txt` 里有 `[CelesteAIBridge] loaded`；端口被占用时日志会提示 |
| 主控提示需要更新桥接 | 主控要求桥接 1.4.0 或更新，并核验 `pico8_entry_guard`；按第 3 节重新构建安装 |
| 接管后按键没有反应 | 检查是否有其他 Mod 改了输入；建议用只启用 CelesteAIBridge 的 Mod 配置 |
| Steam 更新了游戏或 OBS 后出错 | 插件与 Mod 和版本绑定，需重新编译并重跑校准测试 |
| 存档进度不对 | 从运行目录的 `save_backup\` 恢复，并确认已关闭云同步 |
| OBS 启动时弹出"安全模式"对话框 | 上次 OBS 没有正常退出。用 `tools\obs_setup.py launch` 启动会先清掉过时的崩溃标记；已弹出时选正常模式（安全模式不加载锁步插件） |
| `--record` 提示 OBS 插件没有连上桥接 | 游戏与 OBS 谁先启动都可以，插件每秒重连一次；用 `tools\obs_setup.py status` 看插件是否加载，没加载就重新运行 `tools\build_obs_plugin.py` |
| 录像里没有 HUD | 游戏内 HUD：需要桥接 0.13.0，桥接太旧时主控会提示并改用网页 HUD。网页 HUD：OBS 打开页面时 HUD 服务要在运行（主控与 `obs_setup.py launch` 会先启动它）；场景是旧版本建的就关闭 OBS 后运行 `tools\obs_setup.py setup --reset` 重建 |
| 录像里游戏区域是一块深色方块 | 录制时游戏窗口是最小化的。主控会自动还原；如果输出里出现"还原失败"，手动把游戏窗口还原后重录 |
| 运行中途停下，提示达到用量上限 | 默认会等额度重置后接着同一个会话（4.8 节）；加了 `--no-quota-wait`、或重置还要等超过 `--quota-wait-max-hours` 时才停止，之后用 `--resume` 续跑 |
| 想用 Fable 5.1 | Max 上 Fable 另有用量限制，先在 Claude Code 的 `/model` 列表确认可用及计费方式 |
| 主控提示端口 47780 已被占用 | 另一个主控还在运行；结束它，或加 `--mcp-port 47781` |
| 主控提示存档名不一致 | 游戏当前进入的不是 `--save` 指定的存档；回到标题画面重新运行，菜单宏会自动选择 |
| 智能体卡住或想提前结束 | 在运行主控的窗口按 Ctrl+C；主控写出 summary.json，没通关时章节内保持冻结，菜单正常运行（可以 `--resume` 续跑），不续跑时从控制台“交还游戏控制”（先收尾保留的录像） |
| 提示找不到 docker | Docker Desktop 没有启动，或装好后还没新开终端；启动 Docker Desktop 后新开 PowerShell 再试 |
| 想让智能体从零开始（清空它写的程序与笔记） | 删除 `workspaces\<标签>\`；会话记录在数据卷 `celeste-claude-<标签>` 里，可用 `docker volume rm` 删除（需先 `docker rm -f celeste-agent-<标签>`） |
| 改了 `agent-container/` 之后 | 重新执行 `docker build -t celeste-agent:0.1 agent-container`；主控发现镜像变了会自动重建容器，工作区保留 |
| `--provider deepseek` 提示找不到密钥 | 按 4.9 节建 `configs\local.providers.json`，或设环境变量 `DEEPSEEK_API_KEY` |
| 智能体总被提示"本章的规划轮次已经用完" | 只在 `--limit-planning` 时有：每个新房间按大小存入轮次（一屏 3 轮、至少 3 轮）、死亡补 1 轮，调用模拟器的消息才扣（见 4.1 节）；用完后 Bash 被拒绝。不想受限制就去掉 `--limit-planning`（默认不限制） |
| 录像里没有规划回放 | 开模拟器时回放只画 `/sim` 的推演（自写模拟器的搜索没有记录）；关模拟器时只画智能体用 `show.trajectory()` 交来的轨迹（它没交就没有）；`--no-playback` 时都不画。主控输出里搜 `[playback]` |
| HUD 上思考很久不变 | 思考期间的更新取决于智能体有没有调用 `narrate`（看 `agent_events.jsonl`）；解说计时会在它下一次调用工具时提醒，一段连续的长思考中间没有提醒的机会 |
| PowerShell 里中文显示成乱码 | 日志文件本身是 UTF-8；用 `tools\run_status.py` 查看，或先执行 `chcp 65001` |


### 按钮消息与在线动作上限

“恢复试玩”对应普通 HUD 暂停后继续，默认不指定工具；“主控中断后恢复”对应主控、网络或额度中断后的重接，默认先观察核对可能未送达的最后动作结果。两种正文独立配置，已有本机 `button_resume_zh.md` 覆盖仍归普通恢复，不自动迁移或覆盖。

暂停启动后第一次继续只发送本次开始／重接说明；后续普通暂停恢复只发送恢复通知，不再同时附加通用自动续轮。用户留言与实际设置通知保留，笔记整理提醒仍按阈值独立发送。

网页 HUD 的“按钮提示词 → 配置默认消息”打开控制台“提示词”页，其中“按钮与主控消息”列出开始、准备、恢复、唤起、取名、目标、权限、剧情、Fast、推理强度、推演及重载等消息正文。保存到 `local/prompts/button_*_zh.md`，仅影响本机，不入库；运行中也可编辑或恢复默认，下一次对应消息生成时读取。消息来源、实际配置及阶段限制由主控附加，正文可清空，但不能改掉实际控制行为。没有模型消息的暂停、停止、断开等操作不因此额外唤起模型；唤起聊天仍等用户发言。

HUD“动作帧数”可实时调整单次 `act` 上限：探索模式 `explore_act_frames` 为 30–3600 帧，速通模式 `max_frames_per_act` 为 60–3600 帧。点击应用后在当前动作边界生效，保存到本次运行的 `run_state.json.tuning`，续跑沿用；不修改自写推演上限、模拟额度或录像。旧会话工具说明可能仍有旧数字，以最新通知和 `observe` 显示的当前范围为准。旧主控未提供该能力时控件禁用并提示更新。

### 个人追加要求

控制台“提示词”页提供独立的“个人追加要求”编辑器，默认留空。选择通用、GPT（Codex）探索／速通或 Claude 执行器探索／速通，填写后保存；当前组合会依次追加通用和专用要求。预览显示下一次启动将使用的内容。

内容保存在不入库的 `local/personal_prompts.json`，不修改共享模板，也不放入知识库；更新仓库仍会采用新的共享默认。保存后在下一次启动或重接模型时加载；普通暂停／继续不重新加载，也不向正在运行的会话插入消息。清空只移除当前范围。个人要求不能扩大实际工具权限、游戏范围或计算额度。原 `local/prompts/` 全文覆盖继续保留，个人偏好优先使用追加入口，避免长期覆盖共享模板而错过更新。

共享探索说明按当前任务安排探图、收集或研究；快速反馈与解说频率保留，程序实验和模型验证同样可以提供反馈。有限模拟辅助也可作为自建模型的对照，当前帧起点、额度与真实验证要求不变。

### 菜单与章节的冻结范围

新运行默认冻结选章地图和章节面板，主菜单与存档选择默认继续运行；三个开关分别为 `--freeze-chapter-select`、`--freeze-file-select`、`--freeze-main-menu`，均支持 `--no-…`，控制台也可设置。续跑沿用原设置，旧运行未记录时保持菜单不冻结。只在菜单就绪后冻结，自动加载与保存不被阻断。章节、片头和结算继续逐帧控制，确认与换章由 agent 显式操作。

默认分章录制不写选章帧与对应 PCM；连续模式按原规则保留菜单录制。`hello.frozen` 与 `hello.input_owned` 区分冻结和输入接管。详细边界见 [分章录制](CHAPTER_RECORDING.md)。


### 已到访地图内自由探索

原版没有通用的“曾进入”标记。许可依据存档的游玩时间、死亡、完成、草莓／心／检查点等正向记录及当前原生 Session 建立，不以解锁状态或地图面板焦点判断。很久以前进入后零计时、零记录退出的地图无法追溯；没有证据时不自动授权。通关成绩在此范围下同时记录面别。

`continue` 完成策略目前支持整章范围，不与有明确终点的部分章节计划组合。时长条件仍由独立目标设置；切换地图、重进检查点或通关不会重置目标计时。

`--scope visited --save-slot N` 只用于已有存档。主控在载入前读取选档候选的到访证据，先核定许可，再载入该存档，保留已有原生 Session 或停在选章界面，不代选新章节；agent 自行选择已获许可地图及其已解锁检查点。SID + A/B/C 面许可集合持久化在 `run_state.json` 的 `visited_maps`；同一试玩续跑沿用该集合，解锁地图不等于曾经进入。未授权地图在原生入场前拦截。空集合及未知候选不自动放开，新建存档在操作前拒绝。

选择该范围默认允许重启章节和返回地图，保存并退出仍禁止；三个权限可以独立覆盖，例如 `--no-allow-restart-chapter`。默认采用 `--completion-policy continue` 与 agent 剧情模式。通关不停止、不扩大地图范围，也不安排后续章节；游戏实验、建模及补收集品均可继续，时长等目标仍独立生效。显式传入 `--completion-policy stop` 可恢复通关停止。`--scope visited` 可在 `--resume` 时将旧顺序计划切换为自由探索，丢弃尚未执行的章节队列，但保留原存档、模型会话与统计。

网页 HUD 的开始试玩区域提供“已到访地图自由探索”及独立的“计划通关后停止／继续”选项。自由探索不支持新建存档，也不接受 `--chapters`／`--segments` 顺序计划；首次正常游玩后再使用。

### 计划外地图（绕行收集）

`--allow-detour`（控制台开关“允许去计划外的已解锁地图”，HUD 与控制台运行中的“计划外地图”下拉框）默认关，只用于单章或顺序范围。开启后计划不变，智能体可以自己用 `act` 按 P 打开暂停菜单选“返回地图”，在原生选章界面选择别的已解锁章节、面（A/B/C）和检查点，例如 8A（核心）的心门挡路时回到 3A 的后段检查点或已解锁的 4B、6B 收集水晶之心，再回到计划章节继续。主控不代选章节、不代按菜单；游戏的选章界面本来只提供已解锁的内容，主控只把入场范围限定在原存档槽位里的官方章节（桥接 1.10.0 的地图集合门禁，其他 MOD 关卡集与新建存档在入场前拦下）。开着时必须允许“返回地图”（另两项权限不变）：开启时一并打开；命令行与 `--no-allow-return-to-map`（或 `--no-allow-chapter-reset`）合用时拒绝启动，要禁止返回地图须同时加 `--no-allow-detour`；运行中控制台与 HUD 的返回地图下拉框锁定为允许，先关掉计划外地图才能单独禁止它。运行中关掉开关不收回返回地图权限；关掉时还在计划外地图里，离开它之前返回地图与 auto 模式的 B、P、N 照样可用。

计划章节（A 面）以外的地图都算计划外，计划章节的 B/C 面也算。计划外地图的通关不结束运行，不算完成计划，不推进或清空章节队列，不计入 `splits`、`completed_ticks` 与 `total_time_ticks`；它另记在 `metrics.json` 与 `summary.json` 的 `detours`（地图、面、章节计时）。死亡统一记录：计划外地图里的死亡计入总死亡数，也算进计划这一截的分段死亡。auto 剧情模式下主控照常跳过计划外地图的片尾剧情、确认结算与明信片，回到选章地图后交给智能体，不替它选下一张地图；为了操作暂停菜单与选章界面，auto 模式开了这个开关时也开放 B、P、N 三个键，智能体自己打开的暂停菜单主控不会关掉。agent 剧情模式下主控不代按任何键。重新进入计划章节时游戏可能开始新的一段会话、章节计时从头开始；开关打开过时，计划这一截的成绩是它在计划章节 A 面里各段会话章节计时之和（每段会话结束时的计时存进 `metrics.json` 的 `plan_banked_ticks`，游戏重启后续跑也接着累计），计划外地图的时间不算；计划章节通关时记一条分段成绩，之后照常结束或换到下一截。总结里的 `total_time_ticks` 同样只算计划章节。已知限制：新的一段会话是按章节计时倒退认出来的，游戏重启后接着存档里保存的会话继续玩时，那段已保存的计时可能被重复计入（少见，只在开关打开过时）。开关打开过之后，即使中途关掉，仍按实际地图区分计划内外（计划章节的 B/C 面照样是计划外）。HUD 的统计与主计时按一局算，与开关无关（见 4.2 节“按一局统计”）。

开关记在 `run_state.json` 的 `allow_detour`，运行中改过时以控制台的最后设置为准，续跑沿用；续跑时也可以显式打开或关闭，例如续跑一次已通关的运行、追加 8A（章节编号 9，核心）并允许绕行：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --resume runs\opus5.5\<上一次的运行目录> --chapters 9 --allow-detour
```

关时行为与原来完全相同：入场门禁仍只认当前计划的章节，auto 模式仍不开放 B、P、N。续跑时游戏停在计划外地图里也能接上（只在开关打开时）；停在选章界面时，auto 剧情模式与原来一样由开局菜单宏进入计划章节。
