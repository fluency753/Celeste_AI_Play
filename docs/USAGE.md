### 2.1 生成 Claude Code 令牌

在自己的电脑上、普通（非管理员）PowerShell 里操作，任意目录都可以：

1. 安装 Claude Code：执行 `irm https://claude.ai/install.ps1 | iex`。安装过程不显示进度，结束后关闭这个窗口。
2. 新开一个 PowerShell，执行 `claude --version`，能打印版本号即安装成功。若提示找不到 `claude`，改用完整路径 `& "$env:USERPROFILE\.local\bin\claude.exe"` 代替下面命令里的 `claude`。
3. 执行 `claude setup-token`。浏览器会打开 Claude 授权页，用 Max 账号登录并点授权；若浏览器没有自动打开，就把终端里显示的链接复制到浏览器。
4. 授权完成后，终端会打印一长串令牌（有效期一年）。用鼠标选中整串令牌并复制，注意换行显示的部分也要选全。
5. 执行 `notepad .env`（在仓库根目录下），把令牌粘贴在 `CLAUDE_CODE_OAUTH_TOKEN=` 后面，不加引号和空格，保存并关闭。
6. 令牌等同于账号凭据：不要发给任何人，也不要提交到仓库。`.env` 已被 `.gitignore` 排除。
7. 核对：带上该令牌执行 `claude auth status`，`authMethod` 应为 `oauth_token`。已在作者本机验证（Claude Code 2.1.309），`opus`（claude-opus-5-5）与 `fable`（claude-fable-5-1）均可调用，上下文窗口均为 100 万 token。

### 2.2 Python 虚拟环境

在仓库根目录的 PowerShell 中执行一次：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

之后所有 `python` 命令都可以用 `.\.venv\Scripts\python.exe` 代替，或先执行 `.\.venv\Scripts\Activate.ps1` 激活虚拟环境。依赖只有三个：`mcp`（游戏工具服务）、`pillow`（截图放大）、`uvicorn`（本机 HTTP 服务）。

### 2.3 安装 Docker Desktop

1. **装 WSL**（管理员权限，需要重启）：右键开始按钮 →"终端（管理员）"，执行 `wsl --install --no-distribution`，完成后重启电脑。Docker 不需要 Ubuntu 等发行版。
2. **检查 WSL 版本**：重启后在普通 PowerShell 执行 `wsl --version`，应为 2.1.5 或更新；否则执行 `wsl --update`。
3. **下载并安装**：从 [Docker 官网](https://docs.docker.com/desktop/setup/install/windows-install/) 下载 `Docker Desktop Installer.exe`，双击安装，配置页勾选 **Use WSL 2 instead of Hyper-V**。
4. **首次启动**：在开始菜单打开 Docker Desktop，接受服务协议（个人使用免费），登录与问卷可以跳过；左下角显示 Engine running 即可。
5. **验证**：新开 PowerShell 执行 `docker version`（Client 与 Server 都有版本号）和 `docker run --rm hello-world`（打印 `Hello from Docker!`）。

装好后已经打开的终端里可能找不到 `docker` 命令，新开一个终端即可；主控也会自动去默认安装位置找。

### 2.4 构建智能体镜像与隔离验收

在仓库根目录执行（Docker Desktop 需在运行）：

```powershell
docker build -t celeste-agent:0.1 agent-container
.\.venv\Scripts\python.exe -m orchestrator.verify --agent opus
```

第一次构建约 1～2 分钟。镜像里有固定版本的 Claude Code（2.1.309）、Python 3 与 numpy、scipy、numba、pillow、networkx、gcc / g++，没有任何游戏文件。

验收脚本会创建（或复用）智能体容器 `celeste-agent-opus`，逐项检查并打印"通过 / 不通过"：

| 类别 | 检查内容 |
| --- | --- |
| 认证 | 容器里的 Claude Code 使用订阅令牌（`oauth_token`），环境里没有 API 密钥 |
| 防火墙 | Claude Code 本身只能连到 Anthropic 官方域名与宿主机上主控的游戏工具端口；任意网站、直连 IP、外部 DNS、宿主机其他端口（包括游戏桥接端口）全部失败 |
| Bash 沙箱 | 让容器里的 Claude Code 用 Bash 工具运行同一套检查：全部失败，包括 Anthropic 与主控端口；命令环境里看不到登录令牌；只能写工作区与 `/tmp` |
| 重算程序沙箱 | 自动重试时主控运行智能体程序用的沙箱（bubblewrap，独立网络命名空间）：同一套检查全部失败；看不到登录令牌；只能写工作区与 `/tmp`，不能写家目录与知识库 |
| 权限 | 智能体用户改不了防火墙、托管配置与 `/etc/hosts`；托管配置拒绝联网工具、禁止退出沙箱 |

2026-10-22 在作者本机实测：全部通过。

### 2.5 生成知识库里的参考资料原文

知识库 `kb/` 里的物理常量与机制文件已入库；另外两份社区资料的原文不入库（第三方文本，不在公开仓库里再分发），需要在本机生成一次，生成后随 `kb/` 一起只读挂载进容器的 `/kb/reference/`：

- Celeste Wiki（celeste.ink）的 Tech 总表与全部技巧子页面（转成 Markdown，许可 GPLv3）；
- 草莓酱（Strawberry Jam Collab）训练场 Beginner → Grandmaster 的全部说明文字与机制库全文（英文、简体中文），直接从本机安装的 Mod 压缩包读取。

```powershell
.\.venv\Scripts\python.exe tools\fetch_reference.py --celeste-dir "D:\Fluency\software\steam\steamapps\common\Celeste"
```

需要能访问 celeste.ink，并且已经安装草莓酱 Mod（`Mods\StrawberryJam2021.zip`）。只要其中一份时可加 `--skip-wiki` 或 `--skip-sj`。输出在 `kb\reference\`，索引见其中的 `README.md`。2026-10-22 实测：wiki 17 个页面，草莓酱训练场 230 条、机制库 86 条，共约 310 KB。

另外可以导入你手上的 PDF 资料（同样只放本机），文字版每页标出原文页码，原 PDF 一并复制，智能体需要看插图时可以直接打开：

```powershell
.\.venv\Scripts\python.exe tools\import_reference_pdf.py 资料.pdf --name celeste_mechanics_explained --title "Celeste 机制详解（反向钟）" --note "来源：……"
```

提取文字需要 poppler 的 `pdftotext` 或 `pip install pypdf`。目前已导入两份：反向钟《Celeste 机制详解》（125 页，源码解读与机制详解，文字版约 240 KB）与《岩浆块机制说明》。只重新生成索引：`tools\fetch_reference.py --index-only`。准备阶段会要求智能体把这些文字版也读完，整份知识库约 34 万 token。

## 3. 桥接 Mod：构建、安装与测试

桥接 Mod（CelesteAIBridge）运行在游戏进程内，只监听本机 `127.0.0.1:47774`。未接管时游戏照常可玩；测试客户端发送 `activate` 后，游戏冻结在当前帧，只有收到 `step` 才逐帧推进。

### 3.1 构建与安装

先关闭游戏。如果 .NET SDK 没有加入 PATH，先执行 `$env:PATH = "<SDK 目录>;$env:PATH"`。然后在仓库根目录的 PowerShell 中执行：

```powershell
.\tools\deploy_bridge.ps1 -CelesteDir "D:\Fluency\software\steam\steamapps\common\Celeste"
```

脚本会编译 `game-bridge/`，再把 `everest.yaml` 与 `bin\CelesteAIBridge.dll` 复制到游戏的 `Mods\CelesteAIBridge\`。启动游戏后，在 `log.txt` 中能看到 `[CelesteAIBridge] loaded`。

### 3.2 冒烟测试

1. 启动游戏，停在标题画面即可。执行 `python tools\enter_save.py test --leave-active`，菜单宏会自动选中 `test` 存档、进入关卡、跳过开场，停在 Madeline 可以操作的第一帧（实测约 7 秒）。
2. 在仓库根目录执行 `python tools\bridge_client.py smoke --out-dir smoke`。
3. 通过的标准：冻结 1 秒帧号不变；单帧推进恰好 1 帧；向右走并起跳 51 帧后有轨迹与截图；最后自动交还控制。截图保存在 `smoke\` 里。

### 3.3 测试客户端常用命令

| 命令 | 作用 |
| --- | --- |
| `python tools\bridge_client.py hello` | 查看桥接版本与当前场景 |
| `python tools\bridge_client.py activate` | 接管并冻结在当前帧 |
| `python tools\bridge_client.py observe --out shot.png` | 读取当前帧的状态、实体、字符地图与截图 |
| `python tools\bridge_client.py step "30,R" "1,R,J" "20,R" --stop death,room --out after.png` | 按帧推进，遇到死亡或换房提前停下 |
| `python tools\bridge_client.py advance --until controllable --max 600` | 空输入推进，直到恢复可操作（过场、重生时用） |
| `python tools\bridge_client.py skip` | 调试用：直接跳过当前剧情，不经过暂停菜单（主控与菜单宏都改用暂停菜单跳过） |
| `python tools\bridge_client.py deactivate` | 交还控制，游戏恢复正常运行 |
| `python tools\enter_save.py <存档名>` | 从标题画面进入该存档的关卡，用暂停菜单跳过开场，停在可操作的第一帧；加 `--chapter 0` 指定章节（0 序章、1 被遗弃之城、2 旧址），加 `--leave-active` 保持接管 |

**预置模拟器的校准（开发中）**：`python calibration\sim_capture.py --chapter 3 --rooms=00-a,01-b --cases 2 --out runs\simcases\3a` 在 test 存档里载入指定房间（`--chapter` 是地图编号：0 序章、1–7 对应第 1–7 章、9 是第 8 章核心、10 是第 9 章告别）、做随机操作，把起止两帧的完整场景与逐帧轨迹存成用例；加 `--targets` 把 Madeline 放到房间里各类实体旁边定点测（同类实体跨章节累计只测 `--per-type` 个，默认 2）；`--speed` 为每个游戏循环推进的帧数（默认 60，即 60 倍速，只跳过中间帧的绘制）；`--assets 文件` 只导出模拟器用的贴图尺寸与精灵动画表。`load_room`、`teleport` 两个桥接命令只在 test 存档上可用，不会动正式存档。

按键写法：`L R U D` 方向，`J` 跳，`X` 冲刺，`Z` 蹲冲，`G` 抓，`T` 交互，`C` 确认，`B` 返回，`P` 暂停，`N` 日志；`A:角度` 表示左摇杆模拟方向（0 为右，90 为上）。每段以帧数开头，例如 `"6,R,J"` 表示按住右与跳 6 帧。

## 4. 运行智能体

### 4.1 让智能体游玩一个章节（可用）

1. 启动 Docker Desktop 与游戏，游戏停在标题画面或任意菜单即可（使用只启用 CelesteAIBridge 的 AIPlay 配置）。
2. 在仓库根目录执行：

   ```powershell
   .\.venv\Scripts\python.exe -m orchestrator.run --agent opus --save test --model opus --chapter 0 --max-minutes 20
   ```

3. 主控会依次：用菜单宏进入 `test` 存档、跳过开场；接管游戏并核对存档名；在 `127.0.0.1:47780` 启动游戏工具服务；创建或复用智能体容器 `celeste-agent-<标签>`，在容器里启动 Claude Code（无头模式）。智能体先进入**准备阶段**：按顺序把知识库从头到尾读一遍（见下文），整理笔记，然后才开始游玩。章节完成、时间预算用完或智能体连续 3 轮不调用工具时结束。章节完成时交还游戏控制；没通关就停下时游戏冻结在当前帧，可以续跑（见 4.8 节）。
4. 另开一个 PowerShell 查看进度：`.\.venv\Scripts\python.exe tools\run_status.py`（加 `-n 30` 显示更多决策）。

常用参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--agent` | 必填 | 智能体标签，决定容器 `celeste-agent-<标签>`、工作区 `workspaces/<标签>/` 与日志目录 `runs/<标签>/`。同一个模型在 test 存档准备、正式存档挑战时用同一个标签，准备好的程序就能带进正式挑战 |
| `--save` | 必填 | 游戏内存档名；与当前存档不一致时拒绝开始 |
| `--model` | `opus` | Claude Code 模型别名，如 `opus`、`fable`、`haiku`；第三方提供方用它自己的模型名，如 DeepSeek 的 `deepseek-flash` |
| `--provider` | `anthropic` | 模型提供方：`anthropic`（Max 订阅令牌）或 `configs\providers.json` 里的第三方，如 `deepseek`，见 4.9 节 |
| `--effort` | `high` | 开局的推理强度：`low`、`medium`、`high`、`xhigh`、`max`；之后智能体可以用 `set_effort` 自己调整 |
| `--max-minutes` | 240 | 现实时间上限，从智能体第一次真正执行游戏工具时开始计（准备阶段不算）；主要指标是游戏内章节计时，这里只防止无限运行。**观测里不显示**（2026-10-24 起）：显示"现实用时 / 预算"会让智能体赶时间、执行还没优化完的路线 |
| `--study-minutes` | 60 | 准备阶段（读知识库、写笔记与程序）的上限，不计入现实用时；到时自动开始计时并开放游戏工具 |
| `--no-study` | 关 | 跳过准备阶段，直接开始游玩（调试用） |
| `--max-usage` | 不设 | 可选：Max 套餐 5 小时或 7 天窗口的已用比例达到该值（0～1）就提前暂停智能体、游戏冻结，等额度重置后接着同一个会话（见 4.8 节）。默认不设：一直用到额度真正用完，用完时同样冻结并等待 |
| `--quota-wait-max-hours` | 24 | 额度重置还要等超过这么多小时时直接停止本次运行（之后可以续跑） |
| `--no-quota-wait` | 关 | 额度到上限时直接停止，不等待 |
| `--chapters` | 无 | 依次通关的章节编号，例如 `0,1,2`（正式挑战），见 4.6 节；给了它就不用 `--chapter` |
| `--sim` / `--no-sim` | 开（容器方式） | 预置模拟器的开关，把项目分成两个版本（见 4.5 节）：默认开，智能体可以随意调用模拟器寻找并优化路线；`--no-sim` 关，智能体不能调用模拟器，只能用自己的办法通关，提示词换成不教打法的版本。`--sim` 写不写都一样 |
| `--live` / `--no-live` | 开 | 实时展示（见 4.2 节）：默认开，智能体思考期间用 `narrate` 随时更新 HUD 上的思考，运行程序期间用 `show.status()` 报告进度、HUD 工具栏实时显示；`--no-live` 关，与之前一样，思考只在每次 `act` 时更新。续跑沿用原运行的设置 |
| `--rounds-per-room` | 3 | 规划轮次：一屏大小（320×180，1A 第一个房间）的新房间存入几轮，也是每个房间的下限，大房间按 `--room-scale` 放大（见下文"规划轮次"）；在游戏里死亡一次另补 1 轮 |
| `--room-scale` | 2 | 房间的长、高每变成这么多倍，存入的轮次乘这么多，向上取整（2 = 与房间面积成正比） |
| `--limit-planning` | 关 | 打开规划轮次的限制（见下文"规划轮次"），自动重试随之关闭；默认不限制思考与模拟器调用。只用于开模拟器的版本 |

容器里的智能体：

- **工具**：Bash、Read、Write、Edit、Glob、Grep 与游戏工具（`observe`、`act`、`set_effort`，实时展示时另有 `narrate`）。WebSearch、WebFetch 在托管配置里被拒绝；Claude Code 以受限模式启动，不读取任何用户、项目或本地设置文件，文件工具只能访问 `/workspace` 与 `/kb`。
- **网络**：容器出站只放行所用模型平台的域名（默认 Anthropic 官方域名；`--provider deepseek` 时只放行 api.deepseek.com，不放行 Anthropic）与宿主机上的游戏工具端口；Bash 命令（智能体自写的程序）在零网络的沙箱里运行，连模型平台也连不上。验收方法见 2.4 节。
- **没有后台任务**：容器里的 Claude Code 以 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 启动，Bash 命令只在前台运行，默认最多 5 分钟（可以用 timeout 参数加到 10 分钟），超时就结束、不会转入后台。
- **工作区** `/workspace`：对应宿主机的 `workspaces\<标签>\`，跨房间、跨章节、跨运行保留。每次观测与动作后，主控把完整观测（`game/latest_obs.json`）、上一次动作的全精度逐帧轨迹（`game/last_act.json`）与每个房间的首次观测（`game/rooms/`）写进来，供智能体的程序读取。
- **知识库** `/kb`：只读挂载仓库的 `kb/`，记录物理常量、状态机、实体规则、全部技巧与机制库、工作区数据格式，以及 `reference/` 里的社区资料原文（见 2.5 节）。技巧与机制的专有名词一律用英文（wallbounce、cornerboost、coyote time、liftboost 等），不用中文译名；基本动作（冲刺、跳、抓墙、体力）与实体名照常用中文。系统提示词也这样写，并要求智能体的思考语句同样只把这类专有名词写成英文。改知识库时可以用 `python tools\english_terms.py kb\*.md orchestrator\prompts\*.md`（加 `--check` 只检查）按其中的对照表统一替换；不要用它处理 `kb\reference\` 的原文。
- **计划文件**：智能体可以把程序算出的按键序列写成 JSON 文件，调用 `act` 时传 `plan_file`，不必把按键抄进参数。
- 主控在每轮开始时核对智能体拿到的工具列表，出现上面以外的工具会立即停止。

`--runtime host` 时（M2 的过渡方式）：Claude Code 直接在本机运行，以 `--tools ""` 关闭全部内置工具，只能调用两个游戏工具；使用独立配置目录 `agent-home/<标签>/`，并关闭 CLAUDE.md 与自动记忆。

准备阶段（读知识库）：

- 第一条消息按顺序列出要读的文件：`kb/` 下的全部文件，加上 `reference/` 里的 wiki 页面与草莓酱英文原文（中文版是同一内容的翻译，不要求读），目前共 27 个文件。
- 主控从 Claude Code 输出流里 Read 工具的结构化结果（起始行、行数、总行数）逐行核对读过哪些行，不依赖模型自己汇报。长文件被 Read 按长度截断时，截断之后的行不算读过。
- 读完之前，`observe` 与 `act` 不执行，只返回"还有哪些文件的哪几行没读"；智能体一轮结束时还没读完，主控就把这份清单发给它。
- 准备阶段不计入现实用时；第一次成功执行游戏工具时开始计现实用时。超过 `--study-minutes` 时自动开始计时并开放游戏工具。`metrics.json` 的 `study_s` 只记读知识库的用时（开局到读完），之后的准备阶段（写笔记、写程序、在模拟器里规划第一个房间）照常计入思考与工具时间，HUD 状态栏也照常显示思考中、运行工具（2026-10-24 之前整个准备阶段都记在"知识库读取"里、状态栏停在"读知识库 100%"、思考与工具时间不走，智能体在准备阶段就规划第一个房间时 HUD 看不出它在做什么）。
- 结束后 `summary.json` 的 `kb_study` 记录每个文件读了多少行。
- Opus 5.5 与 Fable 5.1 在 Claude Code 里的上下文窗口都是 100 万 token（在容器里用 `/context` 实测），整份知识库约 24 万 token，读完后还有约 72 万 token 才会触发自动压缩。

2026-10-22 用 Haiku 5.5 测试准备阶段：27 个文件全部读完，用时 35 秒（并行读取），上下文约 24.4 万 token；读完后智能体写好 `notes.md` 再调用 `observe`，主控在这时开始计时，时间预算按预期生效。

规划（默认不限制）：

- 默认不限制思考与模拟器调用：想多久、调用多少次模拟器、每次推演多少条都由智能体决定，计划文件的自动重试照常生效。观测里不显示现实用时与时间预算（`--max-minutes` 只是主控的安全上限）。开模拟器版本的提示词（`orchestrator/prompts/system_sim_zh.md` 的"做法"与"建议的工作方式"、`free_zh.md`）要求整个房间在模拟器里推演到出口、优化完再一次执行，没推演到出口的路线不执行（只有超过单次 `act` 600 帧的上限才分几次执行），需要分段搜索时用模拟器的检查点（4.5 节）；每个房间尽量一次通过：推演出能通关的路线之后以它为基准继续优化，哪怕是帧级的优化也加分（换起跳点、冲刺方向与时机，压缩每段帧数，试别的走法），多用高阶技巧与机制（super、hyper、wavedash、ultra、wallbounce、cornerboost、liftboost 等，以及弹簧、移动块、冲刺水晶等实体能借到的速度）缩短用时；搜索要以用时评分，只看"能不能到"的搜索往往给出能过但很慢的路线。
- 2026-10-23 晚按要求改成默认不限制：DeepSeek V4.1 Flash 在每屏 3 轮的限制下，好几轮花在程序出错和搜索失败上，轮次用完只能执行手里能过但很慢的路线（例如整段普通爬墙）。
- 2026-10-24 不再显示预算、改成"推演到出口再执行"：不限制轮次后 DeepSeek 的 30 分钟短测里，它仍然"推一点走一点"、路线乱也照走。读思维链：它一直看观测头部的"现实用时 / 预算"（"Time check… Let me move faster now"、"partial progress is better than none"），在序章第一个房间找到 266 帧的路线、自己列出可改进的地方后，因为赶时间直接执行；提示词前部"一段动作一次执行""用 land 停下检查""再规划下一段"是为没有模拟器的玩法写的，与"每个房间尽量一次通过"矛盾；它在 1A 临时写的搜索是从固定动作片段里随机拼接、按"走多远"打分、不做局部优化，到不了出口就先执行走得最远的那条，再从新位置重抽；模拟器不能存中间状态，在游戏里走一段成了它拿新起点的办法。

规划轮次（`--limit-planning` 打开）：

- 游戏只在 `act` 执行时推进，`act` 返回之后游戏冻结、章节计时停住，想多久由智能体决定。限制的是"规划轮次"，按房间大小给：本章每进入一个没来过的房间，按 ceil(3 × (宽/320) × (高/180)) 存入轮次、至少 3 轮——一屏大小（1A 第一个房间）3 轮，长、高每加倍轮次翻倍，比一屏小的房间也给 3 轮（`--rounds-per-room`、`--room-scale`）。序章的四个房间（448×180、464×200、320×180、992×180）依次是 5、5、3、10 轮，1A 的房间多数 3 轮、高一些的 4～5 轮，两倍长两倍高的房间 12 轮。之前是一屏 5 轮（序章 7、9、5、16 轮），2026-10-23 按要求改成 3 轮。在游戏里死亡一次补 1 轮（`RunConfig.death_bonus`），没用完的留给后面的房间，换章节清零。任何时候（任何位置、任何一帧停下时）都可以调用模拟器，只要还有剩余轮次。剩余轮数写在每次观测的头部（HUD 不再显示）。
- 只有调用模拟器才占轮次（`--sim` 时）：一条消息的工具全部返回后，这期间 `/sim` 写出了推演记录（或命令里直接调用了 `celeste-sim`），这条消息就扣一轮，同一条消息里并行的几次调用算一轮。Read、Write、Edit、Glob、Grep、`observe` 和不调用模拟器的 Bash（看数据、改程序、分析地图）都不占轮次。模拟器只能通过 Bash 调用，所以轮次用完后 Bash 被拒绝，其他工具照常可用。没有 `--sim` 时退回旧规则：`act`、`set_effort` 以外的工具每条消息占一轮，用完全部拒绝。
- 提示词要求智能体每个房间只过一次：用这几轮在模拟器里探索、比较、选出最快的路线，然后一次执行通过；简单的房间省着用，把轮次留给难的房间。直接用预置模拟器，不自己写模拟器；搜索算法由智能体自己决定，提示词鼓励它针对具体房间的结构设计剪枝条件与引导条件。提示词强调用时越短评分越高、普通操作既减少观赏性也拖慢用时；不写"避免死亡"一类的话。思考语句只写对房间或这一轮的分析与判断，不写具体数值与算法名。
- 为什么这样定：每次暂停只给一轮工具时，智能体只敢走一小段保险的慢路线；完全不限时，它在一次暂停里反复搜索，观众看不到试错过程。按房间给轮次，智能体有余地在模拟器里找快路线，探索过程再用"规划回放"画进游戏给观众看。按 Fable 5.1 的那次运行统计，各房间用的轮次中位数是 4，最难的房间 14～25 轮。
- 剩余轮次怎么告诉智能体：每次观测的头部有一行；每次调用模拟器的那条 Bash 结束时，`/sim/sim.py` 在标准错误末尾提示一行"（系统）这条消息调用了模拟器，占一轮规划轮次；本章剩余 N 轮"；工作区的 `game/rounds.json` 由主控实时更新（`left` 剩余、`used` 已用等），智能体随时可读，读文件不占轮次。
- 实现：容器的托管配置登记了 PreToolUse 钩子（`agent-container/celeste-gate.py`），Claude Code 调用任何工具之前都先问主控的 `/gate`（`orchestrator/pausegate.py`）；扣轮次由 `orchestrator/playback.py` 在一条消息的工具全部返回时根据推演记录做。拒绝次数记在 `metrics.json` 的 `pause_denials`，用掉的轮次记在 `plan_rounds_used`，主控输出里有 `[gate] 用掉一轮模拟器规划 …` 与 `[gate] 拒绝 …`。
- 准备阶段（游戏工具第一次真正执行之前：读知识库、写程序、自测）不受限制；第一次执行游戏工具时开始记账。续跑（`--resume`）没有准备阶段。
- 计划文件的自动重试同时关闭（`retry` 被忽略，结果里会说明），因为它会在不消耗轮次的情况下自动跑多次重算。
- 注意：只数模拟器调用，智能体用自己写的模拟器搜索就不占轮次。提示词要求搜索用 `/sim`（回放也只画 `/sim` 的推演），目前没有别的强制手段。
- 之前的版本是"每次暂停只允许一轮工具"：2026-10-23 用 Haiku 5.5 在 test 存档序章实测，房间 1 起跳太早掉进坑里、会塌的木桥上又掉下去三次，最后通关（章节计时 1:05.365，19 次决策，死亡 4 次）；DeepSeek 每次只敢走一小段。改成按房间给轮次之后，试错改在模拟器里进行，由规划回放展示。

规划回放（默认开启；`--no-playback` 关闭）：

- 智能体每规划完一轮（这条消息的工具全部返回），主控就把这一轮在预置模拟器里推演过的路线画进游戏画面，给观众看试错的过程；智能体同时在想下一轮，下一轮先结束时排队依次放，录像里一轮接一轮。回放时游戏完全不推进，不计章节计时，也不占轮次；录像里照常录下，`frames.csv` 里这些帧的章节计时记为 -1，`recording.json` 的 `replay_frames` 是回放帧数。
- 数据从哪来：工作区存在 `game/simlog/` 时，`/sim/sim.py` 的 `Sim`、`SimPool` 把每一次推演记成一条二进制记录（每帧位置、结果、按键哈希等，格式见 `orchestrator/playback.py`）。一轮结束后主控把记录文件移出工作区（运行目录的 `playback/pending/`），回放线程只把表头读进内存，挑好要画的路线，画完删掉。准备阶段（第一次执行游戏工具之前）的推演同样回放：智能体常在准备阶段就开始规划第一个房间，之前不画，序章第一个房间看不到绘制过程（2026-10-23 晚改）。只用自己写的模拟器做搜索时没有记录，提示词因此要求智能体用 `/sim` 搜索，并把每轮运行搜索的 Bash 的 `description` 写成一句给观众看的中文（只写分析与判断，不写数值和算法名），回放时显示在 HUD 上。
- 画几条：每 100 条推演画一条（`RunConfig.playback_ratio`），每轮至少 40 条（`playback_min_tracks`；推演更少时全画），不设上限。挑法：金色的一条（这一轮往前走的出口里最快的，快慢比的是推演终点的帧号——从检查点出发的推演帧数少，不能只比帧数；离起点不到 40 像素的出口多半是掉头回上一个房间，不算；这一轮没有往前走的出口就没有金色路线）；各个出口位置最快的一条；死亡按地点归并、离目标近的优先，最多占三分之一；剩下的名额按路线形状做最远点采样，挑和已选的最不像的。按推演先后出场，看起来像搜索一步步往前推进。
- 怎么画：所有轮次 3 倍速（`playback_speed`），每条路线每帧一个点（画之前合并误差不到 0.3 像素的共线点）。一轮里的路线在 0.8 秒内按推演先后陆续从 Madeline 身上长出来，延伸中一律淡绿色；一条线走到头的那一帧定下结果：死亡的从死亡点往起点一路变成淡红（终点画一个叉），这一轮最快的一条从终点往起点一路变成实心金色，变色以 8 倍速传导（`playback_recolor`）；其余的保持淡绿。线多时整体再调淡。只画线，不画角色。所有线变完色之后，这一轮的线变成淡灰留在画面上，接着放下一轮。
- 执行之前：智能体调用 `act` 时，主控先等排队的轮次放完（最后一轮变色传导完成），镜头平滑回到 Madeline（本来就在那里时直接开始），然后真实执行，画面上的线全部清掉。
- 镜头：线条延伸时镜头跟着伸得最远的绿线（此刻所有路线里前端离起点最远的那一点）平滑移动（受房间边界限制）；金色路线走到头、开始往回变金时，镜头跟着变色的那一点往回移，回到起点后停住；这一轮没有金色路线时，所有线画完后镜头沿伸得最远的那条线以同样的速度往回移到起点；两轮之间停在回放镜头上；渲染时临时换上回放镜头、渲染完原样换回，渲染期间随机数也换成单独的发生器，游戏状态一点不变。智能体 `observe` 截图的那一帧不换镜头、不画线，它看到的是游戏本来的画面。
- 刚进章节时圆圈转场还没放完：回放帧先把转场放完，黑屏消失之后才开始画线（进关卡的转场只影响能不能暂停，没有别的作用）。
- 声音：回放帧里音乐照常播放、音效暂停，录像里的音乐和之后真实执行时连在一起；游戏冻结、也没有回放时声音整体暂停。

### 4.2 HUD：右上角信息卡片（可用）

HUD 是一个本地网页，显示智能体名称与状态、当前房间、章节计时（主计时）、推理强度、思考与工具总时间、对话上下文、压缩次数、知识库读取用时、死亡次数、本章剩余的规划轮次、模拟器调用次数、当前这次调用推演的路径条数、当前房间推演出的最速出房用时、正在调用的工具和当前思考（现实用时不再显示，时间预算照常生效）；规划回放时状态显示"规划回放"，下方写第几轮、推演了多少条路线，思考语句换成这一轮的说明。2026-10-23 晚改版：卡片收窄（1080p 下 350 像素宽，原来 430），思考语句字号加大，推理强度用英文档位名，去掉进度条等装饰。同一个页面既放进置顶窗口供现场观看，也作为 OBS 浏览器源进入录像。

- **服务**：主控运行时会在进程内启动 HUD 服务：`http://127.0.0.1:47790/hud`（`--hud-port` 改端口，`--no-hud` 关闭）。也可以单独启动：`.\.venv\Scripts\python.exe -m overlay.server`。它总是显示最近一次运行（`runs\latest.txt`），换一局不用刷新页面；`--run <运行目录>` 可以固定显示某一局。
- **置顶窗口**：主控运行时自动打开（`--no-hud-window` 关闭；已经开着就沿用），结束时关闭；也可以单独打开：`.\.venv\Scripts\python.exe -m overlay.window`（需要 `pip install -r requirements.txt` 装上 pywebview，使用系统自带的 WebView2）。窗口透明、无边框、置顶、点击穿透、不进任务栏、不抢焦点；贴在游戏窗口客户区右上角，宽度为游戏窗口的 18.2%（1080p 下 350 像素）、边距 2%，随游戏窗口移动与缩放；游戏最小化时隐藏。游戏窗口按进程名 `Celeste.exe` 查找，不会认错成同名的资源管理器窗口。游戏要用窗口化或无边框全屏，独占全屏盖不上去。这个窗口不会进录像（OBS 的游戏采集只采游戏画面，录像里的 HUD 来自浏览器源）。
- **OBS**：`tools\obs_setup.py` 建的场景里已经有 HUD（见 4.4 节）。它用"本地文件"方式打开 `overlay\hud.html`，页面再去连 HUD 服务取数据，所以 OBS 比主控先启动也没关系。自己加时：添加"浏览器"来源，勾选本地文件选这个页面（或 URL 填 `http://127.0.0.1:47790/hud`，但 OBS 启动时服务必须已在运行），1080p 下宽 350、高 508（2026-10-24 之前是 400：调用工具折成三行、思考六行、回放说明两行时卡片最高约 498），放在右上角（x 1532、y 38）。页面背景透明，不用额外设置。
- **实时性**：执行中桥接每 6 帧（0.1 秒）推送一次章节计时、冲刺次数与房间，页面每 0.1 秒取一次数据并在两次之间按实时外推，所以主计时逐帧走动、左侧色条随冲刺状态变色；思考期间思考时间持续走动。思考语句一有新的就淡入替换；主控在每段动作推进之前先把新语句写出、等 0.4 秒（`RunConfig.thought_lead_s`，游戏冻结着，录像里不占时间）让 HUD 换好，所以录像里新语句与这段动作的第一帧同时出现，不再滞后（以前每 3 秒才检查一次，常常动作做完、进了下一个房间才换上）。想恢复定时检查，在 `configs\local.hud.json` 里设 `thought_check_s`。

- **配置**：配色、名称与参数在 `configs\hud.json`；本机想改的项写进 `configs\local.hud.json`（不入库），会覆盖同名项。

### 4.3 重放一次运行（不调用模型）

按某次运行记录下的决策逐条重放，用来复现问题或检查主控、桥接的改动是否影响游戏结果：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.replay runs\dev-opus\20261022-200717 --save test --chapter 0
```

每条决策会打印停止原因与实际帧数，并与原记录比对（"一致"或"不同"）。重放的日志写在 `runs\replay\<时间戳>\`。实测：重放 Opus 的序章记录，21 次决策逐帧一致，两段剧情都通过暂停菜单跳过。

### 4.4 录制：OBS 只录游玩帧（可用）

录制时 OBS 的每个视频帧都向游戏要一帧：游戏推进一帧、画到屏幕上，OBS 采下这一帧；智能体思考、游戏停住时 OBS 一帧也不写。成片的帧数等于游玩帧数，声音也只取游玩帧对应的那 1/60 秒，思考时间在成片里完全不存在。HUD 作为场景里的浏览器源一起录进去。

**一次性准备**

1. 安装 OBS 32（Steam 版即可）与 ffmpeg（`winget install Gyan.FFmpeg`）。
2. 构建并安装锁步插件（先关闭 OBS；不需要 Visual Studio，脚本会用 pip 装 zig 交叉编译）：

   ```powershell
   .\.venv\Scripts\python.exe tools\build_obs_plugin.py --obs-dir "D:\path\to\OBS Studio"
   ```

   OBS 更新后要重新构建，并重跑下面的校准测试。
3. 本机设置写进 `configs\local.recording.json`（不入库，只写要改的键；默认值见 `configs\recording.json`）：

   ```json
   {
     "obs_dir": "D:\\path\\to\\OBS Studio",
     "ffmpeg": "C:\\Users\\<你>\\AppData\\Local\\Microsoft\\WinGet\\Links\\ffmpeg.exe",
     "video_args": "-c:v h264_nvenc -preset p5 -tune hq -rc constqp -qp 16 -g 120",
     "audio_offset_ms": 130
   }
   ```

   `video_args` 是 ffmpeg 的视频编码参数：有 NVIDIA 显卡用上面的 NVENC，否则保留默认的 libx264。`audio_offset_ms` 只在某段量不到声音延迟时作为后备（见下）。

**每次录制**

```powershell
# 启动游戏（桥接 0.8.5 以上；当前版本 0.11.4）后直接运行主控：录屏默认开启
.\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --model opus
# 不录屏
.\.venv\Scripts\python.exe -m orchestrator.run --agent dev-opus --save test --model opus --no-record
```

- **录屏开关**（2026-10-24）：`--record`（默认）时主控在开局前检查 OBS：没在运行就调用 `tools\obs_setup.py` 的启动流程（自动建好专用的配置文件与场景集合 CelesteAI、记下你原来选中的配置、最小化到托盘、等锁步插件连上桥接），结束时（通关、预算用完、中断或出错，都在成片与纯享版写好之后）关掉 OBS（最小化到托盘的 OBS 有时不响应正常关闭，30 秒内没退出就强制结束；`obs_setup.py stop --force` 同样），并把 OBS 下次打开时选中的配置还原成你原来的；OBS 已经开着时直接用（要是 CelesteAI 配置），结束时不关。`--no-record` 时不启动、不调用 OBS。手动管理 OBS 的命令照旧可用：`tools\obs_setup.py launch` / `stop` / `status`。改了 `overlay\hud.html` 或 HUD 尺寸后，先关掉开着的 OBS，让主控下次重新启动它（OBS 的浏览器源不会自动刷新）。

- `obs_setup.py` 不动你自己的配置文件与场景：CelesteAI 配置文件是 1920×1080、60 fps、NV12、48 kHz；场景里只有游戏采集、应用音频捕获（只录 Celeste.exe）与 HUD 浏览器源，没有桌面音频和麦克风。场景集合已存在时不改动（你在 OBS 里的调整会保留），只把 HUD 浏览器源的宽高同步成 `configs\recording.json` 里的值（HUD 加高后旧场景会切掉卡片底部；OBS 运行时不改，`stop` 之后再 `launch` 即可）；`setup --reset` 重建（原来的先备份）。`status` 查看插件是否加载、是否连上桥接。
- **开局也录进去**：主控先把游戏退回选档页（这一步不录、快速完成），从选档页开始录制，再按正常速度选存档、进地图、选章节、进关卡、用暂停菜单跳过开场剧情，所以录像从选档页开始。HUD 在这段时间显示智能体名称、推理强度与"等待"，计时都是 0。`--resume` 续跑与 `--skip-enter` 时没有开局，接管游戏后开始录制。
- 结束（通关、预算用完或中断）时先停止录制、等 ffmpeg 收尾，再交还游戏控制；结果写进 `summary.json` 的 `recording`。
- 游戏窗口不能最小化：最小化后游戏的画面缓冲缩成 8×8 像素，录像里只剩 HUD、游戏区域是一块深色方块。主控在开始录制前、以及录制中每次推进游戏前检查，发现最小化就把窗口还原（不激活，不抢你当前窗口的焦点）并在输出里提示。窗口被别的窗口挡住不影响录制。
- 录制期间动作块按 60 fps 实时播放（节奏由 OBS 决定），`--play-speed` 不起作用。
- 其他参数：`--ffmpeg`、`--record-video-args`、`--audio-offset-ms` 临时覆盖配置；`--record-marker` 在画面左下角画帧号条码（只用于校准）。

**产出**（`runs\<智能体>\<时间>\recording\`）

| 文件 | 内容 |
| --- | --- |
| gameplay.mkv | 成片完整版：画面 + 声音（AAC 256 kbps），含规划回放 |
| gameplay_pure.mkv | 成片纯享版：只有真实游玩的帧（去掉规划回放），录制结束时由主控生成 |
| video.mkv、audio.wav | 只有画面、只有声音（32 位浮点，每帧 800 个样本） |
| frames.csv | 每个成片帧对应的游戏帧号、章节计时与 OBS 时间戳 |
| segments.csv | 连续推进的各段，以及每段开头量到的声音延迟 |
| recording.json | 结果摘要：帧数、缺帧与重复检查、声音对齐情况 |

**纯享版**（2026-10-24）：录制结束时主控从完整版里去掉规划回放的帧（`frames.csv` 里章节计时为 -1、-2 的行），生成 `gameplay_pure.mkv`：画面按行号（即 `video.mkv` 的帧序号）挑帧、按录制时的编码参数重新编码；声音按同样的行号从 `audio.wav` 裁剪（每帧 800 个样本），两段游玩之间去掉了回放，音乐不再连续，接缝处淡出、淡入各 5 毫秒去掉爆音。没有规划回放时纯享版直接与完整版相同（硬链接）。结果写进 `recording.json` 的 `pure`；失败不影响完整版。已有的录像可以补生成：`python tools\make_pure.py runs\<智能体>\<时间>\recording`（编码参数默认用那次录制的）。2026-10-24 用 DeepSeek 短测的录像（20919 帧，其中回放 13979 帧）实测：纯享版 6940 帧（115.7 秒，31 段），NVENC 编码 36 秒生成；截帧检查画面里没有回放的线。

**声音怎么对齐**：OBS 采到的声音比画面晚 110～170 毫秒，而且录制中途 OBS 增加音频缓冲时会突然变化约 70 毫秒，不能用一个固定值。桥接在游戏停住时暂停全部声音（录制时在停住后的第一个节拍、推进前恢复；不录制时停住 60 毫秒后暂停），所以每段动作开头的声音都从完全静音恢复；插件在每段开头找这条边（对齐到这一段第一帧的开头），量出当时的延迟（取最近 5 次的中位数）用于这一段。

**暂停与继续之间的接缝**：桥接 0.11.3 之前停住 60 毫秒后才暂停声音，这段时间放出的音乐不进录像，每段开头还多一帧静音，接缝处音乐会跳一下（2026-10-23 正式运行的录像里能听出来）。现在暂停正好在上一帧的 1/60 秒结束时生效、恢复在下一段第一帧生效，音乐内容是接上的；插件在相隔一个节拍以上的两帧之间，前一帧结尾淡出 2 毫秒、后一帧开头淡入 2 毫秒，去掉爆音；每段量到的延迟与最近 5 次的中位数相差不超过 20 毫秒时直接用这一段自己的值，恢复的那一刻正好落在第一帧开头。桥接 0.11.4 起停住后的第二个空闲节拍才暂停：0.11.3 在第一个节拍暂停，暂停正好卡在上一帧的末尾，FMOD 按混音块生效的抖动常把上一帧最后 3～19 毫秒截成静音（2026-10-24 DeepSeek 短测约四分之一的接缝），听起来是细小的断口；现在上一帧的音乐总能完整放出，代价是接缝处音乐向前跳约一帧长度（约 17 毫秒，有淡出淡入，听不出来）。`calibration/m6_recording_test.py` 会检查每段动作最后一帧末尾的静音（应在 3 毫秒以内）。

**音频块边界的断口（电流声）**（2026-10-24 修正）：之前的插件在约一半的段里每 1024 个样本留下一个值为 0 的样本（OBS 音频块的边界，取样时向上取整与四舍五入不一致），连续游玩时听起来是持续的电流声，与接缝无关。修正后块与块首尾衔接、偶尔漏掉的单个样本用相邻样本补上；改完插件要重新编译安装（先 `python tools\obs_setup.py stop`，再 `python tools\build_obs_plugin.py --obs-dir "<OBS 目录>"`）。M6 测试会检查 WAV 里有没有这种断口。

两条录音路线共用 `orchestrator/audio_validation.py` 的断点检测：`obs_mix` 的 M6 校准会调用它，`game_nrt` 的输出也可用同一离线工具检查。默认仅将“左右声道同时精确为零，且同一声道前后信号均高于 1e-6”标为疑似单采样断点，避免把静音中的浮点残留误报。1e-6 是线性振幅（满幅为 1，约 -120 dBFS），与声音恢复校准的 2e-3 阈值分开；较安静的信号可显式降低阈值。结果用于定位候选断点，不等于完整音质鉴定，也不会改写录音。

```powershell
.\.venv\Scripts\python.exe tools\check_recording_audio.py runs\<agent>\<时间>\recording\audio.wav
```

离线工具发现疑似断点返回退出码 1，未发现返回 0；文件格式或参数错误返回 2。使用 `--silence-threshold` 调整离线检查阈值，M6 校准的对应参数为 `--dropout-threshold`。检查按块读取，适用于较长录像。`calibration/audio_mixer` 的独立混音器自检可用第二个位置参数导出 float32 立体声 WAV，再交给同一工具检查，整个过程不连接真实游戏或 OBS。

**校准测试**（游戏停在 test 存档的关卡里、Madeline 站在平地上，OBS 已启动）：

```powershell
.\.venv\Scripts\python.exe calibration\m6_recording_test.py --rounds 40 --think 0.7
```

不调用模型，模拟 40 轮"停 0.7 秒 → 推进约 1 秒"并录制，检查：成片帧数 = 推进的帧数、游戏帧号连续；每一帧画面里的帧号条码与记录一致（证明 OBS 采到的正是那一帧）；WAV 长度 = 帧数 × 800；每段都量到声音延迟、对齐误差不超过一帧；gameplay.mkv 含画面与声音。

M6 验收（2026-10-23，桥接 0.8.5，OBS 32.2.2，RTX 5080 + NVENC）：校准测试全部通过——2219 帧画面与条码逐帧一致，40 段全部量到声音延迟，对齐误差中位数 0 毫秒、最大 12.7 毫秒。实测 Opus 5.5 游玩 4 分 31 秒（15 次决策、死亡 4 次），成片 1633 帧（27.2 秒），帧号连续、无缺帧无重复，19 段中 15 段量到声音延迟（130～152 毫秒），HUD 一同录入。录 2219 帧期间游戏进程内存只增长约 30 MB。

### 4.5 预置模拟器（默认开启；`--no-sim` 关闭）

预置模拟器是由完整游戏代码逐帧推演的《蔚蓝》模拟器：从游戏某一帧的完整场景出发，给出任意按键之后每一帧 Madeline 与房间里实体的结果，与真实游戏逐帧一致（序章与第 1–9 章 A 面的校准用例全部通过）。它含有游戏代码，**只在开发者本机构建，不在仓库里**；本机的发布目录是 `sim\dist\`（`celeste-sim` 单文件程序、资源表、说明 `README.md` 与 Python 接口 `sim.py`）。

- 开关与两个版本（2026-10-24）：容器方式下默认开启（`--no-sim` 关闭；本机运行方式没有模拟器）。开关把项目分成两个版本，目标都是以最短的章节计时通关，提示词各一套：
  - **开模拟器**（`orchestrator/prompts/system_sim_zh.md`、`container_sim_zh.md`、`sim_zh.md`、`free_zh.md`、`retry_zh.md`、`playback_zh.md`）：智能体可以随意调用模拟器寻找并优化路线；提示词写明做法（整个房间推演到出口、按帧数优化完再一次执行）、建议的工作方式、物理参数简表、多用高阶技巧与机制、自动重试与规划回放。
  - **关模拟器**（`system_nosim_zh.md`、`container_nosim_zh.md`）：不挂 `/sim`，提示词删掉所有教它怎么玩的部分（做法、建议的工作方式、物理参数简表、写模拟器与搜索的建议、规划与优化的要求、自动重试的用法建议），只写目标、规则（不得调用或破解模拟器，不读、不反编译游戏程序，断网）、游戏工具与观测的格式、工作区里有什么，其余由智能体自由发挥。它算出的逐帧轨迹可以用 `show.trajectory()` 交给系统画出来（只用于展示，见 4.1 节"规划回放"）。准备阶段仍要求读完知识库（知识库本身两个版本相同）。
  - 两套共用 `interface_zh.md`（推理强度、坐标与画面、act 的输入格式、系统自动处理的部分）。`--limit-planning` 只用于开模拟器的版本。
- 开模拟器时，主控会把 `sim\dist` 只读挂到容器的 `/sim`，开局要求智能体把 `/sim/README.md` 和知识库一起读完；之后游戏每次停下（每次 `act`、`observe` 之后，自动重试之前），主控都会把当前帧的完整场景写到工作区的 `game/sim_state.json`，作为模拟器的起始状态。
- 智能体用 `/sim/sim.py`（`Sim`、`SimPool`）或 `/sim/celeste-sim` 命令行推演候选按键，把选中的按键与预测的逐帧位置写成计划文件交给 `act`；自动重试的重算程序也能调用它。
- **检查点**（2026-10-24）：任何一次推演的任何一帧都可以存成检查点（`r.save(路径, 第几帧)`），之后 `Sim(检查点)`、`SimPool(检查点)`、`sim.load`、`celeste-sim --state` 都从那一帧接着推演，存哪条路线、存到第几帧由智能体决定；检查点上还能再存检查点。检查点文件嵌着它所依据的快照、从快照出发的完整按键与每帧 expect，读入时从快照把按键重放一遍（几百帧只多几毫秒）；`r.full_inputs()`、`r.full_expect()` 拼出从快照算起的完整路线，`r.write_plan(路径)` 直接写成计划文件，并核对快照就是游戏当前停下的这一帧（否则不能从当前帧执行）。这样分段搜索、拼接都在模拟器里做，不必为了拿新起点先在游戏里走一段。实现：本机 `sim\engine\Sim\SimStart.cs`（读入快照或检查点）与 `sim\package\sim.py`。核对（容器里，`runs\cktest\test_ckpt.py`）：校准用例里随机 155 个（加序章 172 个）各在随机一帧存检查点再接着推演、再在后半段随机一帧存第二层检查点，与整段推演逐帧完全相同；`SimPool`、命令行、`info` 都能读检查点；同一个起点重复推演结果相同。
- **结果可复现**：每次读入都把随机数种子设成快照的帧号，同一个起点、同一串按键的结果总是一样（检查点重放与当初那次推演逐位相同）。游戏里由随机数决定的序章木桥（木板开始掉落前晃动 0.1～0.5 秒或 0.1～0.3 秒）现在一律取下限，即木板最早掉的最坏情况：模拟器里能过的路线，在游戏里不管随机数如何都能过（之前随机取，2026-10-24 的短测里模拟器说能过、游戏里死了一次）；最坏情况下随机试 6000 组跑跳，236 组能到桥尾触发小鸟的剧情，桥仍然过得去。
- 剧情：碰到剧情触发器、心与磁带，或走到会按位置自动开始剧情的 NPC 附近（序章的老奶奶、序章结尾的鸟、2A 的镜子，以及第 3–6 章的 Oshiro、Theo、老奶奶、Badeline 等）时，模拟器在游戏开始剧情的那一帧以 `cutscene` 停下，`detail` 是事件名或 `npc:类型名`。NPC 的判定（本机 `sim\engine\Sim\SimNpcCutscene.cs`）照反编译源码，只保留与 Madeline 位置、状态有关的条件；2026-10-23 晚补上，之前模拟器把这些 NPC 当装饰，DeepSeek 正式运行时序章老奶奶的对话没有预料到、序章结尾的剧情被报成"死亡"。核对：新旧模拟器跑起始快照里有这些 NPC 的 203 个校准用例，通过数相同；只有两个序章桥尾用例由"中途对不上"变成"在剧情开始处停下"（旧版在那两处与游戏差在剧情开始后的慢动作上）；把 Madeline 挪到桥尾起跳，在剧情条件成立的那一帧停下；按正式运行序章房间 2 的按键推演，老奶奶的剧情在第 67 帧开始（游戏里第 68 帧失去控制）。
- 自检（不调用模型）：游戏在 test 存档的关卡里时运行 `python tools\sim_check.py`，主控推进几段随机按键，每段之前让容器里的模拟器先预测，再与游戏实际逐帧对照，应全部"逐帧一致"（2026-10-23 实测 6 段全部一致；容器里 Claude Code 的 Bash 沙箱也能直接运行 `/sim/celeste-sim`）。
- 速度：模拟器不按游戏的实时节奏走，每一帧固定按 1/60 秒的游戏时间推演，算完马上算下一帧，能多快就多快。2026-10-23 在容器里实测（序章第 3 个房间）：单个进程连续推演约 7.4 万帧/秒（约为实时的 1200 倍）；每组按键都要重新读入起始状态，随机生成 200 组、每组约 180 帧时约 3.3 万帧/秒、每秒 190 组；`SimPool` 开 4 个进程约 12.7 万帧/秒、每秒 720 组。容器能用 24 个核，Docker 不限制 CPU；`SimPool()` 默认开 4 个进程，可以用 `workers` 参数开更多（22 个进程实测约 20 万帧/秒、每秒约 1560 组，每组约 130 帧）。
- 开关会改变容器的挂载，切换时主控会自动重建容器（工作区与会话记录保留）。

### 4.6 依次通关多章（`--chapters`）

`--chapters 0,1,2` 表示依次通关序章、1A、2A：一章通关（章节计时在这一帧停止）后，主控记下分段成绩，自动走完结算画面（序章没有结算画面，直接回地图）、回到地图（第一次通关时等解锁下一章的动画）、选下一章、按掉第一次进入章节时的明信片、用暂停菜单跳过开场剧情，停在新章节可操作的第一帧，智能体在同一个会话里接着玩。换章途中按正常速度推进，录像不快进。HUD 的主计时是已通关各章与当前章的章节计时之和，`summary.json` 里有每章的分段成绩（`splits`）与总计时（`total_time_ticks`）。

自检（不调用模型，只用 test 存档，不碰正式存档）：

```powershell
# 可选：先关掉游戏，把 test 存档重置成正式存档的初始进度（只读 opus5.5 的存档文件；test 存档先备份到 runs\test_save_backups\<时间戳>\）
.\.venv\Scripts\python.exe calibration\reset_test_save.py --saves-dir "<游戏目录>\Saves" --like opus5.5
# 启动游戏后（停在任意画面）：进入 test 存档的序章，在每章把 Madeline 放到终点前走进去，确认主控自动进入下一章
.\.venv\Scripts\python.exe calibration\chain_check.py
```

### 4.7 正式挑战

流程已全部由主控串联，并在 test 存档上彩排通过（见 4.6 节）。两个智能体分开时段各跑一次：

1. **开跑前**
   - 在 Claude Code 里用 `/usage` 看一下余量。额度用完时主控会让游戏冻结、等额度重置后接着玩（不计时，见 4.8 节），所以余量不足不会毁掉成绩，只会拉长现实时间；Fable 占每周额度更多。注意运行期间同一账号的其他会话也会被用完的额度挡住。
   - 启动 Docker Desktop；建议重启一次游戏（AIPlay 配置，只启用 CelesteAIBridge），停在标题画面即可。游戏停在别的存档或章节里也可以，菜单宏会先退回选档页。
   - 确认本机有预置模拟器 `sim\dist\celeste-sim`（见 4.5 节）。
2. OBS 不用手动启动：录屏默认开启，主控会自己启动 OBS、结束时关掉（见 4.4 节）。
3. **启动主控**（Opus 5.5）：

   ```powershell
   .\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --model opus --chapters 0,1,2 --max-minutes 600
   ```

   Fable 5.1 把前三个参数换成 `--agent fable5.1 --save fable5.1 --model fable`，其余相同。`--max-minutes` 是现实用时上限（不含准备阶段与等待额度的时间），按需要放宽。
4. 主控依次：用菜单宏进入正式存档的序章并跳过开场剧情；核对存档名；把存档的全部文件备份到本次运行目录的 `save_backup\`；开始录制；创建智能体容器 `celeste-agent-<标签>` 并启动 Claude Code。智能体先读完知识库与 `/sim/README.md`（准备阶段，不计时，上限 60 分钟），第一次执行游戏工具时开始计现实用时。
5. 成绩以游戏内章节计时为主：序章、1A、2A 的章节计时之和（HUD 主计时，`summary.json` 的 `splits` 与 `total_time_ticks`）。剧情能跳过的一律通过暂停菜单跳过；推理强度默认 high，智能体可以用 `set_effort` 自己调整。
6. 一章通关后主控自动进入下一章；2A 通关后结束：停止录制、交还游戏控制，产出写入 `runs\<标签>\<时间戳>\`。中途出意外时见 4.8 节续跑。

智能体标签：`opus5.5`、`fable5.1` 两个标签还没用过，工作区是空的，两者起点相同（之前测试用的 `opus` 标签的工作区里有它当时自写的模拟器，正式挑战不会带进去）。想让智能体带着准备好的程序开跑，就先用同一个标签在 test 存档上跑一次准备。

### 4.8 额度等待与中断续跑

**额度等待**：Claude Code 输出流里的限额事件报告 Max 套餐 5 小时与 7 天窗口的已用比例与重置时刻。默认一直用到额度真正用完：Claude Code 报告限额拒绝（rejected 限额事件，或"usage limit reached"一类的错误提示）时，主控结束 Claude Code 进程；设了 `--max-usage` 时，任一窗口的已用比例到这个值就提前这样做。之后游戏冻结在当前帧（章节计时不走），现实用时与准备阶段的计时都暂停，HUD 显示"等待额度重置（HH:MM 恢复）"；到重置时刻再等 2 分钟，用 `claude --resume` 接着同一个会话（上下文保留），第一条消息告诉智能体暂停过、先 `observe`。被结束时正在执行的 `act` 会照常执行完，结果写进工作区。重置还要等超过 `--quota-wait-max-hours`（默认 24）小时、或不知道何时重置时就停止本次运行（之后可以续跑）；只看到错误提示、没有重置时刻时，按最近一次限额事件里用量最高的窗口的重置时刻等待，至少 5 分钟。`metrics.json` 的 `waited_s`、`quota_waits` 记录等待。

**中断续跑**：没通关就停下的运行（时间预算用完、主控报错、Ctrl+C）不交还游戏控制，游戏冻结在原处——游戏在暂停菜单里章节计时也照样会走，所以不能靠暂停菜单。用同样的 `--agent`、`--save` 加 `--resume <运行目录>` 续跑：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent opus5.5 --save opus5.5 --resume runs\opus5.5\20261023-120000
```

- 模型、章节、`--sim`、时间预算沿用原运行，推理强度沿用中断时生效的那个（这些都可以显式改，例如加大 `--max-minutes`）；不跑准备阶段。
- 统计接着累计：现实用时、分段成绩、死亡、决策数；Claude Code 接着原来的会话。中断发生在两章之间（结算画面或地图上）时，主控先用菜单宏进入下一章。
- 原会话无法恢复时加 `--fresh-session` 开一个新会话，智能体从工作区的笔记与程序接着玩。
- 录像按运行分段，每段在各自运行目录的 `recording\` 下。
- 不打算续跑时：`.\.venv\Scripts\python.exe tools\bridge_client.py deactivate` 交还游戏控制。游戏本身关掉或崩溃后无法续跑（章节进度只在游戏内存里）。

实测（2026-10-23，Haiku 5.5，`dev-haiku` 标签，test 存档 2A）：把上限设成 0.5、等待时长限制成 15 秒，连续 16 次"到上限 → 结束进程 → 等待 → 用 `--resume` 接回"都接回了同一个会话，上下文逐次累加，等待时间不计入现实用时；随后用 `--resume` 续跑这次运行，会话、上下文与决策数都接上了，智能体接着之前的思路继续游玩。

### 4.9 其他平台的模型（`--provider`）

除了 Max 订阅里的 Claude 模型，也可以让其他平台的模型进同一个沙箱游玩：容器里运行的还是同一个 Claude Code，只是通过平台兼容 Anthropic 的接口调用它们的模型；工具、提示词、知识库、沙箱、规划轮次与回放、HUD 与录制全部相同。提供方列在 `configs\providers.json`，目前有 `deepseek`（已实测）；GPT 使用原生 `--engine codex` 执行器。

**API 密钥只放在本机**，不入库、不出现在命令行与日志里：

1. 把密钥存成本机的一个文本文件（只有密钥一行），放在仓库目录之外，例如 `D:\secrets\deepseek.key`。
2. 新建 `configs\local.providers.json`（`configs\local*` 不入库），写上文件位置：

   ```json
   { "deepseek": { "key_file": "D:\\secrets\\deepseek.key" } }
   ```

   也可以不建这个文件，改设环境变量 `DEEPSEEK_API_KEY`。
3. 主控读出密钥，经 `docker exec -e 变量名` 把它作为 `ANTHROPIC_AUTH_TOKEN` 交给容器里的 Claude Code（值从主控进程的环境传入，不写进命令行）。智能体自写的程序在零网络的 Bash 沙箱里运行，并且看不到密钥：主控以 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` 启动容器里的 Claude Code，它启动的子进程里清掉 `ANTHROPIC_AUTH_TOKEN` 等凭据变量。2026-10-23 实测：不设这一项时 Bash 里能读到密钥（长度 35），设了之后读不到；沙箱也连不上 api.deepseek.com。

**运行**（DeepSeek V4.1 Flash；存档要先在游戏里建好，和 opus5.5、fable5.1 一样）：

```powershell
.\.venv\Scripts\python.exe -m orchestrator.run --agent deepseek-flash --save <存档名> --provider deepseek --model deepseek-flash --chapters 0,1,2 --max-minutes 600
```

- 模型名：`deepseek-flash`（DeepSeek 官方接口里这个名字目前指向 V4.1 Flash 1017）、`deepseek-v4-pro`。主控在模型名后加 `[1m]`，让 Claude Code 按 100 万 token 的上下文压缩（压缩窗口 786432 token），Claude Code 的各个模型槽位与子智能体都指向这个模型，与 DeepSeek 文档里的 Claude Code 配置一致。HUD 显示的名字在 `configs\hud.json` 的 `names` 里。
- 网络：容器的防火墙只放行 `api.deepseek.com` 与游戏工具端口，**不放行 Anthropic**；Max 订阅令牌不会传给第三方。换提供方会改变容器的防火墙设置，主控会自动重建容器（工作区与会话保留）。建议每个模型用自己的 `--agent` 标签。
- 截图照常附上（DeepSeek 接口支持图片）；`set_effort` 照常可用，强度作为请求参数发给平台，效果以实测为准。
- 额度：Max 额度等待只针对订阅。第三方按用量计费，余额不足或接口出错时 Claude Code 报错、主控停止本次运行，游戏冻结在原处，处理好之后用 `--resume` 续跑（续跑沿用原来的提供方）。
- 认证失败（密钥错了、过期）时 Claude Code 会按退避重试 10 次、拖约 3 分钟，主控在第二次 401 时就停下并提示检查密钥。
- 2026-10-23 用假密钥检查整条链路（`--provider deepseek --model deepseek-flash --sim`，test 存档）：容器重建后只连得上 api.deepseek.com（Anthropic 与其他网站的域名都解析不到）；Claude Code 拿到全部游戏工具、连上游戏工具服务，请求到达 DeepSeek 并返回 401（"api key ****0000 is invalid"），主控 4 秒内停下；启动命令里没有密钥。
- 2026-10-23 用真密钥在 test 存档序章试跑（`--sim --record`，标签 `dev-deepseek`）：`/models` 列出 `deepseek-flash` 与 `deepseek-v4-pro`；准备阶段读完知识库 45 秒、连同写工具共 4 分钟；游玩 10 分钟，9 次决策、没有死亡，停在第 2 个房间。它每次暂停用一次 Bash 跑自己写的束搜索，第二次调用被拒绝后直接执行；思考语句里 bunnyhop、jumpthru、climb 等用英文。第一次试跑发现"每次暂停一轮工具"在有准备阶段时没有生效（第一次游戏工具的钩子先于计时开始），已改正，第二次试跑里生效。扫描本机的运行记录与工作区，没有任何文件含有密钥。
- 加别的平台：在 `configs\providers.json`（或本机的 `configs\local.providers.json`）里照 `deepseek` 加一项（接口地址 `base_url`、防火墙放行的 `allowed_domains`、要放行的宿主机端口 `allowed_host_ports`、开跑前检查的地址 `gateway_check`、密钥的 `key_env` / `key_file`、模型名后缀 `model_suffix`、传给 Claude Code 的 `env`），平台需要提供兼容 Anthropic Messages 的接口；部署向导的 platform 步骤选"其他平台"会帮你写好。

**GPT**：使用原生 `--engine codex`，不再内置经 Claude Code 转换 OpenAI 协议的预设。准备、存档选择与 HUD 会话流程见 [LIVE_ADAPTATION.md](LIVE_ADAPTATION.md)。第三方 Anthropic 兼容接口仍可按上一段配置。

## 6. 常见问题

| 现象 | 处理 |
| --- | --- |
| `deploy_bridge.ps1` 提示文件被占用 | 游戏还在运行，关闭后重试 |
| 平时自己玩时少了很多 Mod | 运行 AI 时用的是 AIPlay 配置；在 CeleMod 里切回自己的配置即可 |
| 测试客户端连不上 | 确认游戏已启动且 `log.txt` 里有 `[CelesteAIBridge] loaded`；端口被占用时日志会提示 |
| 接管后按键没有反应 | 检查是否有其他 Mod 改了输入；建议用只启用 CelesteAIBridge 的 Mod 配置 |
| Steam 更新了游戏或 OBS 后出错 | 插件与 Mod 和版本绑定，需重新编译并重跑校准测试 |
| 存档进度不对 | 从 `runs/` 中的存档备份恢复，并确认已关闭云同步 |
| OBS 启动时弹出"安全模式"对话框 | 上次 OBS 没有正常退出。用 `tools\obs_setup.py launch` 启动会先清掉过时的崩溃标记；已弹出时选正常模式（安全模式不加载锁步插件） |
| `--record` 提示 OBS 插件没有连上桥接 | 先启动游戏再启动 OBS 都可以，插件每秒重连一次；用 `tools\obs_setup.py status` 看插件是否加载，没加载就重新运行 `tools\build_obs_plugin.py` |
| 录像里没有 HUD | 场景是旧版本建的（网址模式）：关闭 OBS 后运行 `tools\obs_setup.py setup --reset` 重建场景 |
| 录像里只有 HUD，游戏区域是一块深色方块 | 录制时游戏窗口是最小化的。现在主控会自动还原；如果输出里出现"还原失败"，手动把游戏窗口还原后重录 |
| 运行中途停下，提示达到用量上限 | Max 额度触顶后无头运行不会自动等待；主控会暂停计时，额度恢复后续跑，成绩中注明 |
| 想用 Fable 5.1 | Max 上 Fable 另有用量限制，先在 Claude Code 的 `/model` 列表确认可用及计费方式 |
| 主控提示端口 47780 已被占用 | 另一个主控还在运行；结束它，或加 `--mcp-port 47781` |
| 主控提示存档名不一致 | 游戏当前进入的不是 `--save` 指定的存档；回到标题画面重新运行，菜单宏会自动选择 |
| 智能体卡住或想提前结束 | 在运行主控的窗口按 Ctrl+C；主控会交还游戏控制并写出 summary.json |
| 提示找不到 docker | Docker Desktop 没有启动，或装好后还没新开终端；启动 Docker Desktop 后新开 PowerShell 再试 |
| 想让智能体从零开始（清空它写的程序与笔记） | 删除 `workspaces\<标签>\`；会话记录在数据卷 `celeste-claude-<标签>` 里，可用 `docker volume rm` 删除（需先 `docker rm -f celeste-agent-<标签>`） |
| 改了 `agent-container/` 之后 | 重新执行 `docker build -t celeste-agent:0.1 agent-container`；主控发现镜像变了会自动重建容器，工作区保留 |
| `--provider deepseek` 提示找不到密钥 | 按 4.9 节建 `configs\local.providers.json`，或设环境变量 `DEEPSEEK_API_KEY` |
| 智能体总被提示"本章的规划轮次已经用完" | 只在 `--limit-planning` 时有：每个新房间按大小存入轮次（一屏 3 轮、至少 3 轮）、死亡补 1 轮，调用模拟器的消息才扣（见 4.1 节）；用完后 Bash 被拒绝。调试时想不受限制，加 `--free-planning` |
| 录像里没有规划回放 | 开模拟器时回放只画 `/sim` 的推演（自写模拟器的搜索没有记录）；关模拟器时只画智能体用 `show.trajectory()` 交来的轨迹（它没交就没有）；`--no-playback` 时都不画。主控输出里搜 `[playback]` |
| HUD 上思考很久不变 | `--no-live` 时思考只在每次 `act` 时更新；实时展示时取决于智能体有没有调用 `narrate`（看 `agent_events.jsonl`） |
| PowerShell 里中文显示成乱码 | 日志文件本身是 UTF-8；用 `tools\run_status.py` 查看，或先执行 `chcp 65001` |
