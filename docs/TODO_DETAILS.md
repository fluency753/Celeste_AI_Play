## 隔离试玩实例、扬声器监听与私有 OBS

### 背景与推进顺序

agent 长期占用、冻结个人 Celeste 进程，会妨碍用户游玩；共用存档和 Mod 设置也可能误改个人进度。此前的私有游戏及 portable OBS 重载验收已证明独立进程方向可行，但这些本机测试脚本还不是正式实例管理功能，覆盖边界见 [桥接重载说明](BRIDGE_RELOAD.md)。

首期提供一个持久化的 agent 专用游戏实例及实时扬声器监听开关，支持与个人游戏并行；暂不扩展多 agent 同时游玩。个人直播与 agent 录制并行的私有 OBS 可后续完成，但首期实例配置和资源归属须为其预留位置，不能继续默认操纵用户的 OBS。

### 持久化隔离游戏实例

- 默认使用专用存档；需要已有进度时，从用户明确选择的存档复制，后续仅写副本，不自动回写、覆盖或同步个人存档。
- 为实例独立维护 Saves、游戏与 Mod 设置、Mod 部署和启用列表、日志、缓存及录制目录。只复用确认只读的游戏素材；bootstrap 配置、运行时和其他可能被游戏／更新器写入的文件需独立处理，不能把可写目录链接回个人安装。
- 控制台支持创建、启动、暂停、续跑、更新与删除。实例目录及身份持久保存，重启后能接回原 agent 会话；复制与更新中断要能恢复，删除前明确存档和录像的保留方式。
- IPC、时钟、音频与 HUD 共享内存均按实例分配并校验身份。控制、捕获和关闭进程核对路径、PID 及创建时间，不仅按 Celeste.exe 名称查找；桥接已有所属主控时不得另连顶掉。实例维护不能隐式代选章节或传送。
- 遵循 Runtime 精简稳定原则：实例编排与日常功能优先放主控及 Bridge，只有必须跨桥接卸载连续存活的资源才由 Runtime 持有。

验收须实际同时运行个人游戏与 agent 实例，确认 agent 的输入、冻结、保存、维护更新、停止及故障恢复不会操作个人进程；对比个人存档、设置和 Mod 启用列表，证明副本进度不会回写。覆盖重连、端口冲突、进程退出与 PID 重用、创建／更新失败和删除时保留用户数据的流程。

### 实时开关隔离实例的扬声器声音

隔离实例默认关闭扬声器监听，HUD 提供实时开关并显示实际状态；主控持久化用户选择，重连、桥接重载和实例重启后恢复。能力面向指定实例，不修改个人游戏或系统总音量，不改写存档中的音量设置。

扬声器监听与录制音频分开控制。不能直接调整会镜像到独立录音混音器的主总线音量，造成录像一起静音。开关不能重启录制、重置音频计数或中断时钟，也不能因载荷重载临时恢复出声；实现前核对 Windows 音频会话与 FMOD 输出的实际边界，再确定资源归属。

验收须实际切换 HUD 并检查扬声器输出，以及独立录制的两条音轨：静音时个人游戏仍有声、隔离实例无声且录像两轨有声；恢复监听后即时生效，录像声音、音量与计时保持连续。覆盖音乐、一次性音效、Mod bank、暂停、桥接重载与重启后的设置恢复。分别报告真实输出和录音结果，不能只断言布尔字段或调用成功。

### 私有 OBS 与个人直播并行（后续阶段）

两个场景不保证直播与录制使用独立画面。采用独立目录的便携版 OBS，通过 `--portable --multi` 与个人 OBS 共存；配置、profile、场景集合、插件、日志、录制目录和控制接口均独立。主控只管理所属私有 OBS 的进程与编码器，启动、切场景、停止和收尾不得改动个人 OBS 的直播或设置。

正式支持配置插件时钟端口及音频共享内存目标；此前验收仅在本机副本修改两处硬编码端口，不能把这种手工步骤当作已实现的配置能力。捕获精确绑定 agent 游戏实例，避免两个 Celeste 进程同时存在时录到个人画面。评估双进程的捕获冲突及 CPU／GPU／编码资源需求，失败不能转而接管或停止个人 OBS。

验收实际同时进行个人直播与 agent 录制，分别检查两路输出画面、音频及帧序列，确认个人 OBS 切换场景不改变 agent 录制内容；agent 实例暂停、重载、重启、录制失败与独立收尾不打断直播。保留用户原 OBS 配置与进程身份的对比证据，不以私有录制单独成功代替并行验收。

## 全章地图与路线准备

### 提供完整章节地图，包含未访问房间

当前 `neighbors` 和模拟器的 `rooms` 只有房间名称、范围，详细观测只缓存已访问房间。补齐各房地形、实体定义与运动路径、危险物、出生点、检查点、触发器和候选出入口；提供章节索引与按房间查询，避免一次把全图塞进上下文。区分静态地图定义与当前实体状态，不以相邻范围冒充可通出口。

### 按入口区域表达房间连接

同一房间可能有互不连通的区域，只有房间名组成的邻接图不足以规划。记录候选连接的边界位置、进入区域、方向及机关条件，并用完整角色碰撞箱核验通路；静态连通和动态可达分别标注。

验收应覆盖从不同前房进入同一房间、却无法到达同一目标区域的情况。

### 增加正式速通前的路线准备与复用

先确定全章主路、分支与汇合点，以及关键机关、接触和出房位置／动量／资源目标，再执行房内动作。保存路线依据和待验证段，并随地图版本、章节面及目标变化校验失效；能力面向各执行器，地图读取不依赖开启模拟器。探索模式保留按访问范围提供信息的规则，不能默认泄露全图。

### 修正速通提示词的局部优化目标

当前强调把单房出门帧数优化到很难再快，容易忽略出房状态对后房的影响。改为服务于章节路线与后续入口条件，先概括关键机制如何产生连续房间的路线收益，再做局部模拟。以房9双重机关加速、带速进入9b直接横穿为验收案例，不能只比较房9的用时。

## 跨房验证与历史状态

### 扩展模拟器的跨房连续运行

当前止于开始换房，不能直接验证候选的连续衔接。需要模拟器核心源码／构建工程或协作者支持，正确执行转场及房间加载，保留或归一化玩家、输入、缓存和实体状态；不能通过手改速度、拼接单房结果冒充连续推演。静态全图查询与此能力分开提供。

### 自动留存关键位置的完整快照

当前首次入房缓存是观测，不是完整 `sim_state`，后者通常会被覆盖，复盘依赖智能体手动保存检查点。按运行保存入房、出房及必要检查点的完整状态、对应输入和版本来源，避免回访状态覆盖首次入房；明确原始快照与根据观测重建的近似状态。

验收应能恢复旧路线的起点，而无需猜补内部字段。

## 速通 TAS 优化器

### 背景：束搜索为什么会漏掉更优路线

来源：2026-10-27 Opus 5.5 探索系列赛中，智能体在自己的 C++ 模拟器上做的束搜索加密动作块后发现，动作更细的新宏集有时反而搜出更长的路线（15 个用例里 6 个更长；4A 一例旧宏集 114 帧、新宏集 123 帧，宽度开到 15000、调小每格上限、换更完整的去重键都找不回来），最后只好两套宏集各搜一遍取更短。原因：

- 束搜索每帧只保留固定数量的状态（宽 600，每格最多 6 个），本身不完备：一条路线的中间状态被挤出一次就再也接不回来。新宏集每个节点的子节点约是旧的 2.5 倍，同一帧桶的竞争更激烈。
- 它的评分是"已用帧 + 地形网格上的绕行距离 ÷ 参考速度 3.5 像素/帧"，像 A*，但估计值不看速度和重力：同一位置速度 390 与 0 的状态估计相同，先往回走去加速、补冲刺、借墙的状态显得"更远"而被淘汰。
- 3.5 像素/帧是一般速度，不是最快速度（ultra 约 6.5 像素/帧），估计值会高估快速状态的剩余时间，不是下界，即使按 A* 用也不保证最优。

所以束搜索适合快速找好解、给出上界；要证明最优，必须配合有可证明下界的精确搜索。整图纯暴力不可行：每帧有效输入几十种、状态是浮点（亚像素、速度），完全相同才能合并，组合数指数爆炸。TAS 圈的做法也是人定路线，再对短窗口做暴力或遗传算法的局部优化。

### 设计

1. **改进束搜索**：估计值加入速度——用放宽的物理模型预先算出"从这个位置、以这个速度区间到终点最少要几帧"的表；名额按位置、速度区间、冲刺数、是否着地分桶；多套评分并行取最优；宽度逐步加大直到结果不变（只作收敛证据）。
2. **段内最优性验证**：束搜索的解作为上界 L；分支定界（或 A*）对每个状态算可证明的下界（已用帧 + 剩余距离 ÷ 物理上可能的最大速度，或更紧的运动学下界），下界 ≥ L 的剪掉，其余全部展开。全部搜完即证明最优，或找到更短的解。下界越紧剪得越多；最高速度高时下界偏松，先用于几十到一两百帧的短段。输入用逐帧全输入，而不只是宏集。
3. **整章拼接**：按房间或检查点分段，每段保留一组 Pareto 出口状态（时间、位置、速度、冲刺；没有哪一个全面更差），再动态规划拼接。出房速度会影响下一间，不能只比时间。

### 验收

- 在 3A、4A 已知用例上，改进后的束搜索单用细粒度宏集不比粗宏集差。
- 对若干短段输出"找到的解 / 可证明下界"，至少有一段证明最优（两者相等）。
- 说明"最优"的前提：相对于模拟器（最优解常贴边，模拟有误差时实机可能复现不了）、输入粒度与分段方式。

## 结构整理

已经集中导航状态、执行器工作区能力、回放作业与来源交接、录像停止阶段及录音混音快照，契约与成因见 [Codex 整改复盘（可选参考）](codex/STATE_CONTRACTS.md)。下面仅列仍需推进的独立范围，不把完成的整改继续列为待办。

### 继续明确游戏编排边界

`ChapterNavigation` 已统一当前／待进入目标及确认消费，自动菜单与 agent 输入使用同一提交入口。`GameSession` 仍编排剧情、输入、目标计量及宿主收尾，后续按责任拆分状态与失败契约；不能仅搬函数或重新复制导航状态。

验收以同一流程经过不同入口时行为一致为准，覆盖自动／智能体模式、续跑、同章检查点和异常收尾；不增加主控隐式代按或传送。

### 统一宿主生命周期

实际工作区能力已由 `execution.py` 声明，提示词、工具、准备、聊天和游玩共用，保留 host Codex 的容器程序通道和 host Claude 的工具限制。后续继续统一准备、聊天、试玩的创建失败、取消、停止与释放接口，以及运行中／等待聊天／已退出的消费者语义。

验收须保留真实适配器分发，只模拟模型和外部进程；不同宿主入口不得漏释放，也不能为没有工作区能力的会话创建无用容器。

### 完善回放覆盖与压力验收

作业接收与关闭、搜索计费身份、原生已记账来源、读取背压及工作线程来源清理已集中。文件索引按表头流读，单条及整批解码前分别核验原始轨迹体量；不能把此体量预算等同于进程 RSS，解码数组和 RPC 临时副本仍有额外开销。

后续对持续并行写入、文件替换／字节回退、超过 128 个来源、公平轮询及慢消费者建立稳定的覆盖证据。区分读取、接管、绘制、房间过滤、因保护策略跳过与最终记账；超限必须记录原因，不得从计数完整推断画面完整。还需覆盖接管失败后的来源继续增长、部分复制与停止超时的组合；测试未覆盖本身不作为已确认缺陷。

### 统一事件镜像与时钟核验

源监听器／总线／VCA 快照现只采一次并应用两轨；本地暂停请求与祖先继承分离，冻结重建和 setter 镜像保留原契约。录像停止请求、采集确认、编码完成及落盘缓存也已分开。

后续整理事件级的初始字段同步与增量 setter，减少字段遗漏的机会；联动核验独立 FMOD 与 OBS 混音两条录音路线的样本单位和时钟。覆盖一次性音效、音量／参数变化、暂停恢复、双轨及块接缝，一条路线或局部舍入公式通过不能代替另一条路线的完整验收。

### 复用外部边界与公共契约测试

本轮回归已保留真实导航入口、工作线程、录制停止与执行器配置链，独立审查发现的二次缺陷也纳入复测。后续将菜单／进程／音频故障边界整理成可复用夹具，避免各测试自行预设成功；按模式、执行器和生命周期建立场景矩阵。

断言用户可见结果、计量与最终资源归属，复用共享音频校验；不以测试数量、统计完整或独立审查通过代替完整流程结论。

### 完善辅助程序输出的资源预算

原始 stdout/stderr 与工具预览已经分开，截断显式报告，长输出可以读完整文件。捕获仍使用整流内存，完整记录尚无单次／累计字节上限和回收规则；两个流各自发布最长 20 秒，发布耗时不能当作命令执行耗时。

后续统一流式捕获、单次与运行累计的内存／磁盘预算、发布总时限和失败回收；达到限制时保留明确的缺失范围，不静默丢头或让机器消费者解析预览。验收覆盖持续大量输出、超时、并发、发布失败及完整记录读取。
