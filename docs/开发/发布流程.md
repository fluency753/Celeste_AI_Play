# 发布流程

正式版与公测版在 GitHub Releases 发布；开发版就是主线上的每一次提交，不单独发布。控制台“关于”页的更新通道与“换版本”都按这里的约定识别版本，所以标签的名字和位置要照做。

## 版本号与标签

- **项目版本 = 控制台版本**：`overlay/console_api.py` 的 `CONSOLE_VERSION`，与启动器 `CelesteAIConsole.exe` 的文件版本相同（`tools/launcher/launcher.rc`、`launcher.manifest`，改完运行 `python tools/build_launcher.py`）。桥接 Mod 与常驻核心有各自的版本，写进版本摘要。
- 版本号规则不变：新功能递增中间位，修复递增末位；不轻易递增首位。
- **正式版**：带注释的标签 `vX.Y.Z`。**公测版**：`vX.Y.Z-beta.N`（或 `-rc.N`），在 GitHub 上勾选 Pre-release。控制台只按标签名区分两者，不看 GitHub 上的勾选。
- 标签只打在 GitHub 主线（`origin/main`）的提交上：控制台只认主线上的标签，换版本与一键更新都靠快进实现。
- 发布后不移动、不删除标签；要修正就发新的修复版本。

## 步骤

1. **确认主线可发**：没有未推送的改动；全量回归通过（`python -m unittest discover -s calibration -p '*_test.py'`）；本机实测过这个版本的主要改动。
2. **写版本摘要**：在根目录 `版本摘要.md` 最上面（说明段落之后）加一节：
   - 标题 `## X.Y.Z（YYYY-MM-DD）· 正式版`（公测版写 `X.Y.Z-beta.N（日期）· 公测版`）；
   - 第一行写组件版本：控制台、桥接 Mod、常驻核心；
   - 3～6 条要点，只写使用者能感受到的变化（新功能、行为变化、修复的明显问题、需要手动做的事，例如重新部署桥接 Mod 或重建镜像）；不写测试、内部重构与验证过程（这些在 `CHANGELOG.md` 与提交信息里）。
3. **提交并推送**版本摘要（连同版本号变动）。
> 云端的 Claude 开发会话不能推送标签（git 推送标签返回 403），也不能通过 GitHub 接口创建 Release（"not permitted for this session type"）。这时由维护者在 GitHub 网页上完成第 4、5 步：打开 Releases → Draft a new release，"Choose a tag" 输入 `vX.Y.Z` 并选 "Create new tag on publish"，Target 选 `main`（或在 Recent Commits 里选要发布的提交），填标题、粘贴说明，正式版勾 "Set as the latest release"、公测版勾 "Set as a pre-release"，再 Publish。网页建的是轻量标签，控制台同样识别。v1.14.0 就是这样发布的。

4. **打标签并推送**（能推送标签时）：

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z：一句话说明" <提交>
   git push origin vX.Y.Z
   ```

5. **建 GitHub Release**：标题 `vX.Y.Z · 一句话说明`，正文就是版本摘要里这一节（去掉标题行）；正式版设为 Latest，公测版勾选 Pre-release。命令行可以用 REST 接口：

   ```powershell
   gh api repos/fluency753/Celeste_AI_Play/releases -f tag_name=vX.Y.Z -f name="vX.Y.Z · 一句话说明" -F body=@release_notes.md -F prerelease=false -f make_latest=true
   ```

6. **等待组件构建并核对附件**：发布 Release 后，`.github/workflows/release-components.yml` 自动在 Windows 上检出该标签，使用固定工具链与校验值固定的标准 Everest 引用构建组件，校验标签属于 `origin/main`、版本及源码身份后上传。附件应包含 `Celeste_AI_Play-<标签>-components-windows-x64.zip`、`components.json`、`SHA256SUMS`。同名同校验值可安全跳过重试，不同内容拒绝覆盖。主线相关代码的 push 只构建候选 Artifact，不发布 Release；也可手动触发 workflow，填已有标签并选择是否上传。
7. **核对源码压缩包**：GitHub 的 Source code 压缩包由 `git archive` 生成，遵守 `.gitattributes` 的 `export-ignore`，不含 `docs/开发/`、`CHANGELOG.md`、`AGENTS.md`。本机可以先核对：`git archive --format=zip -o check.zip vX.Y.Z`，再列出其中的文件。
8. **在控制台核对**：“关于”页把更新通道选为正式版（或公测版），检查更新应显示刚发布的版本；“换版本”的列表里应出现这个标签。

## 发布说明的样子

```markdown
控制台 1.14.0，桥接 Mod 1.11.0，常驻核心 1.0.5。

- **新功能**：……
- **变化**：……
- **修复**：……
- **升级时要做**：运行 `setup.ps1 -Only bridge` 安装组件；仅 Runtime 变化或首次安装才安排维护重启，兼容桥接可受控重载。
```

首个正式版（1.14.0）的说明是整个项目当时的能力概览，之后的版本只写相对上一个正式版或公测版的变化。

## 本机构建与补传组件

```powershell
python tools/package_release.py --tag vX.Y.Z --output build/release
python tools/publish_release.py --tag vX.Y.Z --check
# 由环境变量 GH_TOKEN 提供当前仓库 Contents:write 令牌；不要写入文件或命令参数
python tools/publish_release.py --tag vX.Y.Z
```

发布器只向**已存在**的 Release 上传附件，不创建 Release、不创建或移动标签。必须在该标签的干净检出上运行，标签提交属于已同步的 `origin/main`；本机 Git 远端同步仍使用 SSH。不能上传本机显式引用目录生成的验证候选，也不能把未提交源码或其他工具链的产物标成正式包。失败保留已有附件；修正内容应发布新版本。

`configs/component_build.json` 固定标准 Everest 6642 引用包的 SHA256、OBS 33.0.0、.NET SDK 10.0.400 与 ziglang 0.16.0（生产程序集仍目标 .NET 8）。引用包只供编译，不上传游戏程序集。新 OBS 版本需明确更新兼容范围并验证，不能把一个 DLL 无条件标成适配所有版本。组件 ZIP 的固定内容、安装校验、无 Git 源码包与运行中保护见 [预编译组件说明](../../docs/PREBUILT_COMPONENTS.md)。
