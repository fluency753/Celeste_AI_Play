# 发布流程

正式版与公测版在 GitHub Releases 发布；开发版就是主线上的每一次提交，不单独发布。控制台“关于”页的更新通道与“换版本”都按这里的约定识别版本，所以标签的名字和位置要照做。

## 版本号与标签

- **项目版本 = 控制台版本**：`overlay/console_api.py` 的 `CONSOLE_VERSION`，与启动器 `CelesteAIConsole.exe` 的文件版本相同（`tools/launcher/launcher.rc`、`launcher.manifest`，改完运行 `python tools/build_launcher.py`）。桥接 Mod 与常驻核心有各自的版本，写进版本摘要。
- 版本号规则不变：新功能递增中间位，修复递增末位；不轻易递增首位。
- **正式版**：带注释的标签 `vX.Y.Z`。**公测版**：`vX.Y.Z-beta.N`（或 `-rc.N`），在 GitHub 上勾选 Pre-release。控制台只按标签名区分两者，不看 GitHub 上的勾选。
- 标签只打在 GitHub 主线（`origin/main`）的提交上：控制台只认主线上的标签，换版本与一键更新都靠快进实现。
- 发布后不移动、不删除标签；要修正就发新的修复版本。

## 步骤

1. **确认主线可发**：没有未推送的改动；全量回归通过（`python -m unittest discover -s calibration -p '*_test.py'`）；本机实测过这个版本的主要改动。
2. **写版本摘要**：在根目录 `版本摘要.md` 最上面（说明段落之后）加一节：
   - 标题 `## X.Y.Z（YYYY-MM-DD）· 正式版`（公测版写 `X.Y.Z-beta.N（日期）· 公测版`）；
   - 第一行写组件版本：控制台、桥接 Mod、常驻核心；
   - 3～6 条要点，只写使用者能感受到的变化（新功能、行为变化、修复的明显问题、需要手动做的事，例如重新部署桥接 Mod 或重建镜像）；不写测试、内部重构与验证过程（这些在 `CHANGELOG.md` 与提交信息里）。
3. **提交并推送**版本摘要（连同版本号变动）。
4. **打标签并推送**：

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z：一句话说明" <提交>
   git push origin vX.Y.Z
   ```

5. **建 GitHub Release**：标题 `vX.Y.Z · 一句话说明`，正文就是版本摘要里这一节（去掉标题行）；正式版设为 Latest，公测版勾选 Pre-release。命令行可以用 REST 接口：

   ```powershell
   gh api repos/fluency753/Celeste_AI_Play/releases -f tag_name=vX.Y.Z -f name="vX.Y.Z · 一句话说明" -F body=@release_notes.md -F prerelease=false -f make_latest=true
   ```

6. **核对发布压缩包**：GitHub 的 Source code 压缩包由 `git archive` 生成，遵守 `.gitattributes` 的 `export-ignore`，不含 `docs/开发/`、`CHANGELOG.md`、`AGENTS.md`。本机可以先核对：`git archive --format=zip -o check.zip vX.Y.Z`，再列出其中的文件。
7. **在控制台核对**：“关于”页把更新通道选为正式版（或公测版），检查更新应显示刚发布的版本；“换版本”的列表里应出现这个标签。

## 发布说明的样子

```markdown
控制台 1.14.0，桥接 Mod 1.11.0，常驻核心 1.0.5。

- **新功能**：……
- **变化**：……
- **修复**：……
- **升级时要做**：桥接 Mod 有新版本，关掉游戏后运行 `setup.ps1 -Only bridge`。
```

首个正式版（1.14.0）的说明是整个项目当时的能力概览，之后的版本只写相对上一个正式版或公测版的变化。
