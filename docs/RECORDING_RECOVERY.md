# 编码器退出后的录制恢复

普通 `--resume` 优先接续已有录制，不默认新建 recording 目录。编码器和独立音频仍存活时沿用 `Recorder.adopt`，不停止或重启；原编码器已结束或失败时，恢复到同一逻辑目录与 `session.id`。`--new-recording` 仍是明确放弃原会话、另开录像的选项。

例外：`--resume` 加 `--chapters`（或 `--segments`）追加下一章、且原录制会话已经正常收尾（`finished`）时，与以往追加章节一样在新运行目录另起新录像，上一章的录像目录、`gameplay.mp4` 与 `gameplay_pure.mp4` 完全不动，主控输出里写明原因。`failed`、仍在录或尚未收尾的会话不受此例外影响。被标成放弃（`abandoned`）的会话不能再恢复，续跑须明确加 `--new-recording` 或 `--no-record`；`--no-record` 只接受已经结束（`finished`、`failed` 或放弃）的会话。

## 采集与累计产物

维护中断若不能直接保留活编码器，只关闭本段采集并等待编码器终态，不立即做累计发布或纯享版转码。会话保持 `finishing`，另记 `postprocess_pending`，不会被 `--no-record` 或追加章节误当作已完成录像；正常 `--resume` 仍接回同一录制，最终正常停止时补齐累计成片与纯享版。

正常观察到本会话编码器 `finished` 后，主控将实际采集目录、会话 ID、帧数及媒体 SHA256 写入 `capture_complete.json`。恢复核对凭据、文件指纹、连续 CSV 行、两轨 PCM 计量及完整包时间戳后，可跳过整段解码；报告 `validation=clean-encoder-packets`。仍需顺序读取文件和媒体包，不是零成本。旧录像、失败采集、凭据缺失／不匹配或包计量异常仍完整解码，报告 `validation=decoded`；不为旧录像补造正常关闭凭据。

新编码器只向原目录下 `.recovery/attempt-*` 写入，避免插件的 FFmpeg `-y`、WAV `wb` 和 CSV `w` 覆盖旧内容。`.recovery/ledger.json` 是实际采集目录的权威来源；主控收尾、重连、所有权检查和继续录制均核对此目录。运行目录的 `recording_session.json` 始终指向原逻辑会话。

首次恢复把原始视频、音轨和 CSV 保存到 `.recovery/base`。核验不可变源后生成完整前缀；新片段封闭时，将这些前缀与片段合并回原逻辑目录的 `video.mkv`、`audio.wav`、`audio_play.wav`、`frames.csv`、`segments.csv`。这里是经过校验的拼接与重新封装，不是向已关闭的 MKV 末尾盲目追加字节。录像仍在采集时，根目录保留上次发布的累计内容，新增内容位于当前 attempt；最终累计成片在收尾后发布。

视频须能解码且编码格式、尺寸、像素格式、帧率兼容；恢复目前要求 60 fps 视频和 48 kHz 双声道 float PCM。完整音轨每个视频帧对应 800 个样本，纯享音轨仅对应 `chapter_ticks >= 0` 的真实游玩帧。恢复不补静音、不伪造帧：仅采用视频、完整 CSV 行及音轨共同覆盖的完整前缀，残缺尾部原件保留，计量与原因记入恢复报告。不能安全确定前缀时停止恢复并给出原因。

视频前缀按帧精确选取：默认 x264 参数带 B 帧，编码器被强制结束后，解码顺序的最后几个包对应的显示帧并不连续（例如只有 …70、72、74）。严格恢复先完整解码一次这段源视频，得到从 0 起连续可解码的帧数，再在不超过完整 CSV 行与 PCM 的范围内，取最大的 M，使解码顺序前 M 个包正好是显示帧 0…M-1（mini-GOP 边界）；文件提前结束（ffprobe 报告 `File ended prematurely` 等错误）时最后一个包可能残缺，不予采用。CSV 与两路 PCM 用同一个 M。裁剪后的前缀与累计成片只按包时间戳核验（每帧恰好一个包、正好覆盖 0…帧数-1，拼接处不会把旧片段的帧插进新片段的 B 帧之间），不再重复完整解码；严格路径每段源视频只完整解码一次，结果随前缀报告缓存，超时按帧数放宽（至少 30 分钟，约按每秒 20 帧估计）。报告里的 `contiguous_video_frames`、`video_packets`、`video_ended_prematurely` 记录取舍依据。

累计媒体 index 连续重排，`game_frame` 与实测时间戳保留。恢复边界单独记录，游戏重启造成的帧号回退与真正漏帧分别报告；正向缺帧不会因为经过恢复而被隐去。`segments.csv` 的序号和首帧偏移相应累加。

## 失败、重试与所有权

- 文件处理前须确认原采集已停止；活跃的其他录制、仍在收尾的编码器或仍被写入的源文件均拒绝恢复。OBS 断开时保持原文件，连接后再试。
- 在用主控发现 OBS 断开，或重启后变成 idle、无法确定原捕获归属时，立即保持暂停并说明处理办法（OBS 重新连上且原采集仍在时可直接继续，否则先中断主控再正常 `--resume` 走恢复入口）；不发停止、不等待收尾，失败采集的收尾正在进行时也一样。不会把旧 Recorder 的 started 状态当作仍在录制，也不会盲目停止未知采集。收尾时发现 OBS 已重启，也不再空等编码器结束，直接把会话留作未收尾，正常续跑时恢复。
- start 请求发送前持久化请求状态。确认丢失后按原 session、ledger 和精确 attempt 目录认领已经启动的采集，不重复 start、不覆盖同一片段。重试时等待一段时间仍看不到该目录的采集：若 OBS 已空闲（连着桥接、没有锁步、没有在录或收尾、独立音频也已停）而 attempt 目录里已有文件，说明采集启动过又结束了，按普通恢复把它收为一个片段再开新片段；若目录一直为空，先补发一次停止（排在任何可能还在 OBS 里排队的 start 之后），确认仍为空后把它换成新的 attempt 目录再启动——原空目录保留不用、记入 ledger 的 `unstarted_attempts`，即使旧请求极晚才执行也只会写进那个空目录，不会与新采集争同一目录或同时录两段（插件同一时间只有一个输出，之后的检查会发现目录变化并暂停）。OBS 仍忙或未连接时保持原交接并提示，不重复 start。
- 合并使用固定 generation、候选文件哈希和发布 journal。多个文件的替换不具有整体原子性，只有全部替换完成后才发布累计状态。中途失败可按同一 journal 重试，输入始终来自不可变源，不会把已经累计的根目录再拼一次。
- ledger 损坏、身份不符、路径逃逸或缺失时不能静默回退到根目录。录制目录的恢复锁在进程退出后由系统释放。
- 旧版成片和结果缓存以同盘重命名移入本次 generation 的 `previous-*`，再按新累计内容重新生成成片与纯享版，避免展示过期视频。原件不会被删除：中途失败时它要么还在原处，要么已完整移入备份；备份位置已有同名文件（例如旧版本复制到一半留下的残片）时，先把它改名为 `previous-*.stale-*` 留着，不当作可信备份。

恢复前缀、规范化片段和发布候选需要额外磁盘空间，而且只增不减：首次恢复备份一份原件（`base`），每段采集各有一份规范化前缀，每次收尾发布都新建一份完整累计副本（`generation-*`），旧成片也移入其中；主控不会自动删除这些副本，每次恢复和收尾都在输出里报告 `.recovery` 的当前占用（收尾摘要的 `recovery_bytes`），确认成片无误后由用户自行决定是否整理。磁盘不足时保留源文件及交接记录，不通过删除旧片或悄悄另开会话兜底。请在停止采集后处理恢复目录，不要在录制中手工更改 ledger 或移动片段。

当前 WAV 使用 32 位 RIFF 长度，累计完整轨 PCM 上限约 4 GiB，对应约 186 分钟的实际录像（包含回放）。超过上限会在累计发布前明确拒绝并保留原片段，尚不支持 RF64 长音轨；墙钟思考／暂停时间不计入此时长。

独立音频停止后重建，会按当前实时游戏状态种入事件。恢复保证的是已有样本保留、帧与样本计量正确，以及新片段继续有声；不承诺跨编码器故障的音乐播放位置或波形接缝完全无跳变。保留活编码器的普通接续及兼容 Bridge 重载仍优先使用原资源。

## 验证

默认回归包含生产录制生命周期与恢复分发；`calibration/recording_recovery_media_test.py` 使用真实 FFmpeg／ffprobe 验证多次恢复、回放双轨、像素与 PCM 保留、残缺尾部、格式拒绝、文件写占用、坏 journal 和发布中断重试，并用生产同款 `libx264 -preset veryfast -crf 16 -g 120`（带 B 帧）的视频在 55%／70%／80%／90% 处截断，逐帧核对前缀正好是显示帧 0…M-1、拼接后旧片段与新片段的帧序完全一致、两路 PCM 与 CSV 同步；ffprobe 不在 ffmpeg 旁边时使用 PATH 中的 ffprobe，两者都没有才跳过。

`calibration/recording_recovery_acceptance.py` 为显式运行的私有游戏／portable OBS 验收，要求指定私有 PID 和独立端口。覆盖真实编码器结束后的多次恢复、retain／adopt、含回放采集、最终成片完整解码及两路音轨；不得对在用主控或个人 OBS 运行此测试。
