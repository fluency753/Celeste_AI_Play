# 搜索方法：用有限的知识更高效地找出更优的路线

本文件讲"怎样写搜索程序"，不讲任何房间、路线或技巧的具体用法。这些方法不依赖你事先知道技巧的名字：只要模拟器把规则算对，好的搜索会把技巧当作最短路线的一部分自然找出来。

适用对象：用预置模拟器（`/sim` 的 `Sim`、`SimPool`）或自己写的模拟器搜索输入序列的程序。速通模式开了预置模拟器时，它与游戏逐帧一致，第 7 节的校准主要针对自己写的模拟器或简化模型。

先说结论：**纯随机拼按键**（从一组固定组合里随机抽、随机按几帧）实现简单，但大量算力花在重复和无望的路线上，时机严格的操作（1–2 帧窗口）几乎抽不中，"没搜到"也分不清是做不到还是没撞上。下面七种方法按收益大致排序，可以组合使用。

---

## 1. 按状态去重的逐层搜索（束搜索 / beam search）

- **做法**：从起始状态出发，每一层在所有保留的状态上展开一组候选输入（一帧或一段），得到下一层的状态；用**状态键**合并相同或几乎相同的状态，再按评分（见第 2 节）只保留最有希望的前 N 个，继续展开。到达目标时，层数就是帧数。
- **为什么有效**：不同按键序列走到同一个状态，只算一次；把预算集中在最好的一批状态上。帧数最优的路线会在前几层的竞争里浮现，super、hyper、wallbounce 之类的技巧就是其中某几步，不需要事先写进动作集。
- **状态键要包含所有影响未来的量**，否则会误合并、剪掉真正的好路线：
  - 位置（含 subpixel 余数，或按 0.25 px 之类的精度取整）、速度、状态机状态、朝向；
  - 冲刺次数、体力（可分段取整）、各种计时器（variable jump、coyote、dash cooldown、dash attack、冲刺状态内的帧号）；
  - **上一帧按住的键**：跳、冲刺、抓的"按下"由松开到按住的边沿触发，同样位置但按键状态不同，未来能做的动作不同；
  - 会动的实体所处的相位（移动块、刺球路径、开关状态），或者把"从起点算起的帧号"放进键里。
- **支配剪枝**（可选）：同一个位置格子里，若一个状态在冲刺次数、体力、朝目标的速度上都不差于另一个，后者可以丢掉。只在你确定这些量"越多越好"时用。
- **多样性**：只按总分取前 N 容易全部挤在同一条走廊里。可以按位置格子分桶，每个桶保留各自最好的几个，再取整体前 N。
- **并行时**：主进程单核做的汇总与进程间传输容易成为瓶颈。去重只在主进程做，不要每层把越来越大的去重集合或完整状态发给各子进程；子进程把候选的分数、序号和去重键全部回传，不要各自先截取前几名；主进程选定保留的节点后，再由子进程从父节点重放生成。并行版本要用同样的输入与单核对比，确认结果完全一致。

## 2. 用评分代替"碰到才算成功"

- **做法**：给每个状态（或每条路线的终点）打分，而不是只分"到达目标 / 没到达"。常用的分量：
  - 到目标的距离（直线距离，或沿一串中间点的路径距离——隔墙时直线距离会误导，见第 6 节）；
  - 朝目标方向的速度、剩余冲刺与体力（为后续动作留资源）；
  - 已用帧数（同样到达时帧数少的优先）；死亡直接淘汰。
- **为什么有效**：失败的路线不再白费，它们告诉搜索"哪边更接近"；束搜索（第 1 节）和交叉熵法（第 3 节）都需要评分来决定保留谁。
- **注意**：分数只是引导，容易陷进"离目标很近但被墙隔着"的局部最优。配合多样性保留和分段中间点使用。

## 3. 按好结果调整抽样（交叉熵法 / CEM）

- **做法**：保留随机抽样的框架，但让抽样分布逐轮学习：
  1. 按当前分布抽一批输入序列，用模拟器跑完并打分；
  2. 取得分最高的一小部分（例如前 5%–10%）作为"精英"；
  3. 统计精英在每个时间段（或每个决策点）上选了哪些按键组合、按了多久，把分布往这些选择上调；
  4. 重复若干轮，保留一定的随机性（例如混入 10%–20% 的均匀分布），避免过早收敛。
- **为什么有效**：时机严格的操作在均匀随机下几乎抽不中，但只要偶尔有一条接近成功的样本，它的按键时机就会在下一轮被放大。这相当于让程序自己"发现"技巧。
- **代价**：改动最小，能直接套在现有的随机抽样程序上；需要一个合理的评分（第 2 节）。

## 4. 只在关键时刻分支

- **做法**：输入只在会改变后果的时刻才值得改变。把"决策点"放在这些事件上，事件之间保持按键不变：
  - 落地、离地（coyote 计时开始）、贴墙或离墙；
  - 冲刺被受理、冲刺结束（F14/F15）、冲刺恢复、variable jump 结束；
  - 碰到弹簧、泡泡、可交互物，体力快耗尽，会动的实体换相位。
- **为什么有效**：每帧都分支时组合数爆炸；固定步长随机切换又会错过窗口。按事件分支把搜索空间压缩到真正有区别的选择上。
- **注意**：有些窗口在事件之后若干帧（例如冲刺途中第几帧起跳），可以在事件点展开"再等 k 帧再按"的一小组候选，而不是只在事件那一帧按。

## 5. 补全动作集

- 冲刺 8 个方向都要有（含左、左上、左下、正下），左右对称，不要只靠整体镜像。
- crouch dash（Z / 冲刺第 0 帧按住下）、跳键的**松开时机**（决定跳多高）、抓的按住与松开、只按方向不按跳等，都是不同的动作。
- 两个跳键、两个冲刺键（J/K、X/Y）可以在相邻帧各产生一次"按下"，连续按同一个键则必须中间松开一帧——动作集要能表达这一点。
- 发现某种组合反复出现在好路线里时，把它做成一个"整块动作"（例如"冲刺方向 d，k 帧后起跳"）加进动作集，提高它被选中的概率。

## 6. 分段搜索，复用中间状态

- **做法**：先确定几个有依据的中间点（能落脚的顶面、能抓的墙面、开口、出口），分段搜索；每到达一个中间点，保存几种有代表性的好状态（位置、速度、资源不同），下一段从这些状态出发。
- **为什么有效**：一次搜完整个房间要很长的序列，搜索空间随长度指数增长；分段后每段都短，而且隔墙时用"沿中间点的路径距离"打分不会被直线距离误导。
- **复用**：真实执行后出现偏差时，从最近的、仍然成立的中间状态重新搜，不必从房间起点重算。已验证的输入前缀可以直接作为下一段的开头。
- **注意**：每段只优化本段的帧数，可能牺牲后面需要的速度或资源；中间点的评分里要考虑"带着多少速度和冲刺离开"。

## 7. 定期对照真实游戏校准模拟器

- **做法**：把同一个起始状态、同一串输入在模拟器里的轨迹，与真实执行返回的逐帧轨迹对比，找出**第一个不一致的帧**，修正模型；把出过错的情形存成回归用例，改模拟器之后先跑一遍。
- **为什么重要**：模拟器错了，搜得越多越浪费，而且会稳定地给出"在模拟器里成立、在游戏里失败"的路线。
- **配合**：计划文件可以带上预期轨迹（`expect` 与 `tolerance`），真实执行一偏离就停下（`deviate`），及早发现模型误差。预置模拟器与游戏逐帧一致时，不一致通常来自起始状态没取对（例如漏了实体相位、按键状态或计时器）。

## 附：实现上的常见坑

- 搜索与模拟的循环里不要反复读写工作区文件（每次试验都重新读观测、扫描历史记录或写状态文件）：`/workspace` 是从主机挂载进容器的目录，比容器内的 `/tmp` 慢得多。需要的数据先一次读进内存或拷到 `/tmp`，模拟器对象尽量只构造一次再复用（复用前确认没有残留上一次试验的状态）。
- 多进程时用遇到子进程崩溃会报错的进程池（例如 `concurrent.futures.ProcessPoolExecutor` 的 `BrokenProcessPool`），或逐个收结果并设超时、边算边输出；`multiprocessing.Pool.map` 在子进程意外退出时会一直等不到丢失的那份结果。
- 先用小批量估计吞吐，再决定一次搜多少；结果按"最好的几条 + 搜索统计（展开了多少状态、合并了多少、最好分数随轮次的变化）"输出，便于判断该继续、换假设还是执行。
