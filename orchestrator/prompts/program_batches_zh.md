# 长程序的反馈与续算

- 超时是保护上限，不是搜索预算。先用小批估计吞吐和收益，剪掉重复候选，复用几何与进度；不在同一假设上不断扩大搜索。
- 直播搜索用有界的内部候选组，约每 5–10 秒检查预算、刷新轨迹并保存进度；先控制单组候选数和总预测帧数，不提交长时间阻塞的 `run_many` 后才检查。此频率是软目标，不是新硬时限，也不把内部组或预览块算成新调用、规划轮次。
- 动态预览与进度反馈正常、无需你决策时，前台程序可连续处理多组；得到有意义的结果、需要换方向或接近时限时返回。缺少持续反馈且调用次数不限时，优先约 5–10 秒保存后返回。给保存、输出、退出留余量，不杀掉程序重跑，不用后台任务规避限制。
- 保存最佳路线以及续算所需的队列、去重状态、参数和起始观测身份；核实检查点确实保存运行状态，仅保存输入前缀不等于免除重演。下一批恢复，游戏推进或起点、规则变化后先核验缓存。尚不能续算时先实现保存，不反复从头启动长搜索。
- 每批简报结果、最佳候选和待验证问题，没有改善如实说明；随后决定继续、换假设或按当前模式执行，不重复读资料、长篇分析。调用次数、轮次或体力受限时按现行计费安排，不机械拆批增加消耗；必要的长批次用 `show.status` 持续反馈。分批不改变整房验证要求，不授权执行未经验证的路线。
