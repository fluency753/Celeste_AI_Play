# 从房间数据建立路线

房间路线由你根据原始几何和游戏机制判断，主控提供数据，不预先给出可达性结论。

- **先取得全房间数据。** 使用进入新房间时返回的完整 JSON，或读取 `/workspace/game/latest_obs.json` 的 `obs`：`level.bounds`、`solids`、所有 `entities`、`exits` 和 `player.hitbox`。坐标是世界像素，矩形为左上角与宽高。用 `frame`、章节和房间核对数据身份；缺少地形数据不表示没有障碍，需重新观测。截图帮助理解场景，不能代替完整碰撞数据。
- **先构建空间关系，再选搜索目标。** 从地形矩形的边缘、实际开口和通道宽高，判断角色身体能经过哪些空间，找出能站立的顶面、可抓墙面及它们之间的连接。必要时自行写程序处理整个房间：可用角色矩形扫过候选通道，或把障碍按碰撞箱尺寸扩张后分析角色锚点的可通行空间。不要只连角色中心与目标点，也不要把到目标的直线距离变小当作通路成立。
- **把空间通路与动作可行性分开验证。** 在候选通路上结合支撑、所需高差、速度、冲刺、体力和危险物设计动作。区分静态地形、单向平台、可破坏物、梦境块和移动实体，查看 `collidable`、`shape` 与状态；站立身体过不去不代表下蹲、特殊机制或其他时机一定过不去。机制不明时保留假设，用针对性的模拟或真实结果验证。
- 碰撞状态、形状或姿态尺寸缺失时，查接口资料或做针对性验证；缺字段不是“不碰撞”，假定的身体尺寸也不是已验证事实。
- **出口和目标都需要实际入口。** `exits` 只是相邻房间边界的投影，先找真实开口及通向它的空间。对隔墙的物体、另一片区域或边界目标，明确准备通过哪个开口、姿态或机制到达；找不到依据时换候选目标或核验疑点，不在相同假设上持续增加搜索。可能需从其他房间进入的区域记作待查，而非认定当前必达或永久不可达。
- **按结果修正自己的空间模型。** 在笔记或程序里保留已验证的通道、连接依据、失败假设及适用条件。换房、碰撞状态变化或预测偏离时更新相关部分，未变化的数据和结论继续复用。探索模式用这些信息选择近期尝试；速通模式据此规划并优化整房路线，保持各自的执行规则。
- 候选优先级遵循本次目标与模式。空间分析足以筛选有依据的候选后就转入动作验证，其余区域记作待查，不必穷举；这不免除速通模式执行前对整房路线的推演要求。
