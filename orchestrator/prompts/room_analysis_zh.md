# 从房间数据建立路线

房间路线由你根据原始几何和游戏机制判断，主控提供数据，不预先给出可达性结论。

- **先取得全房间数据。** {observation_source_rule}：优先看统一 `collision` 和随工具返回的碰撞图，再结合 `entities` 的机制状态、`exits` 和 `player.hitbox`。`collision.objects` 同时包含地形与实体固体、单向平台、危险物和触发类对象，不能只读旧 `solids`。先核对帧号、章节和房间；`scope=view` 只覆盖局部，`complete` 表示该范围内地形与实体均已提供，`geometryComplete=false` 表示仍有未知形状，均不能按空白或已验证安全处理。坐标为世界像素。旧接口没有统一快照时，仍须合看地形与全部实体。
- **密集危险物按需精读。** 默认共享形状和分组说明见接口；先看完整碰撞图与分布，再用 `observe(detail="geometry", region=[x,y,w,h])` 核验候选通道，不展开打印全房重复危险物。分组范围不是实心障碍，也不证明组间空隙可走。
- **动态状态只对快照帧成立。** 实体 `mutable=true` 表示后续可能移动、变形、失去碰撞或消失，当前零速或未观察到移动不代表静态；`collidable=false` 仍保留形状但当前不参与碰撞。`kind` 是碰撞类别而非永不可穿越，梦境块、门等还要结合 `category` 和状态。圆形、组合和稀疏 Grid 使用真实 `geometry`，未知形状不能用包围盒当实心。碰撞图的分色帮助快速发现阻挡，不提供未来可达性结论；`game/rooms/` 是历史快照，不能作为当前实体位置。
- **先构建空间关系，再选搜索目标。** 从地形矩形的边缘、实际开口和通道宽高，判断角色身体能经过哪些空间，找出能站立的顶面、可抓墙面及它们之间的连接。{geometry_program_rule}不要只连角色中心与目标点，也不要把到目标的直线距离变小当作通路成立。
- **把空间通路与动作可行性分开验证。** 在候选通路上结合支撑、所需高差、速度、冲刺、体力和危险物设计动作。区分静态地形、单向平台、可破坏物、梦境块和移动实体，查看 `collidable`、`shape` 与状态；站立身体过不去不代表下蹲、特殊机制或其他时机一定过不去。机制不明时保留假设，用针对性的模拟或真实结果验证。
- 碰撞状态、形状或姿态尺寸缺失时，查接口资料或做针对性验证；缺字段不是“不碰撞”，假定的身体尺寸也不是已验证事实。
- **出口和目标都需要实际入口。** `exits` 只是相邻房间边界的投影，先找真实开口及通向它的空间。对隔墙的物体、另一片区域或边界目标，明确准备通过哪个开口、姿态或机制到达；找不到依据时换候选目标或核验疑点，不在相同假设上持续增加搜索。可能需从其他房间进入的区域记作待查，而非认定当前必达或永久不可达。
- **按结果修正自己的空间模型。** {geometry_record_rule}换房、碰撞状态变化或预测偏离时更新相关部分，未变化的数据和结论继续复用。探索模式用这些信息选择近期尝试；速通模式据此规划并优化整房路线，保持各自的执行规则。
- 候选优先级遵循本次目标与模式。空间分析足以筛选有依据的候选后就转入动作验证，其余区域记作待查，不必穷举；这不免除速通模式执行前对整房路线的推演要求。
